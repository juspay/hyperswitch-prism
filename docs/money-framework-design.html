Money Framework Design

Why we can't ban i64 — and why we don't need to

The Goal

Prevent connector code from constructing, tampering with, or incorrectly formatting payment amounts. Every amount that reaches a connector's wire format must pass through AmountConvertor, which handles currency-specific decimal conversions (e.g., JPY has 0 decimals, KWD has 3).

Why Banning i64 Is Impossible

The Problem

i64 is a primitive type used everywhere in connector structs — for amounts, yes, but also for timestamps, retry counts, expiry values, status codes, and dozens of other fields. There is no way to distinguish an "amount i64" from a "non-amount i64" at compile time or via a lint. 

struct ConnectorRequest {
    amount: i64,          // this is an amount — dangerous
    retry_count: i64,     // this is NOT an amount — perfectly fine
    timestamp: i64,        // this is NOT an amount — perfectly fine
    expiry_month: i64,     // this is NOT an amount — perfectly fine
}

A grep or lint rule cannot know which i64 fields represent money. Banning i64 entirely would break every connector in the system. There is no semantic marker on a primitive type.

The Actual Solution: Make MinorUnit Opaque

Instead of banning the output type (i64), we control the input type (MinorUnit). If connectors cannot extract a raw number from MinorUnit, they cannot assign it to an i64 field — and they are forced to use ConnectorMinorUnit (which comes from AmountConvertor).

The Safe Path

MinorUnit (domain, opaque)
↓ AmountConvertor::convert()
ConnectorMinorUnit (connector, has Serialize + Display)
↓ serde / Display
JSON / XML / String (wire format)
Why This Works

ConnectorMinorUnit has no public constructor. The only way to obtain one is through AmountConvertor::convert(), which performs the correct currency-aware conversion. Once a connector has a ConnectorMinorUnit, it serializes correctly via Serialize or Display — no raw i64 is ever exposed.

The Blocked Path

MinorUnit (domain, opaque)
↓ .get_amount_as_i64()? ✗ BLOCKED — requires trait import
↓ .to_string()? ✗ BLOCKED — Display removed
↓ .0? ✗ BLOCKED — field is private
↓ MinorUnit::new(i64)? ✗ BLOCKED — requires trait import
i64 ← connector cannot reach this

What Is Blocked vs. What Is Open

Operation Status How
MinorUnit(value) — direct construction Blocked Inner field is private
MinorUnit::new(i64) — constructor Blocked Behind MinorUnitProtoAccess trait; CI lint bans import in connector code
.get_amount_as_i64() — extractor Blocked Behind MinorUnitProtoAccess trait; CI lint bans import in connector code
Display / .to_string() Blocked Display trait removed from MinorUnit
Add, Sub, Mul Blocked Trait impls removed; methods are pub(crate)
Serialize / Deserialize Limited Leak Available due to Cargo feature unification; but deserialized MinorUnit is opaque — value cannot be extracted
Debug / {:?} Limited Leak Prints MinorUnit(5000) — not cleanly parseable; needed for error messages and logging
PartialEq, PartialOrd Open Comparison only — returns bool, does not leak the value
Default Open Only produces MinorUnit(0) — a known-safe value
ConnectorMinorUnit — Serialize, Display Open Intended for connector wire formats; value came through AmountConvertor

Two Layers of Enforcement

Layer 1 — Compiler (Trait Gating)

MinorUnit::new() and .get_amount_as_i64() are methods on the MinorUnitProtoAccess trait. Without importing the trait, the compiler rejects the call: 

// Connector code — no trait import
let raw = minor_unit.get_amount_as_i64();
//        ^^^^^^^^^^^^^^^^^ ERROR: method not found
//        help: trait `MinorUnitProtoAccess` provides `get_amount_as_i64`
//              consider importing it

The compiler tells the developer exactly which trait to import. If they follow the suggestion, the code compiles locally — but then Layer 2 catches it.

Layer 2 — CI Lint (Import Ban)

# CI pipeline check
grep -rn "proto_boundary" crates/integrations/ --include="*.rs" \
  | grep -v "test.rs" \
  && echo "FAIL: connector code must not import proto_boundary" \
  && exit 1

If a developer adds the trait import to make it compile, the CI check fails and the PR cannot merge. The developer must find the correct approach: use AmountConvertor to get ConnectorMinorUnit.

Why Not Ban MinorUnit Entirely from Connector Code?

Connectors receive domain request structs that contain MinorUnit fields: 

// domain_types — connectors receive this struct
pub struct PaymentsAuthorizeData {
    pub minor_amount: MinorUnit,
    pub currency: Currency,
    // ...
}

The connector sees MinorUnit as a type in these structs. It cannot avoid referencing the type. But it cannot do anything dangerous with it — it can only pass the value through AmountConvertor::convert() to get a ConnectorMinorUnit.

Summary

We cannot ban i64 because it's a primitive type used for non-amount fields throughout connector code. No lint can distinguish "amount i64" from "timestamp i64."

Instead, we make MinorUnit opaque so connectors cannot extract a raw i64 from it. This forces them to use ConnectorMinorUnit (obtained via AmountConvertor) in their wire structs, which serializes correctly with currency-aware formatting.

The protection is: control the input, not the output. We can't stop connectors from writing i64 fields. We stop them from getting a raw number to put there.

Design Principle

Make the right thing easy (ConnectorMinorUnit serializes correctly out of the box) and the wrong thing obvious (extracting raw i64 requires importing a banned trait, which CI rejects).
