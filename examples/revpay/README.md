# RevPay local UAT reconstruction

Reconstructed on the local `REVPAY_INTEG` checkout from the existing code and
[RevPay Merchant API 3.1.10](https://drive.google.com/file/d/1qRtAKBP2hFT9wY766Q3Fstn2goUrSQT0/view).
The unavailable Linux checkout could not be compared, so this is not a byte-for-byte restoration.

## Payment methods

| Method | UCS payment method / card network | RevPay Payment_ID | Card_Type |
| --- | --- | --- | --- |
| Visa / Mastercard | `card`, `VISA` / `MASTERCARD` | 2 | 02 / 03 |
| FPX (B2C) | `online_banking_fpx`, e.g. issuer `Maybank` | 3 | omitted |
| MyDebit Secure | `card`, `MYDEBIT` | 31 | 05 |
| DuitNow QR | `duit_now` | 37 | omitted |
| GrabPay | `grabpay_redirect` | 17 | omitted |
| BOOST | `boost_redirect` | 11 | omitted |
| TNG | `touch_n_go_redirect` | 28 | omitted |
| UnionPay-CNP | `card`, `UNIONPAY` | 38 | 06 |
| Alipay+ | `ali_pay_plus_redirect` | 36 | omitted |
| WeChatPay | `we_chat_pay_redirect` | 14 | omitted |

Alipay Online (`ali_pay_redirect`, ID 15) remains distinct from Alipay+.
DuitNow QR uses RevPay's hosted payment page returned in `Bank_Redirect_URL`
with response code `09`; no raw QR payload or QR image is generated by UCS.
Live UAT must confirm merchant provisioning and the hosted QR behavior.

For MyDebit, the caller must set `card.card_network: "MYDEBIT"`. BINs overlap
with other schemes, so MyDebit is never inferred from PAN alone. An explicit
MyDebit selection takes precedence over a co-badged UnionPay BIN. Explicit
`UNIONPAY`, or an inferred `62` BIN without a recognized explicit network,
now selects CNP ID 38 and type 06, replacing the previous Visa/Mastercard ID 2
and MyDebit type 05 fallback.

FPX supports 19 bank variants from Appendix B, including Bank of China
(`BOCM01`). `Maybank` selects Maybank2u (`MB2U0227`). The separate M2E channel
and FPX B2B (`Payment_ID: 9`) are not implemented.

Added protobuf identifiers (existing numbers unchanged):

- `PaymentMethod.boost_redirect = 190`, `BOOST_WALLET = 144`.
- `PaymentMethod.ali_pay_plus_redirect = 191`, `ALI_PAY_PLUS = 145`.
- `CardNetwork.MYDEBIT = 19`.

Regenerate gRPC clients to use these new identifiers. Other connectors keep
Alipay+ in their unsupported-wallet groups; MyDebit does not become a supported
network on other connectors merely because it exists in the shared enum.

## HTTP examples and the earlier deserialization error

`boost-authorize.json`, `fpx-authorize.json`, `alipay-plus-authorize.json`,
and `duitnow-qr-authorize.json` are request-body examples for
`POST /composite/payments/authorize`. Replace the unique merchant transaction
reference and callback URLs before UAT. Configure the usual RevPay connector
headers with your own merchant credentials; no credentials are stored here.
These examples are not executed automatically.

The payment method has two JSON levels:

```json
"payment_method": {
  "payment_method": {
    "online_banking_fpx": {"issuer": "Maybank"}
  }
}
```

`issuer` uses the shared protobuf bank name, such as `Maybank`, `CimbBank`,
`RhbBank`, or `BankOfChina`, with that exact spelling. It is not the RevPay bank
code (`MB2U0227`) or the merchant-facing label `FPX`. The connector maps bank
names to RevPay codes. The example includes `order_details: []` for the HTTP
serializer's repeated-field contract.

The retained Linux log only says the body failed to deserialize. It contains
neither the request body nor the HTTP error response, so the historical cause
cannot be established. A regression test now checks both complete composite
request bodies against the actual generated request type. If the Euler caller
still receives HTTP 400, inspect its error response and compare the request
shape with these examples; do not infer a gateway failure from a local 400.

## Refund references and existing fixes

The local baseline already contains expiry normalization to `YYYYMM`, card-type
inference, a description fallback, redirect responses with null Transaction_ID,
and separate original-payment/refund reference handling. Those paths are kept
and covered by tests.

For refunds, pass the original payment's `merchant_transaction_id` (the exact
value sent to RevPay as `Reference_Number`) in `connector_order_id`, and a new
unique `merchant_refund_id` for the refund. Do not use the gateway Transaction_ID
or the refund ID as the original payment reference. Missing or blank original
references are rejected locally. The refund regression test exercises the shared
request conversion and verifies both identifiers and the signature.

The RevPay webhook implementation also now initializes
`connector_preprocessing_id: None`, fixing an existing compile error against the
merged shared webhook type.

## Validation and remaining UAT work

Run from the repository root:

```sh
cargo test -p connector-integration --lib --locked --offline
cargo check -p grpc-server --locked --offline
```

The connector suite passed locally: 270 tests, including 37 RevPay tests.

For a sandboxed server check, `DOCS_RS=1 cargo check -p grpc-server --locked --offline`
skips the `superposition_core` dependency's C-header export into the Cargo registry;
the normal check may need write access to that header directory.

Tests perform no gateway calls. UAT still needs real callback URLs, merchant
payment-method enablement, and a caller that emits the new payment-method
payloads. This reconstruction changes only hyperswitch-prism; it does not
restore Linux-side Euler code, database records (GPM/MGA/MGPMF), credentials,
or running services. Confirm those separately before an end-to-end test.
