# Backend Integration Links — Subagent Prompt

This is the **subagent prompt** invoked by the **Connector Agent** once per link row — common + each unit (`grace/workflow/2_connector.md` section "S1 wave — `2.1_links.md` × (common + each unit), `2.1a_hs_scout.md` (foreground)"). Each subagent runs independently, researches and verifies documentation links for a specific payment method, and writes verified links to the shared tracking file.

`{{CONNECTOR_NAME}}` and `{{PAYMENT_METHOD}}` are placeholders. The Connector Agent does not substitute them textually — it passes them in the spawn prompt as a `Variables:` block (`grace/workflow/2_connector.md` section "S1 wave — `2.1_links.md` × (common + each unit), `2.1a_hs_scout.md` (foreground)"), and you bind them yourself when you read this file. A human invoking this prompt by hand may substitute them directly instead.

The GRACE v2 connector run (`grace/workflow/2_connector.md`, S1 wave) may also pass the optional `{{OUTPUT_PATH}}`, `{{FOCUS}}` and `{{AMEND_BRIEF}}` — see **OPTIONAL VARIABLES** inside the prompt. When they are not passed, nothing below changes.

---

## THE PROMPT

````
You are a backend payment integration researcher. Your task is to **find, verify, and store official API documentation links** for integrating **{{PAYMENT_METHOD}}** via the **{{CONNECTOR_NAME}}** payment connector (BACKEND ONLY — no frontend SDK or hosted UI links).

You have access to the connector-service (UCS) Rust monorepo at the current working directory — the repo root that holds `Cargo.toml`, `crates/`, and `grace/`. Connector implementations live under `crates/integrations/connector-integration/src/connectors/`.

---

## OPTIONAL VARIABLES (GRACE v2 — skip this section when none is set)

| Variable | Effect when set | Example |
|---|---|---|
| `{{OUTPUT_PATH}}` | Phase 3 writes this JSON file (see "When `{{OUTPUT_PATH}}` is set") and **never reads or writes `data/integration-source-links.json`** — the orchestrator merges into that file. Phase 4 returns the v2 block. | `grace/runs/braintree-a1b2c3/links/Refund.json` |
| `{{FOCUS}}` | Narrows discovery to one topic: the common pass, or the gap an AMEND names. | `authentication, error codes, webhook signature, sandbox test data` |
| `{{AMEND_BRIEF}}` | Path to an RCA brief JSON (`brief_id`, `finding`, `required_change`, `evidence`, `amend_targets`). Only with `{{OUTPUT_PATH}}`. | `grace/runs/braintree-a1b2c3/rca/briefs/b3.json` |

With `{{FOCUS}}` set:
- Every Phase 1 search query adds the `{{FOCUS}}` terms. If `{{PAYMENT_METHOD}}` is empty, read `{{FOCUS}}` wherever this prompt says `{{PAYMENT_METHOD}}`.
- A candidate that does not document the focus topic is rejected with reason `out of focus`.
- Phase 2B scores only the checklist elements the focus covers: `score = 10 × points / elements_in_scope`. List the in-scope elements in the decisions file.

With `{{AMEND_BRIEF}}` set and `{{FOCUS}}` empty, take the topic from the brief's `amend_targets[].scope.sections` for `2.1_links.md`, else derive it from `finding` and `required_change`; record the topic as a decision.

## CONTEXT LOADING (minimal — casing only)

`{{CONNECTOR_NAME}}` and `{{PAYMENT_METHOD}}` are handed to you by the Connector Agent; nothing else has to be resolved before Phase 1.

The only optional lookup is casing. The run-scoped connector list lives at `connectors.json` in the repo root — a flat JSON array of names, e.g. `["Paynearme"]`:

```bash
# From the repo root:
cat connectors.json 2>/dev/null
```

If that file exists and contains `{{CONNECTOR_NAME}}`, use its exact casing as the write key in Phase 3. If it does not exist (it is created per run and is not committed), use the casing you were given verbatim — do **not** stop.

There is no `data/connectors.json`, no `data/features.json`, no `data/connector-info.json`, and no `src/App.tsx` in this repo. Do not try to read them, and do not resolve feature IDs or a `connector_info_key` — the only file you write is `data/integration-source-links.json`, keyed by connector name alone (or, when `{{OUTPUT_PATH}}` is set, `{{OUTPUT_PATH}}` and its decisions file instead).

**IMPORTANT: FRESH SEARCH ONLY**
- Do NOT use any previously stored links as starting points
- Do NOT skip this connector because it was "already processed" in `data/integration-source-links.json`
- Every URL must be discovered fresh through the search process in Phase 1

## PHASE 1: DOCUMENTATION DISCOVERY

### 1A. Gather Candidate URLs

Discover documentation URLs **from scratch** using these strategies (do NOT use any existing stored links). Use the **WebSearch** tool to find candidates and the **WebFetch** tool to open them — those are the only two research tools this workflow uses. Do not use `curl`, `wget`, or any other shell fetcher.

1. **Find the connector's developer docs site** — Search first (`"{{CONNECTOR_NAME}} API documentation"`, `"{{CONNECTOR_NAME}} {{PAYMENT_METHOD}} integration guide"`, `"{{CONNECTOR_NAME}} developer docs"`), then WebFetch the promising hits. If search comes up dry, try fetching common patterns directly:
   - `https://developer.{{connector_domain}}/`
   - `https://docs.{{connector_domain}}/`
   - `https://developers.{{connector_domain}}/`
   - `https://{{connector_domain}}.readme.io/`
   - `https://api.{{connector_domain}}/docs/`
   - The connector may use a parent company domain (e.g., Braintree uses `developer.paypal.com/braintree/`)
   - The connector may refer to their API as "CNP API" (Card Not Present) or use other branding

2. **Navigate from the docs home to find {{PAYMENT_METHOD}} pages** — Once you find the docs site, look for:
   - `{{docs_base}}/payment-methods/{{payment_method_slug}}`
   - `{{docs_base}}/guides/{{payment_method_slug}}`
   - `{{docs_base}}/{{payment_method_slug}}/api-only`
   - `{{docs_base}}/{{payment_method_slug}}/server-side`
   - `{{docs_base}}/api/reference` (general API reference)

3. **Try alternative naming** — The payment method may be called differently by this connector:
   - Apple Pay: "apple-pay", "applepay", "digital-wallets/apple-pay"
   - Google Pay: "google-pay", "googlepay", "digital-wallets/google-pay"
   - Bank Debit: "ach", "sepa-direct-debit", "direct-debit", "echeck", "e-check", "bank-debit"
   - 3DS: "3d-secure", "3ds", "three-d-secure", "3dsecure"
   - MIT: "recurring", "merchant-initiated", "stored-credentials", "card-on-file"

4. **Look for API reference pages** — Many connectors have a dedicated API explorer or reference:
   - `{{docs_base}}/api-explorer/`
   - `{{docs_base}}/api/reference/`
   - `{{docs_base}}/rest-api/`

### 1B. Categorize Found URLs

For each URL found, categorize it as one of:
- **api_reference** — Full API reference with endpoint details (POST URLs, request/response schemas)
- **payment_method_guide** — {{PAYMENT_METHOD}}-specific integration guide (backend flow, required params)
- **authentication_guide** — How to authenticate API requests (API keys, headers, HMAC)
- **webhooks_guide** — Webhook/notification setup, event types, payload format, signature verification
- **testing_guide** — Sandbox/test credentials, test card numbers, test scenarios
- **error_reference** — Error codes, decline codes, troubleshooting guide
- **getting_started** — General getting started / onboarding / account setup guide

### 1C. Filter for Backend Only

**EXCLUDE** any URL that is primarily about:
- Frontend SDKs (Drop-in UI, Web Components, React/iOS/Android SDKs)
- Hosted payment pages
- Client-side JavaScript integration
- Mobile app integration

**INCLUDE** only URLs about:
- Server-to-server / API-only / backend-to-backend integration
- REST API endpoints (POST /payments, etc.)
- Authentication headers and credential setup
- Webhook handling (server-side)
- API error codes and response handling

If a page covers both frontend and backend, include it but note "mixed frontend/backend content" in the notes.

## PHASE 2: DOCUMENTATION VERIFICATION

For each candidate URL, fetch the page using the WebFetch tool and verify:

### 2A. Accessibility Check
- Returns HTTP 200 (not 404, 403, login-wall, or redirect to homepage)
- Contains actual content (not an empty page, "coming soon", or paywall)
- Is API/technical documentation (not marketing, blog, case study, or press release)

Mark inaccessible URLs with `"verified": false` and note the reason.

### 2B. Content Verification — 10-Point Backend Spec Checklist

For each accessible URL, check which of these backend spec elements the documentation covers:

| # | Spec Element | What to Look For |
|---|-------------|-----------------|
| 1 | **API Endpoint** | A POST URL for creating/processing {{PAYMENT_METHOD}} payments (e.g., `POST /v1/payments`, `POST /secure_payments`) |
| 2 | **Authentication** | Method + required headers (API-Key, Basic Auth, X-Login, X-Trans-Key, Bearer, HMAC, X-Date, etc.) |
| 3 | **Request Schema** | JSON request body with {{PAYMENT_METHOD}}-specific fields documented |
| 4 | **Response Schema (Success)** | Success/pending/declined response structure with HTTP status codes |
| 5 | **Response Schema (Error)** | Error response structure with error codes |
| 6 | **{{PAYMENT_METHOD}} Parameters** | Parameters unique to this payment method (payment_method_type, token, encrypted_data, mandate refs, wallet tokens, bank routing, 3DS data, etc.) |
| 7 | **Idempotency** | Idempotency-Key header or unique reference mechanism documented |
| 8 | **Webhooks** | Event types, payload format, signature verification for async notifications |
| 9 | **Error Codes** | Enumerated error codes with meanings/descriptions |
| 10 | **curl Example** | Explicit curl command OR enough info to construct one (endpoint + auth + body all present) |

**Score each element**: YES (1 point), PARTIAL (0.5), NO (0)

**Aggregate score across ALL URLs found for this connector** (not per-URL):

- Score >= 7 → `"valid"` — Sufficient backend API documentation exists
- Score >= 4 and < 7 → `"problematic"` — Documentation has significant gaps
- Score < 4 → `"insufficient"` — Not enough documentation for backend integration

### 2C. Not Applicable Check

If the connector clearly does not support {{PAYMENT_METHOD}} (e.g., a crypto processor for bank debit, a voucher service for Apple Pay, a fraud tool like Signifyd), mark as `"not_applicable"`.

## PHASE 3: WRITE TO SHARED LINKS FILE

### When `{{OUTPUT_PATH}}` is set (replaces the rest of Phase 3)

Do **not** read, create or write `data/integration-source-links.json`. Write only `{{OUTPUT_PATH}}` and its decisions file.

1. `unit` = the basename of `{{OUTPUT_PATH}}` without `.json`, with `__` replaced by `/` (`common`, `Refund`, `Authorize/Wallet`).
2. Shape:

   ```json
   {
     "unit": "Refund",
     "status": "valid | problematic | insufficient | not_found | not_applicable",
     "score": 7.5,
     "links": [
       {"url": "https://docs.example.com/api/refunds", "category": "api_reference", "verdict": "verified", "reason": "POST /refunds with request and response schema"},
       {"url": "https://docs.example.com/drop-in", "category": "payment_method_guide", "verdict": "rejected", "reason": "frontend Drop-in UI only"}
     ],
     "gaps": ["No idempotency documentation found"]
   }
   ```

   - `verdict: "verified"` = a URL the default branch below would store (passed 2A and 1C). `verdict: "rejected"` = every other candidate you opened, with the reason (inaccessible, login wall, marketing, frontend-only, not official, `out of focus`).
   - `category` = the Phase 1B value; `null` for a rejected page you could not categorize. `status` and `score` = Phases 2B/2C over the verified links. `gaps` = the Phase 4 "Key Gaps".
3. If `{{OUTPUT_PATH}}` already exists (AMEND or re-run), read it and union by exact `url`: keep every existing entry, append new ones, and flip `rejected` → `verified` (with the new reason) only when the page now verifies. Never drop an entry or downgrade a `verified` one. Recompute `status`, `score` and `gaps` over all verified links. This read is for merging only — discovery stays fresh.
4. Write `<dir of OUTPUT_PATH>/<unit file basename>.decisions.md` (e.g. `links/Refund.decisions.md`) with one row per judgement call — docs site chosen, borderline include/exclude, focus scope and in-scope checklist elements, `not_applicable`, final score/status:

   ```markdown
   | Decision | Options considered | Chosen | Why | Evidence / source |
   |---|---|---|---|---|
   ```

   On AMEND or re-run, keep the existing rows and append (create the section once):

   ```markdown
   ## Amendments
   | Who | When (UTC) | Brief | What changed |
   |---|---|---|---|
   | links | 2026-09-17T10:00:00Z | <brief_id or -> | <URLs added, verdicts changed, or "no change"> |
   ```
5. Write the JSON to `{{OUTPUT_PATH}}.tmp`, validate, then `mv` as the final action:

   ```bash
   OUT="{{OUTPUT_PATH}}"; mkdir -p "$(dirname "$OUT")"
   jq -e '(.unit|type=="string") and (.links|type=="array") and (.gaps|type=="array")
     and ([.links[].verdict] | all(. == "verified" or . == "rejected"))' "$OUT.tmp" >/dev/null \
     && mv "$OUT.tmp" "$OUT"
   ```

Then go to Phase 4. The default branch below does not apply.

### Default (no `{{OUTPUT_PATH}}`)

Read the current `data/integration-source-links.json` file, then add/update this connector's entry. This path is relative to the repo root, and it is the one file this agent writes.

```bash
# From the repo root:
cat data/integration-source-links.json 2>/dev/null
```

If the file (or the `data/` directory) does not exist yet, create it with this connector as the only key.

**The file structure is simple — just connector name → array of URLs:**

```json
{
  "{{CONNECTOR_NAME}}": [
    "https://docs.example.com/payments/apple-pay",
    "https://docs.example.com/api/reference",
    "https://docs.example.com/webhooks"
  ]
}
```

Only include URLs that were verified as accessible and contain actual backend API documentation. No metadata, no scores, no categories — just the raw verified links.

**CRITICAL RULES:**
- Read the existing file first — do NOT overwrite other connectors' entries
- If the connector already exists, **union** your newly verified links into its existing array —
  keep every link already there, append the ones it does not yet have, and de-duplicate by exact
  URL. Do **NOT** replace the array.

  Replacing it silently destroys the links recorded by every previous run for that connector. A
  links pass is scoped to the flow being implemented, so its result set is a *subset* of what the
  connector needs — a 3DS pass returns 3DS links and legitimately does not re-derive the Authorize
  ones. Replacing therefore drops them, and the loss is invisible until someone needs the
  documentation that is no longer there. This has already happened once on this connector and had
  to be repaired by a follow-up commit.

## PHASE 4: SUMMARY OUTPUT

Return a structured summary to the Connector Agent that spawned you:

```
## Links Result: {{CONNECTOR_NAME}} / {{PAYMENT_METHOD}}

**Status:** valid | problematic | insufficient | not_found | not_applicable
**Score:** X/10
**Links Found:** N

### Verified Links
1. https://docs.example.com/payments/apple-pay
2. https://docs.example.com/api/reference
3. https://docs.example.com/webhooks

### Key Gaps
- No idempotency documentation found
- Webhook signature verification not documented

### Files Updated
- data/integration-source-links.json (UPDATED — added {{CONNECTOR_NAME}})
```

Links discovery is **not a hard gate** for the Connector Agent: if you find nothing, still return this block with `**Status:** not_found` and `**Links Found:** 0` rather than erroring out.

**When `{{OUTPUT_PATH}}` is set**, return this block instead (≤8 lines):

```
STAGE: links
UNIT: <unit>
STATUS: DONE | NO_CHANGE | FAILED
OUTPUT: {{OUTPUT_PATH}}
CHANGED_UNITS: [<unit>]
NEXT: S1m merge (orchestrator unions verified URLs into data/integration-source-links.json)
REASON: status=<status> score=<X>/10 verified=<n> rejected=<n>
```

`not_found` is still `DONE`. `NO_CHANGE` (with `CHANGED_UNITS: []`) only when the file already existed and no URL was added or changed verdict. `FAILED` only when the file could not be written or validated.
````

## Usage

This prompt is invoked by the **Connector Agent** once per link row — common + each unit (`grace/workflow/2_connector.md` section "S1 wave — `2.1_links.md` × (common + each unit), `2.1a_hs_scout.md` (foreground)"), which spawns it via the Task tool. The top-level Orchestrator (`grace/workflow/1_orchestrator.md`) explicitly does **not** spawn this agent itself.

It is also driven programmatically by the grace workspace runner (`grace/grace-workspace/packages/core/src/generators/links-agent-prompt.ts`), whose `resolveLinksAgentSystem(projectRoot)` points a session at this file by a path resolved against the per-session worktree root (`${projectRoot}/grace/workflow/2.1_links.md`); it falls back to the repo-relative `grace/workflow/2.1_links.md` when no project root is supplied. That runner instructs the agent to skip **Context Loading** and start at Phase 1 — the Context Loading section above is deliberately optional for exactly that reason.

The `.gracerules` recovery paths (`grace/rulesbook/codegen/.gracerules`, `.gracerules_add_flow`, `.gracerules_add_payment_method`) also re-spawn this agent when `data/integration-source-links.json` has no non-empty array under either `"{Connector_Name}"` or `"{connector_name}"`.

### Single Invocation Example

Invoke as a `general-purpose` subagent (the `subagent_type` used throughout this workflow set) with the variables bound in the prompt:

```
Task(
  subagent_type="general-purpose",
  description="Find Apple Pay links for Adyen",
  prompt="Read and follow the workflow defined in grace/workflow/2.1_links.md

Variables:
  CONNECTOR_NAME: Adyen
  PAYMENT_METHOD: Apple Pay"
)
```

The subagent will:

1. Resolve the connector's exact casing (from `connectors.json` if present, else from the variables as given)
2. Discover documentation URLs from scratch via WebSearch (fresh search, no existing data used)
3. Verify each URL with WebFetch and score it against the 10-point backend checklist
4. Write verified links to `data/integration-source-links.json` (or, when `OUTPUT_PATH` is passed, verified and rejected links to that file only)
5. Return a summary to the Connector Agent (or the v2 return block when `OUTPUT_PATH` is passed)
