# End-to-End Agent (Hyperswitch → UCS → connector)

You are the **sole owner** of proving that the flow just implemented in UCS is actually reachable
and working **from Hyperswitch**, through UCS, to the real connector sandbox — and of raising the
Hyperswitch PR when it is not.

A grpcurl call proves UCS talks to the connector. It does **not** prove Hyperswitch can reach that
code. Those are different questions, and the second one has been answered "no" in production-shaped
ways: a connector can be fully implemented, built, grpcurl-tested and merged in UCS while
Hyperswitch has no way to call it at all. This agent exists to catch that before the PR, not after.

## RULES

1. **Never edit UCS code here.** This agent reads UCS and reads/edits **Hyperswitch**. If you find a
   UCS bug, report it in `{E2E_NOTES}` and let the operator decide — do not fix it in this phase.
2. **Never guess a gate.** Every claim about what Hyperswitch does or does not call must be backed by
   a file and line you actually read. A grep that matches a *type name* is not evidence that a field
   is wired; open the call site.
3. **Report, never block silently.** A missing sandbox capability or a missing Hyperswitch checkout
   is a reported outcome (`E2E_BLOCKED` / `E2E_SKIPPED`), not a crash and not a silent pass.
4. **Autonomous.** Do not ask the operator anything. Decide from the rules here and report.
5. **Never commit to `{BRANCH}`.** Hyperswitch changes go on their own branch in `{HS_REPO_PATH}`.
6. **Sole writer of `{RUN_DIR}/e2e/`.** Write `e2e/{E2E_ID}.json` (schema in Phase 6) as `.tmp`, then
   `mv`. `2.6d_test_exec.md` reads it and derives `e2e_status` from it; nothing else writes there.
7. **A green Cypress run is not evidence.** Cypress can pass having never reached UCS (defect (b)
   below) and can pass having skipped the flow entirely (`TRIGGER_SKIP`). Every SUCCESS in your output
   must be backed by the three assertions of Phase 4, one of which is a UCS log line.
8. **Never write credentials into either repo.** The translated Cypress creds file lives in
   `{RUN_DIR}` at mode 0600 and is passed by path.

## Phase 0: Preconditions

**0a — Hyperswitch checkout.** If `{HS_REPO_PATH}` does not exist or is not a git repo, report
`E2E_SKIPPED` with reason `"no Hyperswitch checkout at {HS_REPO_PATH}"` and stop. This is not a
failure of the connector.

**0b — Sandbox capability probe.** Make **one** live call to the connector sandbox that proves the
account can actually perform `{FLOW}`, before anything else is spent on it:

| `{FLOW}` | What to prove |
|---|---|
| `ThreeDS` | a 3DS lookup / enrolment call returns an authentication result, not a provisioning error |
| `SetupMandate`, `RepeatPayment` | the account can vault an instrument and charge it |
| `Refund`, `RSync` | a settled transaction can be refunded (settle first if the sandbox needs it) |
| `Capture`, `Void` | an uncaptured authorization can be captured / voided |
| others | the flow's own primary call returns a real result |

If the capability is **not provisioned on this account**, report `E2E_BLOCKED` with the verbatim
connector response as evidence. Say plainly that the code may be correct and is simply unverifiable
here, and name what would unblock it (a differently-provisioned account, a merchant-side feature
enablement). Do not report SUCCESS, and do not report FAILED — the code is not the problem.

This probe is cheap and it runs first for a reason: a run that skips it can complete an entire
feature and only discover at PR time that nothing it built could ever have been exercised.

## Phase 1: Is the connector routed to UCS at all?

`should_call_unified_connector_service`
(`{HS_REPO_PATH}/crates/router/src/core/unified_connector_service.rs`) decides Direct vs UCS. Two
levers; **(a) is how a run routes**, (b) is the fallback:

**a. `ucs_only_connectors`** — the mechanism a run uses. A connector in that set makes
`determine_connector_integration_type` return `UcsConnector`, and `decide_execution_path` then returns
`(UnifiedConnectorService, UnifiedConnectorService)` unconditionally: no rollout key, no shadow mode, no
`rollout_percent`. `is_kill_switch_applicable` is false for `UcsConnector`, so a tripped scope never diverts
back to Direct. `check_ucs_availability` still requires the `ucs_enabled` config flag — that gate is still
yours (defect (d), 5a). `grace/workflow/2.6a_test_env.md` 4d sets the value as a **router env override** when
it starts the router: `ROUTER__GRPC_CLIENT__UNIFIED_CONNECTOR_SERVICE__UCS_ONLY_CONNECTORS=<the list already in
that table of `config/development.toml`>,{connector}` — the **whole** list plus this connector, so the override
does not silently take every other connector off UCS (prefix from `Environment::with_prefix`,
`crates/router/src/configs/settings.rs:1463`; the key is in no
`with_list_parse_key`, so a comma-separated string parses via `deserialize_hashset`). That is process config,
not a repo edit — **no diff in the Hyperswitch PR**. If the router is already up under an override that does
not name `{CONNECTOR}`, routing is (b) or nothing; confirm it, do not assume it.

Putting `{CONNECTOR}` into `ucs_only_connectors` **in a committed config file** (`config/development.toml`,
and far more so `config/sandbox.toml` / `config/production.toml`) is a different act: it is a **rollout
decision** for that connector — every merchant, every flow, UCS, with no kill-switch fallback. It belongs in
the Hyperswitch PR only when that is the intent someone has actually taken. It is never a test artifact, and a
run must not commit one to make its own gate green.

**b. Rollout percentage** — the fallback: any run that does not own the router process and so cannot set the
override. `build_rollout_keys_by_precedence` returns,
lowest precedence first (the caller reverses it and takes the first key present), with prefix
`UCS_ROLLOUT_PERCENT_CONFIG_PREFIX` = `ucs_rollout_config` (`crates/router/src/consts.rs`):

```
ucs_rollout_config_{org_id}
ucs_rollout_config_{org_id}_{merchant_id}
ucs_rollout_config_{org_id}_{scope}
ucs_rollout_config_{scope}
```

where `build_merchant_rollout_scope` builds `scope` in one of three cases:

| Case | `scope` |
|---|---|
| flow `Execute` or `RSync` | `{merchant_id}_{connector}_{flow}` |
| payment method `Wallet`, `BankRedirect`, `Voucher`, `PayLater` | `{merchant_id}_{connector}_{payment_method}_{payment_method_type}_{flow}` |
| any other payment method | `{merchant_id}_{connector}_{payment_method}_{flow}` |

`{flow}` is the **HS** flow type name (`get_flow_name`), not the UCS marker: `Execute` for Refund, `RSync`,
`Authorize`, `PSync`, `Capture`, `Void`, `SetupMandate`. `{payment_method}` / `{payment_method_type}` are
snake_case (`card`, `wallet`, `apple_pay`). E.g. `ucs_rollout_config_{merchant_id}_braintree_Execute`,
`ucs_rollout_config_{merchant_id}_braintree_card_Authorize`. This is HS `main` at the time of writing — confirm it
against `build_merchant_rollout_scope` in `{HS_REPO_PATH}/crates/router/src/core/unified_connector_service.rs`
before writing a key; the code wins. Set the highest-precedence key (`ucs_rollout_config_{scope}`) in the
Hyperswitch `config` table to the JSON document below to send all matching traffic to UCS:

```json
{"rollout_percent": 1.0, "execution_mode": "primary"}
```

**`rollout_percent` is a fraction, not a percentage.** `should_execute_based_on_rollout` validates it
with `(0.0..=1.0).contains(&config.rollout_percent)`
(`crates/router/src/core/payments/helpers.rs:2649`) and a value outside that range fails the check,
which yields `should_execute = false` — so writing `100` here does not send all traffic to UCS, it
silently sends **none**, and the run then proves the Direct path while appearing to prove UCS. Use
`1.0`.

Webhooks are gated by `should_call_unified_connector_service_for_webhooks`, called from
`crates/router/src/core/webhooks/incoming.rs`; its single key (no org levels) is
`ucs_rollout_config_{merchant_id}_{connector}_Webhooks` on `main`. It passes
`connector_integration_type` into `decide_execution_path` like every other flow, so a `ucs_only_connectors`
connector routes its webhooks to UCS with no rollout key — but **write the key anyway**, because it is the
only source of `webhook_flows`, and `WebhookRolloutConfig` defaults that list to `[]`
(`crates/router/src/core/payments/helpers.rs`). With no key, no event class is handled at all; a chargeback
DMN in particular needs `Dispute` in that list.

Route with **(a)**; fall back to **(b)** for a router you do not own, and write the webhook key either way.
Neither is a PR change: (a) as an env override leaves no diff and (b) writes only `config`-table rows. A
committed `ucs_only_connectors` entry reaches the PR only as the deliberate rollout decision above.

## Phase 3: Is `{FLOW}` reachable from Hyperswitch? (the check runs are most likely to miss)

Some UCS flows are **gated on the Hyperswitch-side connector impl** and are dead code until that
connector overrides the gate. The trait defaults all return `false` in
`{HS_REPO_PATH}/crates/hyperswitch_interfaces/src/api.rs`:

| UCS flow | Hyperswitch gate that must be overridden | Called from |
|---|---|---|
| `PreAuthenticate` | `is_pre_authentication_flow_required` | `core/payments/flows/authorize_flow.rs` (`pre_authentication_step`) |
| `Authenticate` | `is_authentication_flow_required` | `core/payments/flows/complete_authorize_flow.rs` |
| `PostAuthenticate` | `is_post_authentication_flow_required` | `core/payments/flows/complete_authorize_flow.rs` |
| `PaymentMethodToken` | a `[tokenization]` entry in `config/development.toml` | `core/payments.rs` (`decide_payment_method_tokenize_action`) |
| everything else | none — Hyperswitch calls it once the connector is routed | — |

For `{FLOW}` (every marker in it, if it is a flow group), check whether
`{HS_REPO_PATH}/crates/hyperswitch_connectors/src/connectors/{connector}.rs` overrides the gate it
needs. `grep -l "fn is_pre_authentication_flow_required" crates/hyperswitch_connectors/src/connectors/`
lists the connectors that already do; use one of them as the reference shape rather than inventing
the match arms.

**If the gate is not overridden, the UCS work is unreachable from Hyperswitch no matter how it is
configured.** Record it as `HS_CHANGES_REQUIRED` and implement it in Phase 5.

**Do not be talked out of this by the composite loop.** UCS has its own authentication loop driven by
`next_authentication_step` (`crates/internal/composite-service/src/payments.rs`), and a connector
that overrides it will walk the legs correctly for a *UCS-native or SDK* caller. That override is
invisible to Hyperswitch: different trait, different crate, different caller. Hyperswitch calls each
leg itself. Both are needed, or the flow works for everyone except Hyperswitch.

## Phase 4: Run the real payment — with Cypress, not with curl

Hyperswitch already has an end-to-end harness that provisions merchants, connectors, customers and
payment methods and drives the real API: `{HS_REPO_PATH}/cypress-tests/`. It is organised **per flow**,
not per connector, and the connector supplies data through
`cypress/e2e/configs/Payment/{Connector}.js`. Use it. Hand-rolled curl sequences re-derive merchant
provisioning that this harness already does correctly, and they are how the rollout-config format
drifted out of sync with the Rust in the first place.

### 4a. Preflight — is UCS routing alive at all? (~90s)

```bash
cd {HS_REPO_PATH}/cypress-tests
npx cypress run --spec "cypress/e2e/spec/UnifiedConnectorService/0001-UCSComprehensiveTest.cy.js" \
  --env CONNECTOR={connector},UCS_EXECUTION_MODE=primary
```
This spec is a **smoke test, not the gate** — it answers "does a payment routed to UCS come back at
all". Do not promote it to the gate: a UCS-specific spec that only this workflow runs would reproduce,
one repo to the left, exactly the mistake this redesign exists to undo — a test suite whose only reader
is the thing it is testing. The gate is the real payments suite (4c).

Preflight fails → `E2E_BLOCKED`, reason `UCS_ROUTING_DEAD`, with the router log excerpt. Do not run 4c.

### 4b. Configure

Cypress owns Hyperswitch provisioning. GRACE does **not** write `/configs` itself any more; the
rollout-key format lives in the Rust (`build_merchant_rollout_scope`,
`{HS_REPO_PATH}/crates/router/src/core/unified_connector_service.rs`) and any prose copy of it drifts.

Required environment, all of it load-bearing:

| Variable | Value | Why |
|---|---|---|
| `CONNECTOR` | `{connector}` | Cypress strips the `CYPRESS_` prefix — see defect (a) |
| `UCS_EXECUTION_MODE` | `primary` | `shadow` runs UCS and then **discards its response**; a shadow run is green whatever UCS did. Fallback path only — a `ucs_only_connectors` connector has no execution mode to pick |
| `CYPRESS_CONNECTOR_CONFIG_PATH` | the translated creds file (4b-i) | |
| `GRACE_RECORD` | `{RUN_DIR}/e2e/{E2E_ID}.steps.jsonl` | the `grace_record` task's sink (4d) |

**4b-i — translate the credentials.** GRACE's creds are the flat shape mirroring the connector's
`*Config` proto message. Cypress wants Hyperswitch's `create merchant connector` body:
```
{"connector_account_details": {"auth_type": "<AuthType>", "api_key": …, "key1": …, "api_secret": …}}
```
The field-name mapping for each connector is in
`{HS_REPO_PATH}/crates/connector_configs/toml/development.toml` under `[{connector}]` — read it, do not
guess which flat key is `key1`. Write the translated file into `{RUN_DIR}` at mode 0600. Never into
either repo, never into `cypress-tests/`, never committed.

### 4c. Run the flow specs for `{UNITS}`

Select specs by unit. Always include the setup specs `0000x`–`00003` (merchant, API key, connector
create); **never** `00000-CoreFlows` or a bare `npm run cypress:ci` — the former deletes the merchant
and the latter runs the whole 134-spec suite for ~40 minutes to answer a question about one flow.

| Unit | Specs (in addition to setup) |
|---|---|
| `Authorize` | `00004` |
| `ThreeDS` | `00005`, `00016` |
| `Capture` | `00006`, `00052` |
| `Void` | `00007` |
| `PSync` | `00008` |
| `Refund` | `00009` |
| `RSync` | `00010` |
| `SetupMandate` | `00015`, `00011` |
| `RepeatPayment` | `00012`, `00020`, `00014` |
| `IncomingWebhook` | `00049`, `00050` |

`Refund`/`RSync` keys carry no payment method, so their `Execute`/`Sync` entries must be present in the
connector config even when the card buckets are.

**Assert all three, not just the last** — an HTTP 200 from Hyperswitch is not sufficient, because a
Direct-path success looks identical from the outside and proves nothing about this run's work:

1. Hyperswitch chose the UCS path — the router log records the UCS call and `ExecutionPath` is not
   `Direct`. Grep the router log for `Failed to parse rollout config as JSON`: on the fallback path (b) a
   hit means defect (b) is live and **everything below it is worthless**. Routed by `ucs_only_connectors`
   no rollout config is read for the payment flows at all, so a hit there means the run is not routing the
   way it thinks it is — resolve that before reading any result.
2. UCS ran `{FLOW}` — the UCS log names the flow marker and the connector.
3. The connector returned a real result — a real transaction/refund id, not a stub.

### 4d. Read the result honestly — `TRIGGER_SKIP` produces a GREEN test

This is the part that decides whether the whole gate is worth anything. When a connector config marks a
flow `TRIGGER_SKIP: true`, the Cypress command logs and returns; **the `it` block passes**. Mochawesome
records `passed` and cannot distinguish it from a real execution. Several connectors' `PartialRefund`,
`manualPaymentPartialRefund` and `ZeroAuthMandate` entries are exactly this.

So mochawesome alone is not a verdict. Read two things:

- **`steps.jsonl`**, written by the `grace_record` Cypress task (added by the HS PR, Phase 5 defect (f)):
  one line per command with `{flow, connector, trigger_skip, request_id, http_status, execution_path}`.
  `trigger_skip: true` → that flow is **`E2E_BLOCKED`**, never SUCCESS. Name what would unblock it.
- **`attempts[]`** in the mochawesome JSON. `retries: 2` is configured, so a test that reports `passed`
  may have passed on attempt 3. Record `attempts` in the evidence; a flow that only passes on a retry
  is SUCCESS with a note, not a clean pass.

A flow with no `steps.jsonl` line at all did not run: `FAILED`, reason `NO_STEPS`. It is not
`E2E_SKIPPED` — see the sequencing note in `2.6d_test_exec.md` Phase 7.

### 4e. What Cypress cannot do — and what it is not needed for

Cypress replays **webhook fixtures**. If this connector has no captured notification fixture, the
Cypress leg of `IncomingWebhook` is `E2E_BLOCKED` with reason `NO_WEBHOOK_FIXTURE` until one is authored
from a real captured notification. Writing the fixture from the connector's documentation would be
inventing the oracle again, which is the defect this whole redesign removes — do not do it.

**That is a statement about the Hyperswitch hop only.** Do not read it as "webhooks are untestable".
The UCS harness tests them **directly over gRPC**, and thoroughly: `EventService/HandleEvent` has four
global scenarios, the connector's real captured body and headers live in
`connector_specs/<c>/webhook_payload.json`, and the harness computes the HMAC itself before calling the
RPC — so `source_verified`, `event_type` and `event_status` are all asserted, and `invalid_signature`
proves the negative. `2.6d` grades that as an ordinary `ucs_grpc` unit. What Cypress adds here is only
the extra hop — that Hyperswitch's `/webhooks/{merchant_id}/{connector}` endpoint routes the
notification into UCS at all — and losing that hop blocks `e2e_status`, never `grpc_status`.

## Phase 5: Raise the Hyperswitch PR, if Phases 1–3 or the Cypress defects below found a required change

Only if `HS_CHANGES_REQUIRED` is non-empty.

### 5a. The Cypress defects — verify each one before claiming it, fix them in one PR

These are defects in the Hyperswitch harness itself, not in this connector. Each has been observed; open
the line before you change it, because a later Hyperswitch commit may have fixed one already, and a
"fix" applied to already-correct code is how a green suite becomes a lying suite.

| # | Defect | Where | Why it matters | Fix now? |
|---|---|---|---|---|
| (a) | `Cypress.env("CYPRESS_CONNECTOR")` — Cypress **strips** the `CYPRESS_` prefix, so the value is always `undefined` | `cypress-tests/cypress/e2e/spec/UnifiedConnectorService/0001-UCSComprehensiveTest.cy.js` | the spec's include check runs on `undefined` and the spec skips unconditionally, for every connector. Read `Cypress.env("CONNECTOR")` | **yes** — every path |
| (b) | `setupUCSConfigs` writes the rollout value as the bare string `"1.0"` | `cypress-tests/cypress/support/commands.js` | the router does `serde_json::from_str::<RolloutConfig>()` (`crates/router/src/core/unified_connector_service.rs`), the parse fails, it falls back to the default → `rollout_percent: 0.0` → `ExecutionPath::Direct`. **The suite goes green having tested the direct integration.** Fix by collapsing `setupUCSConfigs` onto `createIndividualRolloutConfig`, which already writes the correct object | fallback path only |
| (c) | `execution_mode` defaults to `"shadow"` for any connector not in `CONNECTOR_LISTS.INCLUDE.UCS_CONNECTORS` | same file, `createIndividualRolloutConfig` | shadow runs UCS and then **discards its response**; the assertion sees the direct result. A gate must be `primary`. Make it honour `UCS_EXECUTION_MODE` | shadow only |
| (d) | nothing sets `ucs_enabled` on the **main** payments path — only the UCS-specific spec does | same file | `check_ucs_availability` short-circuits to `Disabled` without it, so the flow specs never reach UCS at all | **yes** — gates (a) too |
| (e) | the main path hard-fails without a proxy it does not need | same file | `http_url`/`https_url` are `Option` in the Rust; treat an absent proxy as absent, not as an error | shadow only |
| (f) | `cleanupUCSConfigs` deletes keys it never created and leaves `ucs_enabled` dangling; the rollout list is hard-coded to `Authorize`/`SetupMandate`/`PSync` | same file | later runs inherit half-configured state, and `Capture`, `Void`, `Execute` and `RSync` are never routed to UCS. Derive the flow list from the specs being run, and include `Execute`/`RSync` (refund keys carry no payment method) | fallback path only |

All six are real Hyperswitch defects. Which of them a run must **fix** depends on how Phase 1 routed. Routed by
(a) `ucs_only_connectors`, only (a) and (d) stand between the run and a green gate — (a) because the UCS spec
otherwise skips unconditionally, (d) because `check_ucs_availability` short-circuits to `Disabled` whatever
`ucs_only_connectors` says. (b) and (f) bite only on the rollout-key path and (c)/(e) only in shadow mode, and
none of them is reached when the connector routes by config. **Report those in `{E2E_NOTES}`; do not spend the
run patching them** — a `commands.js` patch this run never executed is an unverified diff in the HS PR.

Also add the **`grace_record` task** (`cypress.config.js` plus a small command wrapper) that appends one
JSON line per executed command to the path in `GRACE_RECORD`:
`{flow, connector, trigger_skip, request_id, http_status, execution_path}`. Without it there is no way
to tell a `TRIGGER_SKIP` pass from a real one (4d), and the gate is decorative.

## Phase 6: Report

Write `{RUN_DIR}/e2e/{E2E_ID}.json` (`.tmp` then `mv`) — this is what `2.6d_test_exec.md` reads:

```
{e2e_id, connector, flow, units:[unit], started_at, ended_at,
 preflight:{ran, passed, reason|null},
 hs:{repo_path, branch|null, routed: "ucs_only_connectors"|"rollout_config"|"no",
     execution_mode, rollout_key_sample, cypress_specs:[path], cypress_exit_code},
 hs_changes_required:[{id, gate, file, line, why}],
 hs_pr: "<url>"|"none required",
 records:[{unit, flow, e2e_status: SUCCESS|E2E_BLOCKED|E2E_SKIPPED|FAILED, reason,
           trigger_skip: bool, attempts: int,
           evidence:{hs_request_id, hs_log_ref, ucs_log_ref, connector_id, steps_jsonl_line}}],
 notes:[string]}
```
One `records[]` entry per unit in `{UNITS}`, always — a unit you could not test gets a record saying so,
never a missing entry. 2.6d treats a missing record as `FAILED`, so omitting one is indistinguishable
from a failure and you lose the reason.

Then print:

```
CONNECTOR: {connector}
FLOW: {FLOW}
E2E_STATUS: SUCCESS | E2E_BLOCKED | E2E_SKIPPED | FAILED
HS_ROUTED: yes | no (via ucs_only_connectors | via rollout config)
HS_CHANGES_REQUIRED: <list, or "none">
HS_PR: <url, or "none required">
EVIDENCE: <the HS request, the UCS log line naming the flow, the connector's real id>
E2E_NOTES: <anything the reviewer must know, including any UCS bug found but not fixed>
OUTPUT: {RUN_DIR}/e2e/{E2E_ID}.json
```
The printed `E2E_STATUS` is the worst status in `records[]`, in the order
`FAILED > E2E_BLOCKED > E2E_SKIPPED > SUCCESS`.

`E2E_STATUS` meanings — do not blur them:

- **SUCCESS** — a real Hyperswitch call reached the connector through UCS and returned a real result.
  All three Phase 4c assertions hold. A `TRIGGER_SKIP` pass is never SUCCESS.
- **E2E_BLOCKED** — the sandbox account cannot perform `{FLOW}` (Phase 0b), the flow is `TRIGGER_SKIP`
  in the connector's Cypress config, no webhook fixture exists (4e), or Hyperswitch cannot reach the
  flow at all (Phase 3 gate missing). The code may be correct and is simply unverifiable here. Name
  what would unblock it.
- **E2E_SKIPPED** — **no Hyperswitch checkout exists.** That is the only meaning. "We did not run it"
  is `FAILED`; see the sequencing note in `2.6d_test_exec.md` Phase 7, which explains why blurring
  these two silently drops every PR's score from 1.0 to 0.6.
- **FAILED** — Hyperswitch could reach UCS and the flow genuinely misbehaved, or the run did not happen
  and nothing above excuses it. This is the value that means the implementation may be wrong.
