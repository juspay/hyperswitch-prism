# End-to-End Agent (Hyperswitch → UCS → connector)

You are the **sole owner** of proving that the flow just implemented in UCS is actually reachable
and working **from Hyperswitch**, through UCS, to the real connector sandbox — and of raising the
Hyperswitch PR when it is not.

A grpcurl call proves UCS talks to the connector. It does **not** prove Hyperswitch can reach that
code. Those are different questions, and the second one has been answered "no" in production-shaped
ways: a connector can be fully implemented, built, grpcurl-tested and merged in UCS while
Hyperswitch has no way to call it at all. This agent exists to catch that before the PR, not after.

---

| Parameter | Description | Example |

## RULES

1. **Never edit UCS code here.** This agent reads UCS and reads/edits **Hyperswitch**. If you find a
   UCS bug, report it in `{E2E_NOTES}` and let the operator decide — do not fix it in this phase.
2. **Never guess a gate.** Every claim about what Hyperswitch does or does not call must be backed by
   a file and line you actually read. A grep that matches a *type name* is not evidence that a field
   is wired; open the call site.
3. **Report, never block silently.** A missing sandbox capability or a missing Hyperswitch checkout
   is a reported outcome (`E2E_BLOCKED` / `E2E_SKIPPED`), not a crash and not a silent pass.
4. **Autonomous.** Do not ask the operator anything. Decide from the rules here and report.
5. **Never commit to `{BRANCH}`.** Hyperswitch changes go on their own branch in `{HS_REPO_PATH}`.
6. **Sole writer of `{RUN_DIR}/e2e/`.** Write `e2e/{E2E_ID}.json` (schema in Phase 6) as `.tmp`, then
   `mv`. `2.6d_test_exec.md` reads it and derives `e2e_status` from it; nothing else writes there.
7. **An HTTP 200 is not evidence.** A payment can succeed having never reached UCS — the Direct
   path returns the same shape — so a 2xx says nothing about this run's work. Every SUCCESS in
   your output must be backed by the three assertions of Phase 4d, one of which is a UCS log line.
8. **Never write credentials into either repo.** The translated Hyperswitch creds file lives in
   `{RUN_DIR}` at mode 0600 and is passed by path.

## Phase 0: Preconditions

**0a — Hyperswitch checkout.** If `{HS_REPO_PATH}` does not exist or is not a git repo, report
`E2E_SKIPPED` with reason `"no Hyperswitch checkout at {HS_REPO_PATH}"` and stop. This is not a
failure of the connector.

**0b — Sandbox capability probe.** Make **one** live call to the connector sandbox that proves the
account can actually perform `{FLOW}`, before anything else is spent on it:

| `{FLOW}` | What to prove |
|---|---|
| `ThreeDS` | a 3DS lookup / enrolment call returns an authentication result, not a provisioning error |
| `SetupMandate`, `RepeatPayment` | the account can vault an instrument and charge it |
| `Refund`, `RSync` | a settled transaction can be refunded (settle first if the sandbox needs it) |
| `Capture`, `Void` | an uncaptured authorization can be captured / voided |
| others | the flow's own primary call returns a real result |

If the capability is **not provisioned on this account**, report `E2E_BLOCKED` with the verbatim
connector response as evidence. Say plainly that the code may be correct and is simply unverifiable
here, and name what would unblock it (a differently-provisioned account, a merchant-side feature
enablement). Do not report SUCCESS, and do not report FAILED — the code is not the problem.

This probe is cheap and it runs first for a reason: a run that skips it can complete an entire
feature and only discover at PR time that nothing it built could ever have been exercised.

## Phase 1: Is the connector routed to UCS at all?

`should_call_unified_connector_service`
(`{HS_REPO_PATH}/crates/router/src/core/unified_connector_service.rs`) decides Direct vs UCS. Two
levers, in this order:

**a. `ucs_only_connectors`** — `config/development.toml`. If `{CONNECTOR}` is absent from that
comma-separated list, Hyperswitch will not route to UCS for it at all. Adding it is a **code-review
change** and belongs in the Hyperswitch PR (Phase 5).

**b. Rollout percentage** — for a local run with no PR. `build_rollout_keys_by_precedence` returns,
lowest precedence first (the caller reverses it and takes the first key present), with prefix
`UCS_ROLLOUT_PERCENT_CONFIG_PREFIX` = `ucs_rollout_config` (`crates/router/src/consts.rs`):

```
ucs_rollout_config_{org_id}
ucs_rollout_config_{org_id}_{merchant_id}
ucs_rollout_config_{org_id}_{scope}
ucs_rollout_config_{scope}
```

where `build_merchant_rollout_scope` builds `scope` in one of three cases:

| Case | `scope` |
|---|---|
| flow `Execute` or `RSync` | `{merchant_id}_{connector}_{flow}` |
| payment method `Wallet`, `BankRedirect`, `Voucher`, `PayLater` | `{merchant_id}_{connector}_{payment_method}_{payment_method_type}_{flow}` |
| any other payment method | `{merchant_id}_{connector}_{payment_method}_{flow}` |

`{flow}` is the **HS** flow type name (`get_flow_name`), not the UCS marker: `Execute` for Refund, `RSync`,
`Authorize`, `PSync`, `Capture`, `Void`, `SetupMandate`. `{payment_method}` / `{payment_method_type}` are
snake_case (`card`, `wallet`, `apple_pay`). E.g. `ucs_rollout_config_{merchant_id}_braintree_Execute`,
`ucs_rollout_config_{merchant_id}_braintree_card_Authorize`. This is HS `main` at the time of writing — confirm it
against `build_merchant_rollout_scope` in `{HS_REPO_PATH}/crates/router/src/core/unified_connector_service.rs`
before writing a key; the code wins. Set the highest-precedence key (`ucs_rollout_config_{scope}`) in the
Hyperswitch `config` table to the JSON document below to send all matching traffic to UCS:

```json
{"rollout_percent": 1.0, "execution_mode": "primary"}
```

**`rollout_percent` is a fraction, not a percentage.** `should_execute_based_on_rollout` validates it
with `(0.0..=1.0).contains(&config.rollout_percent)`
(`crates/router/src/core/payments/helpers.rs:2649`) and a value outside that range fails the check,
which yields `should_execute = false` — so writing `100` here does not send all traffic to UCS, it
silently sends **none**, and the run then proves the Direct path while appearing to prove UCS. Use
`1.0`.

Webhooks are gated separately by `should_call_unified_connector_service_for_webhooks`, called from
`crates/router/src/core/webhooks/incoming.rs`; its single key (no org levels) is
`ucs_rollout_config_{merchant_id}_{connector}_Webhooks` on `main`.

Use **(b)** to prove the flow now; record **(a)** as required for the PR.

## Phase 2: Does the connector config map cleanly?

Read `{HS_REPO_PATH}/crates/router/src/core/unified_connector_service/connector_config.rs`:

- Is there a `Connector::{Connector}` arm in the auth-mapping match?
- Does its `{Connector}Metadata` struct (if any) match the UCS `{Connector}Config` message in
  `crates/types-traits/grpc-api-types/proto/payment.proto` **field for field**?
- Does the arm accept the `ConnectorAuthType` variant the credentials actually use?

A mismatch here is a Hyperswitch change for the PR. A field present in the proto but absent from the
metadata struct means that config value can never reach the connector.

## Phase 3: Is `{FLOW}` reachable from Hyperswitch? (the check runs are most likely to miss)

Some UCS flows are **gated on the Hyperswitch-side connector impl** and are dead code until that
connector overrides the gate. The trait defaults all return `false` in
`{HS_REPO_PATH}/crates/hyperswitch_interfaces/src/api.rs`:

| UCS flow | Hyperswitch gate that must be overridden | Called from |
|---|---|---|
| `PreAuthenticate` | `is_pre_authentication_flow_required` | `core/payments/flows/authorize_flow.rs` (`pre_authentication_step`) |
| `Authenticate` | `is_authentication_flow_required` | `core/payments/flows/complete_authorize_flow.rs` |
| `PostAuthenticate` | `is_post_authentication_flow_required` | `core/payments/flows/complete_authorize_flow.rs` |
| `PaymentMethodToken` | a `[tokenization]` entry in `config/development.toml` | `core/payments.rs` (`decide_payment_method_tokenize_action`) |
| everything else | none — Hyperswitch calls it once the connector is routed | — |

For `{FLOW}` (every marker in it, if it is a flow group), check whether
`{HS_REPO_PATH}/crates/hyperswitch_connectors/src/connectors/{connector}.rs` overrides the gate it
needs. `grep -l "fn is_pre_authentication_flow_required" crates/hyperswitch_connectors/src/connectors/`
lists the connectors that already do; use one of them as the reference shape rather than inventing
the match arms.

**If the gate is not overridden, the UCS work is unreachable from Hyperswitch no matter how it is
configured.** Record it as `HS_CHANGES_REQUIRED` and implement it in Phase 5.

**Do not be talked out of this by the composite loop.** UCS has its own authentication loop driven by
`next_authentication_step` (`crates/internal/composite-service/src/payments.rs`), and a connector
that overrides it will walk the legs correctly for a *UCS-native or SDK* caller. That override is
invisible to Hyperswitch: different trait, different crate, different caller. Hyperswitch calls each
leg itself. Both are needed, or the flow works for everyone except Hyperswitch.

## Phase 4: Run the real payment — with curl, directly

GRACE drives Hyperswitch's own REST API with `curl` and completes any browser leg with a
headless shim. It does **not** use `cypress-tests/`.

Why the change. The Cypress suite was the harness of record and it manufactures green runs
that prove nothing — the defects are catalogued in Phase 5a and three of them are fatal to a
gate: the UCS spec reads `Cypress.env("CYPRESS_CONNECTOR")`, which is always `undefined`, so
it skips for every connector; `setupUCSConfigs` writes the rollout value as the bare string
`"1.0"`, the router's `serde_json::from_str::<RolloutConfig>()` fails, it falls back to
`rollout_percent: 0.0`, and **the suite goes green having tested the direct integration**;
and `execution_mode` defaults to `shadow`, which runs UCS and then discards its response. On
top of that a connector config marking a flow `TRIGGER_SKIP: true` makes the `it` block
**pass**, and `retries: 2` means a reported pass may be attempt 3.

curl has none of those failure modes: nothing is skipped silently, nothing is retried behind
your back, and every request and response is in the transcript. What it costs is the browser,
which 4c buys back for the one leg that needs it.

### 4a. Provision, with curl

GRACE owns provisioning. Against the HS admin API, in order — record every id in
`{RUN_DIR}/e2e/{E2E_ID}.provision.json`:

| # | Call | Yields |
|---|---|---|
| 1 | `POST /accounts` (admin key) | `merchant_id` |
| 2 | `POST /api_keys/{merchant_id}` | `api_key` |
| 3 | `POST /account/{merchant_id}/connectors` | `merchant_connector_id` |
| 4 | `POST /customers` | `customer_id` |

Step 3 needs GRACE's flat creds translated into Hyperswitch's
`{"connector_account_details": {"auth_type": …, "api_key": …, "key1": …}}` shape. The
field-name mapping per connector is in
`{HS_REPO_PATH}/crates/connector_configs/toml/development.toml` under `[{connector}]` — read
it; do not guess which flat key is `key1`. Write the translated file into `{RUN_DIR}` at mode
0600 and pass it by path (RULE 8).

Then route the connector to UCS. Set the rollout key in the HS `config` table:

```json
{"rollout_percent": 1.0, "execution_mode": "primary"}
```

Three things this must get right, each of which the Cypress path got wrong:

- **A JSON object, not a string.** A bare `"1.0"` fails `serde_json::from_str::<RolloutConfig>()`
  and silently yields `ExecutionPath::Direct`.
- **`1.0`, not `100`.** `should_execute_based_on_rollout` validates with
  `(0.0..=1.0).contains(&config.rollout_percent)`
  (`crates/router/src/core/payments/helpers.rs`); `100` fails the check and sends **no**
  traffic to UCS.
- **`primary`, not `shadow`.** Shadow runs UCS and discards its response, so the assertion
  reads the direct result.

Also set `ucs_enabled` — without it `check_ucs_availability` short-circuits to `Disabled` and
the payments path never reaches UCS at all.

Build the key by reading `build_merchant_rollout_scope` in
`{HS_REPO_PATH}/crates/router/src/core/unified_connector_service.rs` **at run time**. Phase 1
records the shape, but the code wins: any prose copy of that format drifts, and that drift is
how the rollout config broke in the first place. Webhooks are gated separately, by
`should_call_unified_connector_service_for_webhooks`.

Read the key back after writing it and record the value. A write you did not read back is not
configuration, it is a hope.

### 4b. Drive the flow

One explicit curl sequence per unit, against `{HS_REPO_PATH}`'s running router:

| Unit | Sequence |
|---|---|
| `Authorize` | `POST /payments` |
| `ThreeDS` | `POST /payments` → 4c → `GET /payments/{id}` |
| `Capture` | `POST /payments` (`capture_method: manual`) → `POST /payments/{id}/capture` |
| `Void` | `POST /payments` (manual) → `POST /payments/{id}/cancel` |
| `PSync` | `POST /payments` → `GET /payments/{id}?force_sync=true` |
| `Refund` | settle → `POST /refunds` — full, partial, and two sequential partials |
| `RSync` | `POST /refunds` → `GET /refunds/{id}?force_sync=true` |
| `SetupMandate` | `POST /payments`, `setup_future_usage: off_session`, amount 0 |
| `RepeatPayment` | `SetupMandate` → `POST /payments` with `mandate_id`; and the stored-NTID arm |
| `IncomingWebhook` | `POST /webhooks/{merchant_id}/{connector}` with the captured body and a signature computed over it |

Append one line per call to `{RUN_DIR}/e2e/{E2E_ID}.steps.jsonl`:
`{flow, connector, request_id, http_status, execution_path, unit}`. This replaces the
`grace_record` Cypress task; because you write it yourself, a step that did not run simply has
no line, and there is no `TRIGGER_SKIP` state that can look like a pass.

### 4c. The redirect leg

Only for a response carrying `next_action.redirect_to_url` — a 3DS challenge or an APM
hand-off. Drive it headless: open the URL, complete the challenge, follow redirects to
`return_url`, then re-read the payment with `GET /payments/{id}`.

Keep the per-connector page details as **data**, in
`grace/testkit/acs/{connector}.json` — the challenge field selector, the submit control, the
success marker, the test OTP where the sandbox documents one. A connector whose ACS page needs
a bespoke handler written into the driver is how the last run ended up with a private patched
harness that no later run could reuse.

Record `{final_url, http_status, hops[]}` in the unit's record, and a screenshot on failure as
evidence. No file under `grace/testkit/acs/` for this connector, and the flow needs a
challenge → `E2E_BLOCKED`, reason `NO_ACS_PROFILE`, naming what would unblock it. Do not
hand-drive a browser interactively; this stage runs unattended.

Some sandboxes cannot avoid the challenge even when asked: Airwallex returns
`REQUIRES_CUSTOMER_ACTION / AUTHENTICATION_REDIRECTED` for a consent CIT even with
`three_ds_action=SKIP_3DS`. Where the connector does document frictionless test cards, prefer
them and assert `eci` and liability shift from the response — a leg you do not have to drive
is a leg that cannot flake.

### 4d. Assert all three hops, not just the last

An HTTP 200 from Hyperswitch is not sufficient, because a Direct-path success looks identical
from the outside and proves nothing about this run's work:

1. **Hyperswitch chose the UCS path** — the router log records the UCS call and
   `ExecutionPath` is not `Direct`. Grep the router log for
   `Failed to parse rollout config as JSON`: a hit means the rollout value is malformed and
   **everything below it is worthless**.
2. **UCS ran `{FLOW}`** — the UCS log names the flow marker and the connector.
3. **The connector returned a real result** — a real transaction/refund id, not a stub.

All three, per unit, quoted into the record. A unit missing any one of them is not SUCCESS.

### 4e. What curl cannot do

**Webhooks still need a captured fixture.** You replay one; you do not author one. If this
connector has no captured notification in `connector_specs/{connector}/webhook_payload.json`,
the Hyperswitch leg of `IncomingWebhook` is `E2E_BLOCKED` with reason `NO_WEBHOOK_FIXTURE`.
Writing the fixture from the connector's documentation would be inventing the oracle, which is
the defect this redesign exists to remove — do not do it.

**That is a statement about the Hyperswitch hop only.** Do not read it as "webhooks are
untestable". `grace/workflow/2.6f_grpc_agent.md` exercises them directly over gRPC —
`EventService/HandleEvent` with the connector's real captured body and headers, HMAC computed
over them, asserting `source_verified`, `event_type` and `event_status`, with
`invalid_signature` proving the negative. What this phase adds is only the extra hop — that
Hyperswitch's `/webhooks/{merchant_id}/{connector}` endpoint routes the notification into UCS
at all — and losing that hop blocks `e2e_status`, never `grpc_status`.

## Phase 5: Raise the Hyperswitch PR, if Phases 1–3 found a required change

Only if `HS_CHANGES_REQUIRED` is non-empty.

### 5a. The Cypress defects — no longer this run's dependency, still real

Phase 4 drives Hyperswitch with curl, so **none of the defects below can block this run** and
none of them is a required change. They remain genuine defects in the Hyperswitch harness —
the repo's own suite still reports green while testing the direct integration — so carry them
into the PR only when the operator has asked for that repair, and never at the cost of the
connector change under review.

Each has been observed; open the line before you change it, because a later Hyperswitch commit
may have fixed one already, and a "fix" applied to already-correct code is how a green suite
becomes a lying suite.

| # | Defect | Where | Why it matters |
|---|---|---|---|
| (a) | `Cypress.env("CYPRESS_CONNECTOR")` — Cypress **strips** the `CYPRESS_` prefix, so the value is always `undefined` | `cypress-tests/cypress/e2e/spec/UnifiedConnectorService/0001-UCSComprehensiveTest.cy.js` | the spec's include check runs on `undefined` and the spec skips unconditionally, for every connector. Read `Cypress.env("CONNECTOR")` |
| (b) | `setupUCSConfigs` writes the rollout value as the bare string `"1.0"` | `cypress-tests/cypress/support/commands.js` | the router does `serde_json::from_str::<RolloutConfig>()` (`crates/router/src/core/unified_connector_service.rs`), the parse fails, it falls back to the default → `rollout_percent: 0.0` → `ExecutionPath::Direct`. **The suite goes green having tested the direct integration.** Fix by collapsing `setupUCSConfigs` onto `createIndividualRolloutConfig`, which already writes the correct object |
| (c) | `execution_mode` defaults to `"shadow"` for any connector not in `CONNECTOR_LISTS.INCLUDE.UCS_CONNECTORS` | same file, `createIndividualRolloutConfig` | shadow runs UCS and then **discards its response**; the assertion sees the direct result. A gate must be `primary`. Make it honour `UCS_EXECUTION_MODE` |
| (d) | nothing sets `ucs_enabled` on the **main** payments path — only the UCS-specific spec does | same file | `check_ucs_availability` short-circuits to `Disabled` without it, so the flow specs never reach UCS at all |
| (e) | the main path hard-fails without a proxy it does not need | same file | `http_url`/`https_url` are `Option` in the Rust; treat an absent proxy as absent, not as an error |
| (f) | `cleanupUCSConfigs` deletes keys it never created and leaves `ucs_enabled` dangling; the rollout list is hard-coded to `Authorize`/`SetupMandate`/`PSync` | same file | later runs inherit half-configured state, and `Capture`, `Void`, `Execute` and `RSync` are never routed to UCS. Derive the flow list from the specs being run, and include `Execute`/`RSync` (refund keys carry no payment method) |

A `grace_record` task (`cypress.config.js` plus a small command wrapper) appending one JSON line
per executed command — `{flow, connector, trigger_skip, request_id, http_status, execution_path}` —
is what the repo's suite would need to tell a `TRIGGER_SKIP` pass from a real one. GRACE no longer
needs it: Phase 4b writes that file itself, from a driver that cannot skip silently. Include it only
as part of a deliberate repair of the Cypress suite.

### 5b. Raise it

```bash
cd {HS_REPO_PATH}
git checkout -b feat/{connector}-ucs-{flow_lowercase}
```

Make the minimum change the earlier phases identified: the gate overrides from Phase 3, the
`ucs_only_connectors` entry from Phase 1(a), the config mapping from Phase 2, and whichever of the 5a
defects you verified are still present. Nothing else.

Validate before committing — Hyperswitch is feature-gated and a bare `cargo check -p
hyperswitch_connectors` fails on unrelated crates:

```bash
cargo check -p hyperswitch_connectors --features v1,frm,payouts
cargo +nightly fmt --all
```

Stage explicitly — never `git add -A`. Commit with a conventional-commit subject, state in the body
**why** the change is needed (which gate defaulted to `false`, and what was therefore unreachable),
and cross-link the UCS PR. Push and open the PR.

If Phases 1–3 found nothing, there is no Hyperswitch PR to raise — say so explicitly rather than
opening an empty one.

## Phase 6: Report

Write `{RUN_DIR}/e2e/{E2E_ID}.json` (`.tmp` then `mv`) — this is what `2.6d_test_exec.md` reads:

```
{e2e_id, connector, flow, units:[unit], started_at, ended_at,
 preflight:{ran, passed, reason|null},
 hs:{repo_path, branch|null, routed: "ucs_only_connectors"|"rollout_config"|"no",
     execution_mode, rollout_key_sample, rollout_read_back,
     provision:{merchant_id, merchant_connector_id, customer_id},
     driver: "curl", steps_jsonl: "<path>"},
 hs_changes_required:[{id, gate, file, line, why}],
 hs_pr: "<url>"|"none required",
 records:[{unit, flow, e2e_status: SUCCESS|E2E_BLOCKED|E2E_SKIPPED|FAILED, reason,
           calls:[{method, path, http_status, request_id}],
           redirect_leg:{ran, acs_profile|null, final_url, hops}|null,
           evidence:{hs_request_id, hs_log_ref, ucs_log_ref, connector_id, steps_jsonl_line}}],
 notes:[string]}
```
One `records[]` entry per unit in `{UNITS}`, always — a unit you could not test gets a record saying so,
never a missing entry. 2.6d treats a missing record as `FAILED`, so omitting one is indistinguishable
from a failure and you lose the reason.

Then print:

```
CONNECTOR: {connector}
FLOW: {FLOW}
E2E_STATUS: SUCCESS | E2E_BLOCKED | E2E_SKIPPED | FAILED
HS_ROUTED: yes | no (via ucs_only_connectors | via rollout config)
HS_CHANGES_REQUIRED: <list, or "none">
HS_PR: <url, or "none required">
EVIDENCE: <the HS request, the UCS log line naming the flow, the connector's real id>
E2E_NOTES: <anything the reviewer must know, including any UCS bug found but not fixed>
OUTPUT: {RUN_DIR}/e2e/{E2E_ID}.json
```
The printed `E2E_STATUS` is the worst status in `records[]`, in the order
`FAILED > E2E_BLOCKED > E2E_SKIPPED > SUCCESS`.

`E2E_STATUS` meanings — do not blur them:

- **SUCCESS** — a real Hyperswitch call reached the connector through UCS and returned a real result.
  All three Phase 4d assertions hold.
- **E2E_BLOCKED** — the sandbox account cannot perform `{FLOW}` (Phase 0b), the flow needs a browser
  challenge and this connector has no ACS profile (4c, `NO_ACS_PROFILE`), no webhook fixture exists
  (4e, `NO_WEBHOOK_FIXTURE`), or Hyperswitch cannot reach the flow at all (Phase 3 gate missing). The
  code may be correct and is simply unverifiable here. Name what would unblock it.
- **E2E_SKIPPED** — **no Hyperswitch checkout exists.** That is the only meaning. "We did not run it"
  is `FAILED`; see the sequencing note in `2.6d_test_exec.md` Phase 7, which explains why blurring
  these two silently drops every PR's score from 1.0 to 0.6.
- **FAILED** — Hyperswitch could reach UCS and the flow genuinely misbehaved, or the run did not happen
  and nothing above excuses it. This is the value that means the implementation may be wrong.
