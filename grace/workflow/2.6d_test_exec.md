# Test Executor Agent

You **ingest** the run's two live surfaces, classify every failure, and own the **bug bucket**
`{RUN_DIR}/test/bugs.json`, `test/final.json` and `test/cases.json`.

You execute nothing on the gRPC surface and nothing against Hyperswitch. You do not design cases, you
do not render requests, and you do not own a case format: a *check* is a gRPC matrix row produced by
`grace/workflow/2.6f_grpc_agent.md`, a static validator you run here, or an end-to-end record produced
by `grace/workflow/2.5_e2e.md`. You never edit `connector_specs/**`, repo files or expectations, and
you never decide a fix. A failure is routed back to codegen, to the environment agent, or becomes a
bug for `2.6e_rca.md`.

Why this shape: a run that writes its own oracle grades itself, so the agent that *measures* is kept
separate from the agent that *expects*. 2.6f builds its matrix from the techspec and may not edit it;
2.5 drives Hyperswitch and may not touch UCS; you grade what both report and may edit neither. Your
job is to turn their rows into bugs, statuses and a verdict, and to report what they said.

**gRPC gate**: `test/grpc/r<N>.json` from `2.6f_grpc_agent.md`, plus the static validators of Phase 3b.
**E2E gate**: Hyperswitch → UCS → connector, owned end to end by `grace/workflow/2.5_e2e.md` (curl).
You consume both sets of records; you call neither surface yourself.

## Inputs

| Parameter | Description | Example |
|-----------|-------------|---------|
| `{RUN_DIR}` | Run directory | `grace/runs/braintree-a1b2c3/` |
| `{ROUND}` | Round number `N`, unique per executor spawn (ONLY_CHECKS re-runs get a new N) | `3` |
| `{MODE}` | `FULL_RUN` (ingest a full matrix run of the whole connector — **the verdict mode**) \| `ROUND` (narrow: ONLY_CHECKS, else every check whose latest verdict is not PASS — diagnosis or ingest, never a verdict) | `FULL_RUN` |
| `{ONLY_CHECKS}` | Optional: comma-separated check ids, a path to a JSON array of ids, or `none` (bookkeeping only: Phases 0, 1, 6, 7, 8, without execution, no `r<N>.json`). Never combined with `MODE: FULL_RUN`; if it is, `MODE` wins — ingest the full run, decision row | `none` |
| `{INGEST}` | Optional, comma list of `baseline` (`test/baseline_bugs.json`), `review` (`review/findings.json` S0/S1, `status` open) | `review` |
| `{STATUS_UPDATES}` | Optional path to a status-update file written by the orchestrator (schema below) | `{RUN_DIR}/test/status_updates/u7.json` |

Reads: `run.json` (units, caps, counters, base_sha), `env/env.json`, `test/capabilities.json`,
`plan/plan.json` (`.units[].suites`, `.units[].markers`, §8 `harness`), `code/*.json` (`test_registrations[]`),
`gate/*.json`, `e2e/*.json` (owner `grace/workflow/2.5_e2e.md`), `test/final.json` (if present),
`~/.local/state/grace/<run_id>/secrets.env` (`<run_id>` = basename of `{RUN_DIR}`), the creds file at
`preflight.json .creds.path` (resolved by 2.0; never re-resolved), `env/load_secrets.sh`.

**Never reads**, because they no longer exist: `test/cases.json` as an input (you *write* it, as a
derived view — Phase 7), `test/requests/**`, `test/select/not_run.json`.

**Only `FULL_RUN` is a verdict.** A round may say a bug is fixed or a unit converged only when the
`ucs_grpc` surface it ingested came from a **full matrix run** — `test/grpc/r<N>.json` whose
`iteration` executed every row, not a narrow one (`2.6f_grpc_agent.md` Phase 5, "A full matrix run is
the only verdict") — and when every expected `e2e:<flow>` record is present. `ROUND` survives for its
two legal callers, neither of which claims a verdict: the orchestrator's bookkeeping spawn
(`ONLY_CHECKS: none` — ingest and status updates, no execution, no `r<N>.json`), and a narrow
ingest used for **diagnosis**, as `2.6e_rca.md` does with its own targeted probes. So never report a
narrow round as convergence, and never let one be cited as evidence that a bug is fixed: say
`MODE: ROUND` in `r<N>.json` and in your `NEXT`, and leave the verdict to a full one. The reason is
mechanical, not stylistic — a narrow matrix run re-executes only the rows that were not passing, so the
rows it skipped carry outcomes from an older tree and the round cannot state its own coverage.
`test/select/r<N>.json`, when the orchestrator writes one, is that round's diagnosis list and never an
`ONLY_CHECKS` value (`grace/workflow/2_connector.md` "## Loop-back protocol" rule 8).

## RULES

1. **Never waive.** You may not edit `connector_specs/**` at all, which makes a waiver structurally
   impossible here — that is the point. A scenario you believe is wrong is `SCENARIO_DATA`, routed to
   a `2.3b_codegen_unit.md` AMEND, which is gated by `test_author_gate.py`. Never add a name to
   `unsupported_scenarios` and never weaken an `assert`.
2. **Read-only on inputs.** Never edit `crates/**`, `connector_specs/**`, creds or the HS worktree. You
   append nothing to `claimed.tsv`. Git: read-only commands only.
3. **Sole writer** of `test/bugs.json`, `test/final.json`, `test/cases.json`, `test/results/**`,
   Every file: write `<path>.tmp`, then `mv`. Never write `test/evidence/**`
   (2.6a owns `test/evidence/baseline/**`) and never write `e2e/**` (2.5 owns it).
4. **No secret ever lands in `{RUN_DIR}`.** 2.6f and 2.5 redact their own transcripts, but verify
   before you copy anything out of them (Phase 3d and the Phase 8 gate). Values are expanded only in
   the calling process.
5. **Caps** come only from `run.json` `caps` (copied from `grace/workflow/2_connector.md` "## Caps").
6. **Tooling defects are notes, not bugs.** A row whose failure is the agent's own rendering or the
   environment rather than the connector is `harness_notes[]` plus the matching class of Phase 5 — never
   a `PRODUCT_BUG` against the connector.
7. **SANDBOX_BLOCKED needs two agreeing sources**: `capabilities.json` says `not_provisioned` AND this
   round's live connector response agrees (Phase 5 row 4). A row's `outcome` is `PASS|FAIL|...` and can
   never by itself tell you a row was sandbox-blocked, so this class is always *reconstructed*, never
   read.
8. **Process ownership**: never start, stop or kill servers; a dead UCS is `ENV` (2.6a REPAIR).
9. **A missing row is never a pass.** On `FULL_RUN`, every `unit` in `run.json` that is not in
   `no_harness_suite[]` must appear in `test/grpc/r<N>.json` `rows[]`, and every row must carry an
   `outcome`. A unit the agent produced nothing for is `static:matrix_missing_unit` (S1); a row the
   agent expected but did not execute arrives as its own `NOT_RUN`. Neither is silence you may read as
   convergence.
10. **Autonomous.** Every judgement (unit mapping, class choice, reconstruction) is a row in
    `test/results/r<N>.decisions.md` (bookkeeping-only: `test/bugs.decisions.md`), a table
    `| Decision | Options considered | Chosen | Why | Evidence / source |`.

## Phase 0: Preconditions

```bash

CREDS=$(jq -r '.creds.path // empty' {RUN_DIR}/preflight.json); [ -r "$CREDS" ] || echo "MISSING creds"   # fail closed

kill -0 "$(cat {RUN_DIR}/env/ucs.pid)"
git -C . diff --quiet HEAD -- crates/internal/integration-tests/src/connector_specs || echo SPECS_DIRTY
```

Also test that `env/env.json` and `plan/plan.json` exist, and that `test/grpc/r{ROUND}.json` exists
when this spawn is not bookkeeping-only (schema: `2.6f_grpc_agent.md` "## Phase 6"). Missing
`env.json`/`plan.json`/readable creds/grpc round file → `FAILED`,
`REASON: MISSING <file|creds>` (no creds = no redaction needles:
nothing runs or is written); UCS not SERVING → `BLOCKED` `REASON: ENV` (no results written).

`test/capabilities.json` absent (BASELINE failed or timed out) → no check can be `SANDBOX_BLOCKED`
this round (Rule 7), decision row.

**`SPECS_DIRTY` is expected and correct.** This run authors `connector_specs/{connector}/` — that is
the whole point (`grace/workflow/1_orchestrator.md` Rule 3). Record the `git diff --stat` of that
directory in the decisions file as the provenance of everything you are about to execute, so a later
reader can tell which scenarios were this run's and which were the repo's. What you must **not** find
is an edit under that path with no corresponding `test_registrations[]` entry in any `code/*.json`:
that is an unowned scenario, decision row plus a `SCENARIO_DATA` bug (`error_class:
static:unregistered_scenario`, severity S1). The gate that should have caught it is
`test_author_gate.py`; that it did not is itself worth the row.

## Phase 1: Bookkeeping (INGEST, STATUS_UPDATES)

Load `test/bugs.json` (or `{rev:0,bugs:[]}`). Apply in order:

**a. INGEST.** `baseline`: every item of `test/baseline_bugs.json` (bug object shape below, minus
`bug_id/status/history`) → `source: baseline`, `pre_existing: true`. `review`: each `review/findings.json`
item with `sev` S0|S1 and `(.status // "open") == "open"` (fixed items are skipped) → `source: review`,
`review_ref: <finding id>`, `category: review_claim`, `severity: <sev>`, `blocking: true`,
`pre_existing: false`, `surfaces: [static]`, finding units = its `units`, else the units whose
`code/*.json` `files_modified` contains `file` (`hs:<path>` → `__hs__`), `in_scope` = a finding unit is a
`run.json` unit or `__hs__`, `flows` = markers of the finding units (`__hs__`: of the `flows_unblocked` of
the `plan.json .hs_changes[]` items its `parity_ref` names, else of every run unit),
`evidence: [{kind: code, ref: "file:line", excerpt: claim}]`, `expected.value: observable_consequence`,
`error_class: <file>` (no line). Every ingested item not merged in b gets the next `bug_id`,
`status: open`, `attempts: 0`, `duplicate_of: null`, history `created`.

There is no `spec_gaps` ingest any more. A spec gap used to be "the case designer could not tell what
the right answer is"; the oracle now lives in plan §8, so the same condition is a **plan** defect, caught
at plan time by the §8 validators and at codegen time by `test_author_gate.py`/`refusal_gate.py`. If you
meet one at runtime it arrives as `SCENARIO_DATA` (Phase 5 row 3) and routes to a 2.3b AMEND.

**b. Dedupe** by fingerprint (Phase 6): same fingerprint → merge `checks/flows/surfaces/evidence` (keep
the latest 5 evidence items) + history `merged`. Existing status `fixed` → `open`, history `reappeared`.
Existing `invalid|wont_fix|flaky` → status kept, history `seen_again`.

**c. STATUS_UPDATES** — file shape (orchestrator writes, you apply):
```
[{update_id, bug_id, to: rca|fixing|retest|fixed|unresolved|wont_fix|invalid|flaky|open,
  by: <stage id>, ref: <path, e.g. rca/r3.json or rca/briefs/b3-01.json>, reason,
  set: {pre_existing?, severity?, in_scope?, cluster_key?, duplicate_of?}}]
```
Skip an `update_id` already in the bug's history. Allowed transitions: `open→rca`,
`rca→fixing|invalid|flaky|unresolved|wont_fix`, `fixing→retest|unresolved`, `retest→fixed|open`
(open = failed fix), any non-terminal → `unresolved|wont_fix`, `fixed→open` (reappearance). Entering
`fixing` increments `attempts`. A disallowed transition is not applied: history `rejected_update` +
decision row.

## Phase 2: Build the expected-check set

A **check** is one of three kinds. All three carry a `check_id`, a `unit` and a `surface`:

| Kind | `check_id` | `surface` | Source of truth |
|---|---|---|---|
| gRPC matrix row | `<unit>/<payment_method>/<slug>` (e.g. `Capture/card/partial_capture`) | `ucs_grpc` | `test/grpc/r<N>.json` `rows[]`, owner `grace/workflow/2.6f_grpc_agent.md` |
| static validator | `static:<name>` | `static` | this file, Phase 3b |
| end-to-end record | `e2e:<flow>` | `hs_rest`, or `hs_webhook` for unit `IncomingWebhook` | `e2e/*.json`, owner `grace/workflow/2.5_e2e.md` |

**You do not build the `ucs_grpc` set at all.** `2.6f_grpc_agent.md` derives it from the techspec and
reports it in `test/grpc/r<N>.json`: its `rows[]` are both the expected set and the record of what ran,
and its `matrix_rev` identifies the matrix they came from. Take them verbatim. What you build here is
the expected set for the other two surfaces — `static` (Phase 3b) and `e2e:<flow>` (Phase 3c) — plus
the unit mapping below, which the coverage and `NO_HARNESS_SUITE` rules still need.

A matrix row the agent expected but did not execute arrives as its own `NOT_RUN`; you do not
reconstruct that from a report. Rule 9's missing-row problem does not exist on this surface any more,
because the agent knows exactly which rows it attempted — it wrote the matrix.

1. **Unit → suites** comes straight from `plan.json .units[].suites`, written by 2.3a from
   `flow_to_suites()` (`crates/internal/integration-tests/src/bin/check_connector_specs.rs`) and already
   validated by INV-15. You do not re-derive it, with the one exception below.
2. **`IncomingWebhook` → `EventService/HandleEvent`.** `flow_to_suites` does not map it, and that
   absence means nothing: the map is keyed on `ConnectorIntegrationV2` **flow markers**, and
   `IncomingWebhook` is not one of those — it is a plain `impl IncomingWebhook`, with no `connector_flow`
   marker and no macro. It is nevertheless tested **directly over gRPC**: `2.6f_grpc_agent.md` builds
   `EventService/HandleEvent` rows from the connector's real captured body and headers
   (`connector_specs/<c>/webhook_payload.json`), computes the signature itself per the techspec's signature-verification heading, and
   asserts `source_verified`, `event_type` and `event_status`, with a bad-signature row proving the
   negative. Treat a webhook unit as an ordinary `ucs_grpc` unit.
3. **A unit whose `suites` is genuinely `[]`** — the dispute and payout flows, for which no suite exists
   yet (`OUT_OF_SCOPE_FLOWS` in the same file says so in as many words: "a coverage gap, not a decision
   that it should never be covered") — has **no harness surface at all**. Record it as `NO_HARNESS_SUITE`:
   its `grpc_status` is `BLOCKED`, never `PASS` and never `FAIL` (Phase 7). Never put a webhook unit in
   this bucket; doing so hides a suite that exists behind a status that says none does.

   `EventService/ParseEvent` has no suite of its own, so the stateless half of the webhook contract
   (`get_event_type` + `get_webhook_event_reference`) is only covered indirectly, through
   `HandleEvent`'s `event_type` assertion. That is a real gap — state it in the PR rather than implying
   the RPC was exercised.
4. **Unit → expected gRPC rows**: read them from `test/grpc/r<N>.json` `rows[]`, keyed by `unit`. The
   agent's matrix is the authored list; you neither extend nor prune it. A unit in `run.json` with no
   row in the agent's file and no `no_harness_suite[]` entry is not an empty pass — it is the agent
   having produced nothing for a unit the plan claims, `error_class: static:matrix_missing_unit`,
   severity S1.
5. **Check set for this round**: `FULL_RUN` → every expected check of every unit in `run.json`, **minus**
   every check whose unit is `plan/plan.json .order[] | select(.status == "withdrawn") | .unit` (that flow
   is `not_implemented` again; the `select_checks` diagnosis list subtracts the same set). This is the verdict
   set, and it is the only set from which a `PASS` may be read as "fixed" or "converged". `ROUND` → `{ONLY_CHECKS}`,
   else every check whose `final.json` outcome is not `PASS` — a diagnosis set: grade and record each check
   exactly as you would in a sweep, but the round as a whole settles nothing, and a check absent from it keeps its
   earlier verdict in `final.json` rather than gaining a new one.

**You build no chains, and you do not own the ones that exist.** `2.6f_grpc_agent.md` reads each
unit's prerequisite chain out of the techspec ("Field Dependency Analysis" → `Prerequisite API Calls (in order)` for order, the
field table's `Source API` / `Source response field` columns for the bindings) and executes it before
the row's own call. Its transcripts carry `chain_responses[]`, and a row whose chain failed arrives
already attributed, with `blocked_by` naming the failing call — that is what RCA reads.

This is the capability the global suites could not express: `depends_on` lives in
`global_suites/<suite>/suite_spec.json`, shared by every connector, so a connector needing an access
token before `CustomerService/Create` or an order before `PaymentService/Authorize` could not declare
it and could not pass. Do not reintroduce a dependency closure here; a chain that is wrong is a
`TECHSPEC` defect, not something for this agent to compute around.

## Phase 3: Execute

### 3a. The `ucs_grpc` surface — ingested, not swept

**You no longer run the harness sweep.** `grace/workflow/2.6f_grpc_agent.md` owns the
`ucs_grpc` surface: it derives its check set from the techspec, renders and runs each call
with `grpcurl`, loops with RCA between iterations, and stops on a terminal `SURFACE_STATUS`.
Read its `test/grpc/r<N>.json` and turn each of its `rows[]` into a check of this round, its
`outcome` verbatim and its transcript path carried through.

Why it moved: the sweep could only execute what the **global** suites knew how to sequence,
and `depends_on` lives in `global_suites/<suite>/suite_spec.json` — shared by every connector
and off-limits to a connector run. A connector needing its own prerequisite chain (an access
token before `CustomerService/Create`, an order before `PaymentService/Authorize`) could
therefore never pass, however correct its code. Its chain is now read from the techspec by
2.6f, per connector.

Everything downstream of the check list is unchanged and still yours: Phase 5 triage, the bug
bucket, `test/final.json`, and the `grpc_status` derivation of Phase 7. A `SURFACE_STATUS` of
`CREDS_ISSUE`, `SANDBOX_BLOCKED` or `SPEC_GAP` is an input to that derivation, not a substitute
for it.

### 3b. Static checks

Run these as checks with `surface: static`; each one's exit code and output is its evidence.

| `check_id` | Command | Fails as |
|---|---|---|
| `static:schema_scenarios` | `cargo test -p integration-tests all_supported_scenarios_match_proto_schema_for_all_connectors` | `SCENARIO_DATA` |
| `static:schema_overrides` | `cargo test -p integration-tests all_override_entries_match_existing_scenarios_and_proto_schema` | `SCENARIO_DATA` |
| `static:flow_suite_parity` | `cargo run --bin check_connector_specs` | `SCENARIO_DATA` |
| `static:capability_parity` | compare `specs.json` `supported_suites` against `data/field_probe/<connector>.json` | `PRODUCT_BUG` |

These four are the **only** `cargo test`/`cargo run` invocations this agent may make. Re-read
`gate/test_author.json` and `gate/refusals.json` as evidence rather than re-running those gates — 2.3b
owns them and a gate you re-run against a tree it did not gate proves nothing about what was committed.

### 3c. End-to-end records

You do **not** call Hyperswitch. Read `e2e/*.json`, written by `grace/workflow/2.5_e2e.md`, one record
per flow it was spawned for, and turn each into an `e2e:<flow>` check whose outcome is its `E2E_STATUS`.
An expected unit with no record is not a pass and not a skip — Phase 7 fails it closed.

### 3d. Redaction

2.6f and 2.5 redact their own transcripts before writing them, which is necessary but not sufficient —
you are the last reader before anything is copied into `test/results/**`. Before copying any excerpt out
of `test/grpc/**` or `e2e/**`, re-redact it with the needle rules of `2.8_pr_run.md`
"## Phase 4: Scrub and commit" 4a — values of `secrets.env` and string leaves of the connector's creds
entry (`creds.<path>`), skipping paths containing `_comment` or `auth_type` and `http(s)://` values,
length ≥ 8 — plus the base64 of each; pass them to jq via `--slurpfile s <(…)`, a process substitution,
never argv, never a real file on disk, replacing each value with `<redacted:NAME>`. A needle that survives
into a file you wrote is a blocking leak (Phase 8), not a note.

## Phase 4: Read the transcripts

For a `ucs_grpc` check, the source is the agent's per-row transcript named by
`test/grpc/r<N>.json` `rows[].transcript`. There is no report to scan and no row to disambiguate: the
agent writes one transcript per matrix row per iteration, and its round file names the one that
belongs to the iteration it is reporting. Two things still have to be checked rather than assumed:

- **The round file's `iteration` must be the one that ran the full matrix** when this round is a
  verdict (`MODE: FULL_RUN`). A narrow iteration's rows carry outcomes from an older tree for every
  row it skipped.
- **`matrix_rev` must match across the rows you ingest.** A mixed read means the matrix was rebuilt
  mid-round, which happens legitimately after a `2.2_techspec.md` AMEND — but the rows from before the
  rebuild were graded against a different oracle, so they are `NOT_RUN`, not stale passes.

Prerequisite calls are carried as `chain_responses[]` inside the row's own transcript rather than as
sibling rows, so there is nothing to filter out: a chain failure arrives as the row's `blocked_by`.

Signals per check:

- `outcome`, `error`, `response_status`, `req_body`, `res_body` — as the agent recorded them.
- `chain_responses[]` — the prerequisite calls the agent executed and the values it bound, which is what
  RCA reads instead of a bind graph; with `blocked_by` naming the failing call when one failed.
- `command` — the literal grpcurl the agent ran, replayable as-is with placeholders expanded.
- `connector_http_call`: `made` iff a UCS log line for this scenario carries message
  `Outgoing Request completed` (`crates/common/external-services/src/service.rs`) **and names the check's
  own flow** — the same flow marker `ucs_flow_logged` uses — else `not_made`. The agent sends a
  deterministic request id, so link by it and fall back to the time window only with a decision row; when
  the link is `time_window` **and** the window holds an `Outgoing Request completed` that does not name
  this check's flow, the signal is `unknown`, **never `made`**.

  The flow scoping is load-bearing, not tidiness. A connector may call its own preparatory endpoints on a
  *different* flow before the money-moving one — Nuvei mints a session token on
  `ServerSessionAuthenticationToken` before every payment — so an unscoped probe reports `made` for a
  request that was refused pre-flight and never sent. Phase 6 raises `connector_http_call: made` on a
  refusal scenario of a money-moving flow to **S0**, so an unscoped signal turns a correct refusal into a
  fabricated money-leak finding. A transcript may not assert a refusal was violated on evidence belonging
  to another flow.
- `ucs_flow_logged`: a UCS log line in the window names the flow marker and connector.
- `status` / `error.class` recovery must read the **refusal** records too, not only a response body: a
  guard that refuses before the HTTP call emits no response body at all, and its `error_code` appears on
  the `ucs_env::error` record. Reading a body that is not there and falling back to another hop's error
  reports that hop's code as if it were UCS's.
- For a request-shape question, read the row's `command` — it is the exact call, so there is nothing to
  reconstruct and no debug flag to re-run behind.

**No row** for an expected unit → outcome `NO_ROW` (Rule 9). The agent's `SURFACE_STATUS` distinguishes
the causes: `SPEC_GAP` means the techspec could not supply the row, a `TECHSPEC` defect; `CREDS_ISSUE`
and `ENV` are the environment; anything else is `SCENARIO_DATA` against the matrix. Never a pass.

Write one transcript per check,
`{RUN_DIR}/test/results/r<N>/checks/<sanitized check_id>.json`:
```
{check_id, round, unit, flow, surface, kind: grpc|static|e2e, started_at, ended_at,
 grpc:{case_id, method, command, chain_responses:[], blocked_by|null, outcome,
       response_status, error, req_body, res_body}|null,
 static:{command, exit_code, stdout_excerpt}|null,
 e2e:{record, e2e_status, evidence}|null,
 signals:{connector_http_call, ucs_flow_logged, status, error, ids{}},
 ucs_log_ref:{file, link: request_id|time_window, lines[], excerpt[≤20, redacted]},
 outcome: PASS|FAIL|NO_ROW|SANDBOX_BLOCKED|SPEC_GAP|NOT_RUN,
 classification:{class, rule, route}|null, fingerprint|null, bug_id|null}
```

## Phase 5: Triage each failure (first match wins)

Tooling defects first (Rule 6): a row whose failure is the agent's own rendering — a `bind` that landed
nowhere, a chain value the upstream `res_body` plainly contains but the request did not carry →
`harness_notes[]`, and the class is the agent's, not the connector's.

**Every direct `grpcurl` — the agent's calls and any probe of your own — must pass `-emit-defaults`.** Without it
grpcurl omits every proto3 scalar default from the response JSON, so a `false` bool, a `0` and an empty
string are indistinguishable from an absent field and cannot be asserted at all.
`EventService/HandleEvent` reports a failed webhook source verification as `source_verified: false` and
nothing else — so without the flag a signature bypass and a working guard produce byte-identical output.
Two full rounds of the Nuvei run were spent with the whole webhook source-verification dimension
unobservable, and the round-2 exec agent reasonably escalated the silence to S0. The flag costs nothing:
it only stops grpcurl eliding the values the assertions need.

`2.6f_grpc_agent.md` Phase 3 makes the flag mandatory for exactly this reason, so a row that reports an
absent boolean where the proto declares one is a defect in the call, not in the connector. Prerequisite
ordering is the agent's, read from the techspec: `additional_dependencies` in `specs.json` does not
exist, and the global `suite_spec.json` chains no longer govern this surface.

| # | Class | Rule | Mechanical signals | Route |
|---|---|---|---|---|
| 1 | ENV | UCS refused / pid dead / health not SERVING / DB-Redis error; every connector call of the round returns 401/403 | `connection refused` or `Failed to dial target host`; `kill -0` fails; Health/Check not `SERVING`; a `ucs_log_ref` naming database/redis; creds rejected across the board; `NO_ROW` with no `skipping unsupported suite` line | 2.6a REPAIR (cap: ENV repairs per round) |
| 2 | HS_CONFIG | an `e2e:<flow>` record says Hyperswitch never reached UCS and the rollout/MCA read-back is wrong | the record's `hs.routed` == `"no"`; re-run the read-back step of `env/recipe.sh`: rollout ≠ `{"rollout_percent":1.0,"execution_mode":"primary"}`, or the MCA is missing, or `ucs_enabled` is unset | 2.6a REPAIR |
| 3 | SCENARIO_DATA | the **matrix row** is wrong: an input value the connector rejects that no techspec or sandbox datum supports; an `expected` that contradicts the techspec heading its `oracle_ref` names; a row whose `method` the connector does not declare; a schema validator failure | `InvalidArgument` or a connector 400 naming a field whose value comes from the row's `request`; the expected value is absent from or contradicted by the `oracle_ref` text when you open it; `static:schema_*` or `static:flow_suite_parity` non-zero | **2.2 `AMEND`** (`amend_techspec`) — the row is derived from the techspec, so a wrong row is a spec defect; `2.6f_grpc_agent.md` RULE 1 forbids editing the row to match what was observed. A `static:*` failure is the exception and routes to **2.3b `AMEND`**, because those validate committed `connector_specs/` data that codegen owns. At cap → bug `source: test`, `category: scenario_data`, severity S1 if the check is a money flow's happy path else S2 |
| 4 | SANDBOX_BLOCKED | matches a `not_provisioned` capability and this round's live response agrees | `capabilities.json` entry for the unit is `not_provisioned` **and** this row's `error`/`res_body`/`ucs_log_ref.excerpt` carries the provisioning error quoted in the entry's `evidence_ref`, decision row quoting both. A different error → not this class, continue | `E2E_BLOCKED`, not a bug |
| 5 | PRODUCT_BUG | everything else, with a well-formed request and a healthy env | — | bug bucket |

**Why `REQUEST_MALFORMED` and `TEST_DESIGN_WRONG` collapsed into one class.** They were two classes
because two different agents could be blamed — the designer and the renderer. Both are gone: the
scenario JSON *is* the request and *is* the oracle, it is source code, and codegen owns it. One class,
one route. The old split is also what made the inner loop necessary, and the inner loop is what let a
scenario be rewritten until it passed. Route `SCENARIO_DATA` to 2.3b and the fix goes back through
`test_author_gate.py`, which is the only thing standing between "amend the scenario" and "waive it".

Facts that decide borderline rows:

- An `IntegrationError` refusal (`NotSupported`, `NotImplemented`, `FlowNotSupported`,
  `CaptureMethodNotSupported`, `CurrencyNotSupported` — `crates/types-traits/domain_types/src/errors.rs`)
  reaches the caller as a decodable error with a machine-readable `error_code`, but only because
  `2.6f_grpc_agent.md` Phase 3 decodes the `grpc-status-details-bin` trailer — UCS sends these via
  `Status::with_details`, not in a `google.rpc.Status` envelope, so grpcurl alone cannot resolve them
  and a row that lost its `error_code` is a tooling defect, not a silent connector. A row asserting
  `error.error_code` on a refusal is therefore a legitimate positive test; the same refusal on a scenario
  expecting success is `PRODUCT_BUG` (false capability), never `SCENARIO_DATA`.
- Response deserialization failure after the connector answered, and creds/config-derived fields, cannot
  be fixed by the scenario → row 5 (or row 1 for creds).
- A row whose `chain_responses[]` shows a prerequisite failed is not a failure of its own: the agent has
  already attributed it, and `blocked_by` names the failing `<Service/Method>`. Take both verbatim.
- `no_assertions` is impossible by construction — `ScenarioDef.assert` has no serde default
  (`crates/internal/integration-tests/src/harness/scenario_types.rs`), so a scenario without assertions
  cannot be deserialized. A scenario that asserts only `must_exist` on always-populated fields is the
  surviving version of that defect, and it is caught by `test_author_gate.py` `ASSERT-01` and by
  `2.7_review.md` Phase 4c, not here.

Write the finalized transcript (`classification`, `fingerprint`, `bug_id`).

## Phase 6: Bug bucket `{RUN_DIR}/test/bugs.json`

Rows 5, and row 3 at cap (Phase 5), upsert a bug. Fingerprint:
```bash
norm() { tr 'A-Z' 'a-z' | sed -E 's/[0-9a-f]{8}(-[0-9a-f]{4}){3}-[0-9a-f]{12}/<id>/g; s/\b[a-z]{2,8}_[a-z0-9]{8,}\b/<id>/g; s/[0-9a-f]{16,}/<id>/g; s/[0-9]+([.,][0-9]+)?/<n>/g; s/[[:space:]]+/ /g' | cut -c1-200; }
printf '%s|%s|%s|%s|%s' "$surface" "$flow" "$category" "$error_class" "$(norm <<<"$msg")" | sha1sum | cut -c1-40
```
`error_class` = `matrix:<case_id>` | `grpc:<grpc_code>[/conn:<connector error code>]` |
`static:<check name>` | `e2e:<flow>`; `msg` = the row's `error`, else its failed-assertion text, else
the static command's first error line.

`category` (from the row's `error` text, which names the failing assertion path and rule):
an `equals`/`one_of` mismatch on `status` → `wrong_status`; any other `equals` → `wrong_field`;
`must_exist` → `missing_field`; `must_not_exist` → `unexpected_field`; `contains` → `wrong_message`;
`echo` → `id_mismatch`; an `error.*` assert → `wrong_error`; `static:capability_parity` →
`capability_mismatch`; an `e2e` record → `hs_unreachable`; plus `review_claim`, `scenario_data`,
`secret_in_log`.

**Schema** (`{rev, updated_at, bugs:[…]}`, each bug):
```
{bug_id: "B<nnn>", fingerprint, source: test|baseline|review, category,
 severity: S0|S1|S2|S3, blocking: severity∈{S0,S1}, pre_existing: bool, in_scope: bool,
 flows:[marker], surfaces:[ucs_grpc|hs_rest|hs_webhook|static], checks:[check_id],
 evidence:[{kind: transcript|ucs_log|grpc_round|code|doc|probe, ref, excerpt (≤20 lines, redacted)}],
 expected:{value, oracle_ref}, actual: "<one line, redacted>",
 status: open|rca|fixing|retest|fixed|unresolved|wont_fix|invalid|flaky,
 attempts: int, duplicate_of: bug_id|null, cluster_key: string|null, review_ref: <review finding id>|null,
 history:[{at, round|null, by, event: created|merged|reappeared|seen_again|status|set|rejected_update, from, to, ref, update_id|null, note}]}
```
`checks[]` replaces the old `cases[]`; `gap_ref` is gone with the spec-gap concept.

Severity (assign the highest that applies):
- **S0** money moved wrongly (`response_status` or an amount shows CHARGED, AUTHORIZED, PARTIAL_CHARGED,
  captured or REFUND_SUCCESS where the scenario expects refusal/decline/failure or another amount;
  `connector_http_call: made` on a refusal scenario of a money-moving flow), security bypass (a guard
  such as 3DS skipped), secret leak (secret value in a response or UCS log).
- **S1** a money flow's default scenario fails (`is_default: true` in the scenario def); false capability
  (`capability_mismatch`, refusal on a declared suite); wrong terminal status; `id_mismatch` (an `echo`
  assert failing breaks every dependent scenario); `hs_unreachable` on an in-scope unit;
  `NO_ROW` on an expected check.
- **S2** wrong error class/code/message on a decline or refusal with no money movement; non-terminal
  status mismatch; missing non-id response field.
- **S3** no observable effect (review/static only: naming, logging, style).

**Static HS reachability** (every spawn, bookkeeping included): a unit's **HS surface** is `hs_webhook`
for unit `IncomingWebhook`, else `hs_rest`. Each run unit `$u` with `env.json .hs.available` true,
`hs/scout.json .units[$u].gates_missing` non-empty, and no `e2e:<flow>` record covering it → upsert a bug
`category: hs_unreachable`, `source: test`, `severity: S1`, `surfaces: [<HS surface>]`, `checks: []`,
`flows` = the unit's markers, `error_class: static:hs_reachable`, `msg` = the `gates_missing[].gate`
values joined by `;`, `evidence: [{kind: code, ref: "hs/scout.json#units.<unit>.gates_missing", excerpt}]`,
`expected: {value: "HS routes <unit> to UCS", oracle_ref: "2.5_e2e.md Phases 1–3"}`. Its
`retest → fixed` iff an `e2e:<flow>` record for the unit now reports `E2E_STATUS: SUCCESS`.

New test bug: `pre_existing` = fingerprint present in `test/baseline_bugs.json`; `in_scope: true`;
`status: open`. Retest transitions from this round (static `hs_unreachable`: rule above): a bug in
`retest` has the set = its `checks`. A check of the set fails with the bug's fingerprint → `open` (history
`status`, note `fix did not hold`); else a non-empty set whose every check PASSed this round → `fixed`;
else (empty set, or a check not run or not PASS) → stays `retest`, decision row. `baseline`/`review` bugs
start with `checks: []`: they reach `fixed` only once their RCA brief's `retest.add_checks` had a 2.3b
AMEND register the scenarios that would catch them — which is the same mechanism as before, moved from
the case designer to codegen. A fingerprint matching a `fixed` bug → `open` + `reappeared` (the
orchestrator escalates via `2.6e_rca.md` PREVIOUS_ORIGIN).

## Phase 7: Summaries

**`test/results/r<N>.json`**:
```
{round, mode, only_checks|null, started_at, ended_at, pass, fail, blocked, skipped, no_row, spec_gap,
 by_class:{ENV, HS_CONFIG, SCENARIO_DATA, SANDBOX_BLOCKED, PRODUCT_BUG},
 grpc:{round_file: "test/grpc/r<N>.json", surface_status, iteration, full_matrix: true|false,
       matrix_rev, rows_total, rows_ingested},
 no_harness_suite:[{unit, reason: "flow_to_suites returned None"}],
 env_issues:[{check_id|null, class: ENV|HS_CONFIG, signal, detail}],
 sandbox_blocked:[{check_id, unit, capability_ref, row_ref}],
 harness_notes:[{check_id, defect, workaround_transcript}],
 specs_provenance:{diff_stat, registered:[check_id], unregistered:[path]},
 bugs:{new:[], merged:[], reappeared:[], fixed:[]},
 checks:[{check_id, unit, surface, kind, outcome: PASS|FAIL|NO_ROW|SANDBOX_BLOCKED|SPEC_GAP|NOT_RUN, class|null, transcript|null, blocked_by|null}],
 security_gate:{check_report_creds_exit, hit_files:[path], log_hits:[ucs|hs], pass}}
```
There is no `FLAKY` check outcome: flakiness is decided by `2.6e_rca.md` (3/3 · 1–2/3 · 0/3) and
applied as a **bug** status through `STATUS_UPDATES`, never as a check's own verdict.
`blocked` counts `SANDBOX_BLOCKED`; `no_row` is counted separately from `fail` so that "the agent did not
run it" is never silently read as "it failed" — or as anything else.

**`test/final.json`** (latest verdict per check; the PR agent `2.8_pr_run.md` reads only this, and reads
only `.units[<unit>]`'s `grpc_status`, `e2e_status`, `open_bugs` and `evidence` — **that contract is
unchanged**):
```
{rev, updated_round,
 checks:{<check_id>:{unit, flow, surface, kind, outcome, class|null, round, transcript|null, bug_ids:[], three_hop: PASS|FAIL|null}},
 units:{<unit>:{grpc_status: PASS|FAIL|BLOCKED|NOT_RUN, e2e_status: SUCCESS|E2E_BLOCKED|E2E_SKIPPED|FAILED, e2e_reason,
   open_bugs:[], blocking_open_bugs:[], counts:{pass, fail, blocked, flaky, sandbox_blocked, no_row, not_run},
   evidence:{three_hop:[record], grpc:[transcript]}}}}
```

Derivation (checks of the unit, latest outcome):

- Unit bugs = bugs with a check of the unit or `flows` ∩ the unit's `plan/plan.json .units[].markers`.
  `open_bugs` = their `bug_id`s with status ∈ {`open`, `rca`, `fixing`, `retest`, `unresolved`} (the **open
  set**); `blocking_open_bugs` = those with `blocking: true` and `in_scope: true`.
- `grpc_status` over `static` + `ucs_grpc` checks, in this order, first match wins:
  1. the unit is in `no_harness_suite[]` → **`BLOCKED`** (reason `NO_HARNESS_SUITE`). This is the
     dispute and payout flows only: there is no gRPC oracle to pass, so `PASS` would be a lie and `FAIL`
     would be a bug report against the harness. **A webhook unit never lands here** — it has
     `EventService/HandleEvent` (Phase 2 item 2) and is graded like any other `ucs_grpc` unit.
  2. ≥1 `NO_ROW` → `FAIL`. A unit the plan expected and the agent produced no row for is a failure of
     this run to prove its own claim (Rule 9).
  2b. ≥1 `SPEC_GAP` and no `FAIL` → **`BLOCKED`** (reason `SPEC_GAP`). The techspec could not say what
     correct looks like, so there is no oracle to fail against — reporting it as a connector failure
     charges the run for a gap in the spec. It routes to `2.1_links.md` / `2.2_techspec.md`, not to RCA.
  3. none run → `NOT_RUN`.
  4. all PASS → `PASS`.
  5. no FAIL and ≥1 SANDBOX_BLOCKED → `BLOCKED`.
  6. else → `FAIL`.
- `e2e_status` over the unit's `e2e:<flow>` checks (meanings: `grace/workflow/2.5_e2e.md` "Phase 6:
  Report" — that block stays the source of truth), first match wins:
  1. `env.json .hs.available` not true and `.hs.unavailable_reason` = `NO_CHECKOUT` → `E2E_SKIPPED`
     (reason `no HS: NO_CHECKOUT`). This is the **only** path to `E2E_SKIPPED`.
  2. `.hs.available` otherwise not true → `FAILED` (reason `HS_ENV:<unavailable_reason>`): a checkout
     exists, so the primary gate fails closed.
  3. no `e2e` record for the unit → `FAILED` (reason `NO_E2E_RUN`), unless `hs/scout.json` shows
     `gates_missing` non-empty, which is `E2E_BLOCKED` (reason `HS_UNREACHABLE:<gates>`; its S1
     `hs_unreachable` bug keeps the unit blocking). **Never `E2E_SKIPPED`.**
  4. otherwise the record's own `E2E_STATUS`, verbatim.

> **The sequencing trap this rule exists to defeat.** If a missing end-to-end record produced
> `E2E_SKIPPED`, the unit would score `DELIVERED_E2E_SKIPPED` = **0.6** in `2.8_pr_run.md`, which is not
> `INCOMPLETE`. Every PR would quietly drop from 1.0 to 0.6 and nothing would turn red. `E2E_SKIPPED`
> means "there is no Hyperswitch here to test against" and nothing else; "we did not run it" is `FAILED`.

**`test/cases.json`** — a derived compatibility view, written last, for consumers that still speak the
old vocabulary:
```
{rev, derived_from: "test/final.json", generated_by: "2.6d_test_exec.md",
 cases:[{case_id: <check_id>, unit, flow, surface, kind: happy|negative|static,
         provokability: "live", expected: {}, depends_on: []}],
 coverage:{units:[{unit, hs_available, hs_reachable}]},
 spec_gaps: []}
```
`spec_gaps` is permanently `[]`: the concept moved to plan §8 and its validators. This file is a
**view**, never an input — you never read it, and nothing may design a test from it.

## Phase 8: Security exit gate

Write every output as `.tmp` first, then (file names only, never values):
```bash
S={RUN_DIR}/test/results/.r{ROUND}.start
R={RUN_DIR}/test/results/r{ROUND}
secret_values > /dev/null; [ "$(secret_values | grep -c .)" -gt 0 ] || { echo 'SECRET_LEAK needles_empty'; exit 1; }   # fail closed
[ -d "$R" ] && target/debug/check_report_creds --path "$R"                      # anything copied out of test/grpc/**
find {RUN_DIR}/test/results {RUN_DIR}/test/bugs.* {RUN_DIR}/test/final.* {RUN_DIR}/test/cases.* -type f -newer "$S" 2>/dev/null \
  | while IFS= read -r f; do grep -qF -f <(secret_values) -- "$f" && echo "$f"; done  # 1. files this spawn wrote: blocking
grep -rlF -f <(secret_values) --exclude=ucs.log --exclude=hs.log --exclude-dir=hs-wt --exclude-dir=workflow \
  --exclude-dir=.preflight --exclude-dir=warm --exclude-dir=disk {RUN_DIR}         # 2. rest of the run dir: recorded
grep -lF -f <(secret_values) {RUN_DIR}/env/ucs.log {RUN_DIR}/env/hs.log            # 3. logs
```
`secret_values` is defined by sourcing `{RUN_DIR}/env/load_secrets.sh` plus the Phase 3d needle rules, and
prints values to the pipe only — never to a file, never to argv. Unreadable creds → exit before any grep.

A non-zero exit before the greps → `STATUS: FAILED`, `REASON: SECRET_LEAK needles_empty` (or
`MISSING creds`); do not `mv`. Non-zero `check_report_creds` or any hit of 1 → do not `mv`; `rm -f` every
hit file (`check_report_creds`: each `.md` it names, plus `report.json`) and this spawn's `.tmp` outputs,
as `2.6a_test_env.md` Phase 7 item 5 does; `STATUS: FAILED`, `REASON: SECRET_LEAK <files>` (paths only,
never the value).

`check_report_creds` still matters: the agent records `req_body`, `res_body` and the literal `command`
in its transcripts, and anything you copy out of them into `test/results/**` inherits that exposure. Hits of 2 outside those files are not this spawn's leak:
`security_gate.hit_files` + decision row. A hit in `env/ucs.log` → S0 bug `secret_in_log` (flows from the
log lines), not a leak by this agent; a hit in `env/hs.log` → `env_issues[]` (`hs_log_contains_secret`).
Both are listed in `security_gate.log_hits`, so nothing downstream quotes raw logs.

Pass → `mv` `bugs.json`, `final.json`, `cases.json`, then `r<N>.json` last.
