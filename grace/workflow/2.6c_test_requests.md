# Test Request Agent

You are agent (2) of the GRACE v2 test phase: the **request generator**. For every case in
`{RUN_DIR}/test/cases.json` (schema: `2.6b_test_design.md`) you write one executable request file under
`{RUN_DIR}/test/requests/`: a harness scenario, a grpcurl call, a Hyperswitch (HS) curl, a signed webhook,
a direct sandbox call, or a static command. The executor's drivers (`2.6d_test_exec.md` "## Phase 3:
Write driver scripts") render placeholders and run the file mechanically.

You render cases. You never change what a case asserts, never send a request to a live service, and
never edit the repo.

## Placeholders

The executor sources `{RUN_DIR}/env/load_secrets.sh` and reads `{RUN_DIR}/env/env.json` (both written only by
`2.6a_test_env.md`; this agent only cites them). These are the only `${NAME}` env placeholders a request may use:

| Name | Secret | Source |
|---|---|---|
| `UCS_CONNECTOR_CONFIG` | yes | `load_secrets.sh` (mirrors `build_wrapped_config`, `crates/internal/connector-creds/src/lib.rs`) |
| `UCS_GRPC_TIMEOUT_SECS` | no | `load_secrets.sh`; the harness reads it (`harness/scenario_api.rs`) |
| `HS_API_KEY`, `HS_WEBHOOK_SECRET` | yes | `~/.local/state/grace/<run_id>/secrets.env`, sourced by `load_secrets.sh` (`HS_WEBHOOK_SECRET` is also the MCA `merchant_secret`) |
| `HS_BASE_URL`, `HS_MERCHANT_ID`, `HS_PROFILE_ID` | no | `env.json` `.hs.api_url`, `.hs.merchant_id`, `.hs.profile_id` |

Other namespaces:
- `${bind.<identifier>}`: from a dependency's `binds_out`, or this request's own `binds_out` inside `poll`.
- `${sign.<key>}`: output of this case's signing script.
- `${derived.<key>}`: this file's `derive` map, evaluated in memory at call time.

## RULES

1. **Never edit the repo.** Not the UCS tree, not the HS worktree, and nothing in `claimed.tsv`. Harness
   test data goes into staged copies under `{RUN_DIR}/test/requests/connector_specs*/`. Every harness
   request carries `harness.specs_root` (never null), which the executor exports as both
   `UCS_CONNECTOR_SPECS_ROOT` (`harness/scenario_loader.rs`) and `UCS_CONNECTOR_OVERRIDE_ROOT`
   (`harness/connector_override/loader.rs`), so the harness never reads the tree's `connector_specs/`.
   Deltas meant for the PR are listed, never applied: `index.json .promotions[]` (Phase 4). Only a
   `2.3b_codegen_unit.md` AMEND writes `connector_specs/` (and claims it), briefed by the orchestrator
   (`__promote__`) with the promotions whose case is `PASS` in `test/final.json`.
2. **Render the case, never fix it.** Every payload value comes from the case's `inputs[]`, its
   fixtures or a bind. If the request needs a value the case does not provide, list the case under
   `unrenderable` in `index.json` with the missing path, and 2.6b amends it. Do not invent test data.
3. **No secrets on disk.** Secret placeholders may appear only in `headers`, `derive`, `poll.headers`
   and `payload.webhook_secrets.*` (a HandleEvent proto field). Phase 3 greps every credential value over
   the output.
4. **Positive overrides only** (harness backend).
   - Key shape: `override.json` keys are `<Service>/<Method>` → scenario → `{grpc_req, assert, pre_request_http}`
     (`ScenarioOverridePatch`, `deny_unknown_fields`). Suite names use the slash form
     (`PaymentService/Authorize`); the on-disk dir is `PaymentService_Authorize`.
   - `grpc_req` is a JSON Merge Patch: objects merge, scalars/arrays replace, `null` removes
     (`crates/internal/integration-tests/docs/connector-overrides.md` "Merge semantics"). Patch leaves,
     not whole objects.
   - **Never** write `assert: null`, an `assert` that expects failure from a success scenario, or an
     `unsupported_scenarios` entry (that is a capability statement). A patch only swaps test data and
     keeps the request truthful.
5. **Override limits.** An override cannot fix, so a case that needs any of the following is not
   harness-eligible:
   - config/creds-derived fields;
   - generated headers and request-reference ids. The harness fixes `x-request-id` to
     `<suite>_<scenario>_req`. For connectors that cap reference-id length, the only knob is `specs.json`
     `request_id_source_field` + `request_id_prefix` + `request_id_length`, applied only when that field
     exists in the suite's `scenario.json`;
   - `IntegrationError` refusals (`NotSupported`, `NotImplemented`, `FlowNotSupported`,
     `CaptureMethodNotSupported`, `CurrencyNotSupported`, in
     `crates/types-traits/domain_types/src/errors.rs`);
   - response deserialization;
   - harness dependency/context propagation.
6. **Dependencies are global.** The harness resolves them only from
   `global_suites/<Service>_<Method>/suite_spec.json` `depends_on`. Capture and Void depend on Authorize
   `no3ds_manual_capture_credit_card`; Refund, `PaymentService/Get` and `RefundService/Get` depend on
   `no3ds_auto_capture_credit_card`. There is **no** per-connector `additional_dependencies` (or
   `request_id_source_field_per_suite`). `ConnectorSuiteSpec` (`harness/scenario_types.rs`) has no
   such field, so the key is silently dropped even though `crates/internal/integration-tests/README.md`
   documents it. A case that needs other upstream context uses grpcurl with explicit binds.
7. **Joinable logs.** The executor's driver sends `x-request-id: grace-<run6>-<case_id>-<attempt>-<rand>`
   on every grpcurl/curl call (2.6d Phase 3). Requests must **not** set `x-request-id` themselves, since a
   second value breaks the join. For harness requests the id is fixed at `<suite>_<scenario>_req`
   (`harness/scenario_api.rs`), and `request_id` records that.
8. **grpcurl shape rules** are those of `grace/workflow/2.3_codegen.md` "### Step 5 — Run the grpcurl call
   for the flow you implemented.":
   - `x-connector-config` metadata, plus `x-merchant-id` / `x-tenant-id`
     (`crates/common/common_utils/src/consts.rs`);
   - `Money` = `{minor_amount, currency}`;
   - `address` required (`{}` accepted);
   - secret fields wrapped as `{"value": …}`;
   - no `request_ref_id`.
   The driver converts grpc responses to snake_case, so `binds_out` / `poll.status_path` paths use proto
   snake_case names.
9. **One writer, atomic files.** You write only `{RUN_DIR}/test/requests/**`. Write each file as `.tmp`,
   validate, `mv`, and write `index.json` last. Decisions go to `{RUN_DIR}/test/requests/index.decisions.md`
   (PROBE: `probe-<bug_id>.decisions.md`). `{ROW_ID}` set → before every final `mv`,
   `test -e {RUN_DIR}/cancelled/{ROW_ID}`; present → return `FAILED`, REASON `CANCELLED`, writing nothing more
   (cancel marker: `grace/workflow/2_connector.md` "## Spawning and joins" join rule 4).
10. **Autonomous.** Never ask. Record every judgement call, HS fact and non-default backend choice in the
    decisions file. Caps live only in `grace/workflow/2_connector.md` `## Caps`.

## Phase 1: Choose the backend

| Case | Backend |
|---|---|
| `static` / `capability_parity` | `static_cmd` |
| `waiver_audit` | `harness`, own staged root with the waiver removed |
| `ucs_grpc` + kind `happy` \| `status_arm` \| `regression`, harness-eligible (below) | `harness` |
| every other `ucs_grpc` case: all negatives (`decline`, `negative_refusal`), `id_consistency`, composite RPCs (`types.Composite*Service`), 3DS legs that carry `connector_feature_data` | `grpcurl` |
| `ucs_webhook` (ParseEvent and HandleEvent; there is no ParseEvent global suite) | `grpcurl` + `webhook` |
| `hs_rest` | `curl_hs` |
| `hs_webhook` | `curl_hs_webhook` |
| fixture preparation that must hit the connector sandbox directly (settle, simulator), and PROBE | `sandbox_fixture_curl` |

**Harness-eligible** means all of the following hold. Record each check in the decisions file.
- `case.harness` names a scenario present in `global_suites/<Service>_<Method>/scenario.json`.
- The suite is in the tree's `connector_specs/{CONNECTOR}/specs.json` `supported_suites`, the scenario
  is not in `unsupported_scenarios`, and the case's `pm` is in `supported_payment_methods` (or that
  list is empty).
- Every case input equals the scenario's `grpc_req` value or is a positive leaf patch of it (rule 4),
  and none hits an override limit (rule 5).
- The dependency the case needs is the one the global `depends_on` provides (rule 6).
- No other harness case needs a different override entry for the same suite/scenario.

## Phase 2: Render

**2a. harness.** The shared staged root is `{RUN_DIR}/test/requests/connector_specs/{CONNECTOR}/`, a `cp -R` of
`crates/internal/integration-tests/src/connector_specs/{CONNECTOR}/` (`$T`), used even when no delta is needed
(`override_entry: null`). Otherwise merge the case's `override_entry` into its `override.json` at
`suite → scenario` using `mp` below. A `waiver_audit` case gets its own root
`connector_specs.<case_id>/{CONNECTOR}/`: for `assert_null:<suite>/<scenario>/<field>` delete that key
from the copied `assert` (restoring the global assertion); for `unsupported:<suite>/<scenario>` delete
that entry from the copied `specs.json`. `specs_root` = the absolute path of the root's parent. The root
holds only this connector, so the run must be `--connector {CONNECTOR}`. The shape-check payload is
`mp(scenario.grpc_req; staged entry.grpc_req)`, and the method is `suite_spec.json` `grpc_method` if set,
else `grpc_method_for_suite` in `harness/scenario_api.rs`.

```jq
def mp($p): if ($p | type) == "object"
  then reduce ($p | to_entries[]) as $e ((if type == "object" then . else {} end);
         if $e.value == null then del(.[$e.key]) else .[$e.key] |= mp($e.value) end)
  else $p end;
```

A root `$r` is always built aside and swapped in: `SHA=$(src_sha "$T") && rm -rf "$r.tmp" && cp -R "$T" "$r.tmp"`, apply
its deltas there, then `rm -rf "$r" && mv "$r.tmp" "$r"`; `$SHA` is the root's `index.json .specs_roots[].specs_src_sha`.

**Re-stage (CREATE and every AMEND).** Codegen, `__promote__` and withdraws edit `$T` after staging. A root is stale when
`src_sha "$T"` ≠ its `specs_src_sha` (2.6d runs the same test and lists its cases under `test_suspect.stale_root`). CREATE
builds every root fresh. AMEND with any stale root: rebuild every root from the current request files: re-check harness
eligibility of each harness request against `$T` (one no longer eligible joins the scope and is re-rendered through
Phases 1–2), then re-copy `$T` and re-apply each remaining shared-root `override_entry` with `mp` and each `waiver_audit`
`harness.restores` deletion, recording the new `specs_src_sha`. A rebuild is a change: never `NO_CHANGE`; `CHANGED_UNITS` adds the units of the rebuilt
roots' cases; decisions row `staged_root_rebuilt` names the old and new sha.

```bash
T=crates/internal/integration-tests/src/connector_specs/{CONNECTOR}     # repo-relative, no trailing slash (the sha covers paths)
src_sha() { find "$1" -type f -print0 | LC_ALL=C sort -z | xargs -0 sha1sum | sha1sum | cut -c1-40; }
jq -r --arg s "$(src_sha "$T")" '.specs_roots[]? | select(.specs_src_sha != $s) | "STALE \(.path)"' {RUN_DIR}/test/requests/index.json
```

**2b. grpcurl.** Pick the seed in this order and record it in `provenance.seed`:
1. `data/field_probe/{CONNECTOR}.json` (the file name may drop underscores; glob as in `2.3_codegen.md`
   "### Step 4 — Load the gRPC request payload from field_probe (MANDATORY when available)."). Take
   `.flows.<flow_key>.<scenario>.proto_request` **only when `.status == "supported"`**. Flow keys are
   snake_case RPC names (`authorize`, `capture`, `get`, `void`, `refund`, `refund_get`,
   `setup_recurring`, `recurring_charge`, `recurring_revoke`, `pre_authenticate`, `authenticate`,
   `post_authenticate`, `parse_event`, `handle_event`, `token_authorize`, …); scenario keys are
   `PaymentMethod` arm names (`Card`, `Ach`, …) or `default`. Replace **every** probe dummy (`probe_*`
   strings such as `probe_connector_txn_001`, `probe_refund_001`, `probe_key`; example card/holder
   values) with the case's input or a bind. Re-wrap values the probe flattens
   (`"card_number": "4111…"` → `{"value": "…"}`).
2. Otherwise run `grpcurl -import-path crates/types-traits/grpc-api-types/proto -proto services.proto
   -proto composite_services.proto -msg-template describe <msg>`. Fill it from case inputs only and drop
   every template field the case does not set. The template shows just one `oneof` arm, so describe the
   arm messages you need separately.

Negatives assert on the response or gRPC status, so their payload must still be well-formed. The only
wrong thing about it is the input under test.

**2c. curl_hs.** Take the trigger from the `grace/workflow/2.5_e2e.md` "Phase 4: Run the real payment"
table. That includes its SetupMandate recipe: `payment_type="setup_mandate"` **and** `mandate_data`
**and** `amount=0`, since `amount=0` alone runs Authorize at $0. Set `capture_method` /
`authentication_type` from `dimensions`, and add `profile_id: "${HS_PROFILE_ID}"` if the struct has that
field. Take body field names from the verified `api_models` structs. Headers: the verified API key header
= `${HS_API_KEY}` and `Content-Type: application/json`. `binds_out` must capture `hs_request_id` (response
header `x-request-id`), the HS object id (`payment_id` / `refund_id`) and the connector reference field.
2.6d needs all three for the three-hop assertion. HS JSON is snake_case. Shape check: payload top-level
keys vs. the struct's fields (repeat for any `#[serde(flatten)]` member type):

```bash
awk '/pub struct PaymentsRequest \{/{f=1;next} f&&/^}/{exit} f&&/^    pub [a-z_0-9]+:/{sub(/^    pub /,"");sub(/:.*/,"");print}' \
  "$HS_WT/crates/api_models/src/payments.rs"
```

**`poll`** (required by 2.6d when a response can be pending): set it on every `ucs_grpc`/`hs_rest` case
whose flow has a Status Mappings arm that maps to a pending status (`PENDING`, `AUTHORIZING`,
`CAPTURE_INITIATED`, `VOID_INITIATED`, `REFUND_PENDING`, or the HS equivalent) while `status_one_of`
expects a non-pending one.
- `ucs_grpc` poll: `types.PaymentService/Get` (payments) or `types.RefundService/Get` (refunds), bound
  to this request's own `binds_out`.
- `hs_rest` poll: `GET /payments/{id}` or `GET /refunds/{id}`, with `force_sync=true` only if Phase 0
  confirmed it.

**2d. Webhooks.** `body_template` is the connector's payload from `### Webhook Payload Structure`, with
ids as `${bind.*}` **in the form the connector sends** (`identifiers[].forms`, `seen_in: webhook`). If no
dependency response carries that form, mark the case `unrenderable`. Write `<case_id>.sign.sh` from
`### Webhook Authentication & Signature Verification`. Contract: raw rendered body on stdin; secret only
from `HS_WEBHOOK_SECRET`; print only `key=value` lines (`body_b64=`, `signature=`, and e.g. `timestamp=`
if the scheme needs one) for `${sign.*}`; `--self-test` exits 0 only on a match. The self-test uses the
spec's worked example when it has one (`doc_vector`). Otherwise it cross-checks against an independent
tool with a dummy key (`cross_tool`), which proves the primitive but not the scheme, so record the scheme
citation. A scheme you cannot self-test (e.g. an external verification API) makes the case `unrenderable`.

```bash
#!/usr/bin/env bash
# scheme: hex HMAC-SHA256 of the raw body (<spec section + quote>)
set -euo pipefail
hmac_py() { python3 -c 'import hmac,hashlib,os,sys; print(hmac.new(os.environ["K"].encode(), sys.stdin.buffer.read(), hashlib.sha256).hexdigest())'; }
if [ "${1:-}" = "--self-test" ]; then
  body='{"id":"evt_selftest"}'
  want=$(printf '%s' "$body" | openssl dgst -sha256 -hmac grace-selftest | sed 's/^.*= //')
  [ "$(printf '%s' "$body" | K=grace-selftest hmac_py)" = "$want" ] && echo SELF_TEST_PASS && exit 0
  echo SELF_TEST_FAIL; exit 1
fi
tmp=$(mktemp); trap 'rm -f "$tmp"' EXIT; cat > "$tmp"      # exact bytes; $(cat) would strip newlines
printf 'body_b64=%s\n' "$(base64 -w0 < "$tmp")"
printf 'signature=%s\n' "$(K="$HS_WEBHOOK_SECRET" hmac_py < "$tmp")"
```

- `ucs_webhook`: `method` `types.EventService/ParseEvent` or `types.EventService/HandleEvent`.
  `payload.request_details` = `{method: "HTTP_METHOD_POST", uri, headers: {<sig header>: "${sign.signature}", …},
  body: "${sign.body_b64}"}` (`body` is proto `bytes`, so base64). HandleEvent adds
  `webhook_secrets.secret: "${HS_WEBHOOK_SECRET}"` and the `event_context` that `events.proto`
  `EventContext` requires.
- `hs_webhook`: `POST ${HS_BASE_URL}/webhooks/${HS_MERCHANT_ID}/{CONNECTOR}` (route shape per the Phase 0
  grep), with `payload: null`. The executor sends exactly the bytes the sign script signed.

**2e. sandbox_fixture_curl / static_cmd.**
- `sandbox_fixture_curl`: base URL from `config/development.toml` `[connectors]`
  `{CONNECTOR}.base_url` (the same source `2.6e_rca.md` uses), path and auth from the spec's
  `## Authentication` and endpoint sections. Credentials come via `derive` from
  `${UCS_CONNECTOR_CONFIG}` (values already unwrapped). Never pass UCS headers.
- `static_cmd` for `capability_parity` has one step per check:
  - `cargo run --bin check_connector_specs`, expecting exit 0;
  - a `jq` step per `(flow, suite, field_probe key)` input asserting
    `.flows.<key> | any(.[]; .status == "supported")` ⇔ suite ∈ `specs.json` `supported_suites`.

**Shape check** (grpcurl, harness, ucs_webhook). Placeholders are substituted with dummies,
`buf convert` round-trips the payload, and every input key missing from the output is either a proto3
default (listed in `stripped_defaults`, which you must delete from the payload) or an unknown key. The
proto3 JSON output keeps set messages, `optional` presence and map keys.

```bash
P=crates/types-traits/grpc-api-types/proto; W=$(mktemp -d)
msg_of() { grpcurl -import-path $P -proto services.proto -proto composite_services.proto describe "${1/\//.}" \
           | sed -nE 's/.*rpc [A-Za-z]+ \( \.([A-Za-z0-9_.]+) \).*/\1/p'; }
M=$(msg_of "$(jq -r .method "$REQ")")        # harness: method from 2a
jq 'walk(if type == "string" then (if . == "${sign.body_b64}" then "MQ==" elif test("\\$\\{") then "1" else . end) else . end) | .payload' \
  "$REQ" > "$W/in.json"
buf convert $P --type "$M" --from "$W/in.json#format=json" --to "$W/out.json#format=json" \
|| echo "SHAPE_FAIL buf convert rejected the payload (message above names the field)"
jq --arg m "$M" --slurpfile out "$W/out.json" '
def ck: gsub("_(?<c>[a-z0-9])"; .c | ascii_upcase);
def isdef: . == null or . == 0 or . == "" or . == false or . == [] or . == {} or . == "0" or (type == "string" and endswith("_UNSPECIFIED"));
def unknown($o; $p):
  if type == "object" then to_entries[] as $e
    | (if ($o | type) == "object" then (if ($o | has($e.key)) then $o[$e.key] elif ($o | has($e.key | ck)) then $o[$e.key | ck] else null end) else null end) as $ov
    | if $ov == null then (if ($e.value | isdef) then {strip: "\($p).\($e.key)"} else {unknown: "\($p).\($e.key)"} end)
      else ($e.value | unknown($ov; "\($p).\($e.key)")) end
  elif type == "array" then to_entries[] as $e | $e.value | unknown((if ($o | type) == "array" then $o[$e.key] else null end); "\($p)[\($e.key)]")
  else empty end;
[unknown($out[0]; "payload")] | {method: "buf_convert", described_msg: $m, unknown_keys: [.[].unknown // empty], stripped_defaults: [.[].strip // empty]}' "$W/in.json"
```

## AMEND mode

- **Scope.** `{AMEND_CASES}` ids (evidence: each case's entry in the newest
  `{RUN_DIR}/test/results/r<N>.json`, schema `2.6d_test_exec.md`); `__cases_rev__` → the
  `cases_changed` + `cases_added` of the newest `cases.json` `amend_history` entry (its `cases_removed`: delete their
  request files and their `index.json` `requests`, `unrenderable`, `specs_roots[].case_ids` and `promotions` entries); `{AMEND_BRIEF}` → the
  cases in its `fix[]` entries whose `file` is under `{RUN_DIR}/test/requests/`, honouring
  `do_not_touch`.
- Run the Phase 2a **Re-stage** (it can add cases to the scope).
- Re-render only those request files, starting from their current content. A scoped case with no request
  file yet (added, or skipped while its gap was open) is rendered through Phases 1–2 and added to `index.json`.
  Regenerating the set is forbidden. Bump each file's `rev`, append its `amend_history`, update the matching
  `index.json` entries (`requests`, `unrenderable`, `promotions`), bump `index.json.rev`, and append a row to a `## Amendments` section of
  `index.decisions.md` (who = `2.6c AMEND`, when, brief/case ids, what changed).
- For `REQUEST_MALFORMED`, first re-derive the failing field with `-msg-template describe` or the HS
  struct. If the request was already correct and no root was rebuilt, return `NO_CHANGE` and say so in REASON
  (it goes back to 2.6d for reclassification).

probe file, `mv` it, and add it to `index.json.probes` (re-`mv` index). Never touch case request files.
