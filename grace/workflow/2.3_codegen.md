## Phase 4a: Determine Implementation Type

Before implementing, determine if this is a **new flow** or a **payment method addition**:

### Checklist

1. **Does `{FLOW}` exist in `create_all_prerequisites!` macro?**
   - Check `{connector}.rs` for `flow: {FLOW}`
   - If YES → FLOW already exists
   - If NO → New flow needed

2. **Is `{PAYMENT_METHOD}` provided?**
   - If YES and FLOW exists → **Payment Method Addition**
   - If NO and FLOW doesn't exist → **New Flow**

3. **Cross-connector validation:**
   - Check if Adyen/Stripe have `{FLOW}` as a separate flow
   - If they DON'T but carry it as a variant of the connector's payment-method enum → It's a payment method

### Decision Table

| FLOW Exists | PAYMENT_METHOD Set | Type | Action |
|-------------|-------------------|------|--------|
| No | No | `new_flow` | Create `{Connector}{Flow}Request/Response` |
| No | Yes | `new_flow` | Create flow with payment method support |
| Yes | No | `flow_completion` | Fill gaps in existing flow |
| Yes | Yes | `payment_method_addition` | Extend the connector's payment-method enum |

### For Payment Method Additions

Do NOT:
- Create `{Connector}{PaymentMethod}Request` struct
- Create `{Connector}{PaymentMethod}Response` struct
- Add to `create_all_prerequisites!` as new flow

DO:
- Find the connector's **payment-method enum** — the enum its request struct holds to select the
  instrument. **It is not always called `PaymentInformation`.** Only five connectors declare an
  `enum PaymentInformation` at HEAD (`rg -l 'enum PaymentInformation' crates/integrations/connector-integration/src/connectors/`
  → `cybersource`, `bankofamerica`, `wellsfargo`, `moneris` in their `transformers.rs`, and
  `barclaycard` in `requests.rs`). For every other connector, read its `transformers.rs` and find the
  equivalent enum by its use, not by its name.
- Add a variant for the new instrument, following the boxing/naming style the neighbouring variants
  already use — do not impose `{PaymentMethod}(Box<{PaymentMethod}PaymentInformation>)` on a
  connector whose existing variants look different
- Create the matching payload struct next to the ones already there
- Add a match arm to the existing `{FLOW}` `TryFrom` implementation
- Map the `PaymentMethodData::{PaymentMethod}` variant (`crates/types-traits/domain_types/src/payment_method_data.rs`)
  onto the new enum variant

## Phase 5: Implement

Verify prerequisites exist (connector struct, ConnectorCommon, auth type, error handling, transformers module). If anything is missing -> return FAILED.

Then implement:

1. **Add {FLOW} to `create_all_prerequisites!`** macro
2. **Create `{Connector}{FLOW}Request`** (Serialize) and **`{Connector}{FLOW}Response`** (Deserialize) in transformers.rs
3. **Implement TryFrom**: `RouterDataV2` -> Request, Response -> `RouterDataV2`
4. **Add `macro_connector_implementation!`** with correct HTTP method, headers, URL, error mapping from spec

### The other three macros

`macro_connector_implementation!` is not the only one. All four live in
`crates/integrations/connector-integration/src/connectors/macros.rs` — read the first matcher arm of
whichever you need for its real argument keys, and copy a working invocation out of a recent
connector (`travelhub.rs`, `paynearme.rs`) rather than writing one from memory:

- **`macro_connector_flow_status_impls!`** — emits the `ConnectorIntegrationV2` blocks for every
  flow this connector does **not** serve, split across two keyed lists: `not_implemented: [...]`
  and `not_supported: [...]`. All 112 connectors at HEAD invoke it
  (`rg -l 'macro_connector_flow_status_impls!' crates/integrations/connector-integration/src/connectors/*.rs | wc -l` → 112),
  and a new connector will not compile without it — the trait bounds demand an impl for every
  flow marker. When you **add** a flow, remember to remove that flow's marker from the
  `not_implemented` list, or your new impl collides with the generated one.
- **`macro_connector_local_flow_implementation!`** — for flows that make no outbound HTTP call;
  it wires `CallConnectorAction::HandleResponseWithoutBuildRequest` and a `handle_response` path.
- **`macro_connector_payout_implementation!`** — payout flow stubs; called with no
  `payout_flows:` list it supplies the full default set of payout markers itself (104 connectors
  use it).

### Non-generic marker traits

`SourceVerification` (`crates/types-traits/interfaces/src/verification.rs`) and `BodyDecoding`
(`.../interfaces/src/decode.rs`) take **no type parameters**. There is exactly ONE impl of each per
connector, over the connector's own generic — not one per flow. Copy the shape from
`crates/integrations/connector-integration/src/connectors/travelhub.rs` (~line 175):

```
impl<T: PaymentMethodDataTypes + Debug + Sync + Send + 'static + Serialize> SourceVerification
    for Travelhub<T>
{
}
```

Writing `impl<T> SourceVerification<Flow, Data, Req, Resp> for X<T> {}` per flow is `E0107`
(wrong number of generic arguments). The same applies to `BodyDecoding`.

### Webhooks

The webhook methods are on `IncomingWebhook` in
`crates/types-traits/interfaces/src/connector_types.rs`. Read that trait before implementing any of
them — the arities differ from what older guides show, and the error type is `WebhookError`, not
`IntegrationError`. `get_event_type` takes one argument besides `&self`;
`process_payment_webhook` takes four. There is no `transformation_status` field and no
`WebhookTransformationStatus` type anywhere in the repo — do not emit either.

**Rules**:

- Always use macros (never manual `ConnectorIntegrationV2`).
- Use `RouterDataV2` not `RouterData`.
- Use `domain_types` not `hyperswitch_*`.
- POST -> include `curl_request`. GET -> omit it.
- **Auth comes from `req.connector_config`**, a `ConnectorSpecificConfig` with a per-connector
  variant (`crates/types-traits/domain_types/src/router_data.rs`). `RouterDataV2` has no
  `connector_auth_type` field — it was removed in `a7a696c3a` (2026-03-14). `get_auth_header`
  takes `&ConnectorSpecificConfig`; any other parameter type fails the trait with `E0407`. Read
  `crates/types-traits/interfaces/src/api.rs` and copy the idiom from `travelhub.rs`.
- **`build_error_response` takes three parameters** — `res`, `Option<&mut events::Event>`, and
  `&ConnectorSpecificConfig` (`interfaces/src/api.rs`). `get_error_response_v2` and
  `get_5xx_error_response` (`interfaces/src/connector_integration_v2.rs`) take the same third
  parameter. There is no `ConnectorEvent` type in this crate — it is `events::Event` — and
  `set_error_response_body` is not one of its methods.
- **Never `unwrap_or_default()` an error code or message.** Use
  `.unwrap_or_else(|| NO_ERROR_CODE.to_string())` and `NO_ERROR_MESSAGE`, from
  `crates/common/common_utils/src/consts.rs`. Those two constants appear 497 times across
  `connectors/`, 113 of them in exactly that `unwrap_or_else` idiom; an empty-string error code
  reaches the merchant as a blank field.
- **`attempt_status` on the error path is flow-aware and non-terminal by default.** Its type is
  `Option<FlowStatus>` (`FlowStatus::Payment` / `Refund` / `Dispute` / `Payout`), not
  `Option<AttemptStatus>`. A blanket `Some(AttemptStatus::Failure)` is both a type error and the
  bug that reports a charged payment as FAILURE; a blanket `None` is the opposite bug (a
  hard-declined refund stays Pending and keeps retrying). Branch on the connector's own error
  signal — see `connectors/flywire.rs` (~362-370) for the full form and `connectors/noon.rs`
  (~499-512) for the minimal one.
- **Two layers of unknown-value handling, both required.** At the *deserialization* layer, give
  every connector status enum `#[serde(other)] Unknown` so an unrecognised value parses instead of
  failing the response. At the *status-mapping* layer, match every variant explicitly — a catch-all
  `_ =>` there silently maps a new upstream status onto whatever arm you picked. Reviewers ask for
  both halves.
- **Pick the amount unit from the vendor spec, not from habit.** There are five types in
  `crates/common/common_utils/src/types.rs`: `MinorUnit`, `StringMinorUnit`, `StringMajorUnit`,
  `FloatMajorUnit`, `StringTwoDecimalUnit` (each with a matching `…ForConnector` converter). Read
  what the connector's API actually puts on the wire and match it. "Default to `StringMinorUnit`
  if unclear" is wrong far more often than it is right.
- **A 2xx response can still be a failure.** When the connector reports declines in the body of a
  200, branch on a success predicate and return `Err(ErrorResponse { .. })` for the failure case —
  do not map it to a success status. `utils::is_payment_failure`
  (`crates/types-traits/domain_types/src/utils.rs`) is the reference predicate.

## Phase 6-7: Build & Test Loop

**This is a single loop. You cannot exit it until both `cargo build` AND `grpcurl` tests pass. If you skip grpcurl testing for any reason, return FAILED, never SUCCESS.**

**DO NOT skip grpcurl testing. "Service not running" is NOT a valid reason to skip — you must start it yourself.**

### CRITICAL — Anti-loop safeguards (violation = immediate FAILED):

- **NEVER rerun the same grpcurl or cargo build command without changing code first.** If you did not edit a source file since the last attempt, you MUST NOT retry. Same code = same result. Always.
- **Maintain a fix log.** Before each retry, write down: (1) what error you saw, (2) what file you changed, (3) what you changed and why. If you cannot fill in all three, you are looping — stop and return FAILED.
- **Read server logs before every fix.** The grpcurl error message alone is never enough to diagnose the problem. You MUST check the grpc-server stdout/stderr for the actual root cause (serialization error, missing field, wrong URL, panic, etc.) before touching any code.
- **3-strike rule on identical errors:** If you see the exact same error message 3 times, you have failed to fix it. Return FAILED immediately. Do not attempt a 4th time.
- **Maximum 7 total loop iterations** (build + test cycles combined). After 7, return FAILED regardless. This prevents runaway loops.

### The Loop:

```
1. Build
2. If build fails -> read error -> fix the specific code -> go to 1
3. Start service (if not running) -> load creds -> run grpcurl tests
4. If grpcurl fails -> read SERVER LOGS -> identify root cause -> fix the specific code -> go to 1
   (You MUST change code between step 4 and going back to step 1. No change = FAILED.)
5. If grpcurl fails with credential error -> ask user -> go to 3
6. Both pass -> exit loop -> return SUCCESS
```

### Step 1 — Build:

```bash
cargo build --package connector-integration 2>&1
```

If it fails, fix the errors and rebuild. Keep iterating as long as errors are changing/reducing. Give up only after 5+ cycles with the same errors 3 times in a row AND the errors are outside your connector's files. Remember: you must make a code change between each retry — never rebuild without changing something.

If giving up on build: return FAILED with the build error details.

### Step 2 — Start the service (mandatory):

**Prefer the first-class harness.** It owns the server lifecycle, credentials and assertions; hand-rolled grpcurl is the fast pre-check for a single request while you iterate.

```bash
make test-connector connector={connector}                       # all suites
make test-scenario connector={connector} suite=authorize \
     scenario=no3ds_auto_capture_credit_card                    # one scenario
./scripts/run-tests --connector {connector} --endpoint localhost:$PORT
```

`make test-connector` / `make test-scenario` start and stop the server for you (`interface=grpc`, the default) and they DO thread the port through: both recipes expand `--endpoint localhost:$(GRPC_PORT)`, so `make test-connector connector={connector} GRPC_PORT=$PORT` moves both the server and the client. What they do not parameterise is the metrics port — see the `CS__METRICS__PORT` note below. `./scripts/run-tests` (installed on PATH as `test-prism` by `scripts/setup-connector-tests.sh`) takes `--endpoint` directly and is the option when you want to own the run yourself.

If you are driving grpcurl by hand you MUST have a running service to test against. Take the port from a variable — never hardcode 8000, another session may already hold it:

```bash
export PORT=8000                      # pick a free port; 8000 is the default and may be taken
export METRICS_PORT=8080              # must differ from 8080 if another session already holds it
CS__METRICS__PORT=$METRICS_PORT make start-grpc GRPC_PORT=$PORT
```

(`CS__METRICS__PORT` works because the config loader reads `config::Environment::with_prefix("CS").separator("__")` in `crates/common/ucs_env/src/configs.rs`, so `CS__METRICS__PORT` overrides `[metrics] port`. Leaving it at the default 8080 is a no-op — pick a distinct value when you actually need to avoid a collision.)

`make start-grpc` builds `grpc-server` (`--profile release-fast`), backgrounds it, writes `.grpc-server.pid`, and waits with a **TCP** probe (40 × 0.5 s = 20 s). It does not parameterise the metrics port (`config/development.toml` `[metrics] port = 8080`), so two concurrent sessions collide there even on different `GRPC_PORT`s — override `CS__METRICS__PORT` too.

> **There is no `/health` HTTP endpoint on the gRPC port.** `config/development.toml` sets `server.type = "grpc"`, and the axum `/health` route (`crates/grpc-server/grpc-server/src/http/router.rs`) is only mounted under `server.type = "http"` — one process serves one transport. A `curl http://localhost:$PORT/health` readiness loop can never succeed.

Use the Makefile's own TCP probe, or the gRPC health service:

```bash
for i in $(seq 1 40); do nc -z 127.0.0.1 $PORT 2>/dev/null && break; sleep 0.5; done
grpcurl -plaintext -d '{}' 127.0.0.1:$PORT grpc.health.v1.Health/Check  # {"status":"SERVING"}
grpcurl -plaintext 127.0.0.1:$PORT list types.PaymentService            # methods available
```

Stop with `make stop-grpc`. SIGTERM releases the gRPC port but the process can linger holding the metrics port — if that port stays bound, `kill -9` the PID from `.grpc-server.pid`.

If the service does not come up inside the 20 s window, return FAILED with the startup error. Do NOT skip testing and return SUCCESS.

### Step 4 — Load the gRPC request payload from field_probe (MANDATORY when available).

**Field probe is the authoritative source for gRPC request payloads.** Before constructing any grpcurl request manually, you MUST check if a field_probe file exists for this connector.

```bash
# Check if field_probe data exists for this connector.
# The probe filename strips underscores from the connector name for a few connectors
# (connector dir `absa_sanlam` -> `absasanlam.json`, `pinelabs_online` -> `pinelabsonline.json`,
# `tsys_transit` -> `tsystransit.json`), so glob rather than assume an exact match:
ls data/field_probe/{connector}.json 2>/dev/null || ls data/field_probe/ | grep -i "$(echo {connector} | tr -d '_')"

# List supported flows and scenarios:
cat data/field_probe/{connector}.json | jq '.flows | to_entries[] | {flow: .key, scenarios: (.value | to_entries[] | select(.value.status == "supported") | .key)}'

# Get the proto_request for a specific flow + scenario (e.g., authorize + Card):
cat data/field_probe/{connector}.json | jq -c '.flows.authorize.Card.proto_request'
```

**How to pick the right scenario:**

1. Look at the `{FLOW}` being implemented and, on a payment-method-addition run, at `{PAYMENT_METHOD}` (e.g. `{FLOW}` = `Authorize` with `{PAYMENT_METHOD}` = `BankDebit` → check the `authorize` flow for `Ach`, `Sepa`, `Bacs`, etc.)
2. Filter to `status: "supported"` scenarios only
3. Pick the scenario that matches the payment method you're implementing
4. If multiple scenarios are supported, test the primary one first, then others if time permits

**If no field_probe file exists** (new connector without prior probe data), fall back to manually constructing the request from the tech spec using the templates below.

### Step 5 — Run the grpcurl Authorize call.

**CRITICAL: You MUST capture the FULL grpcurl command AND the FULL response output. Both are required in the output report.**

**Mandatory metadata.** The server rejects the call before it ever reaches the connector unless you send either the single `x-connector-config` header **or** the legacy pair `x-connector` + `x-auth` plus the keys that auth kind names. Omitting them returns `Missing required field: x-connector` / `Missing required field: x-auth`.

- **Modern:** `-H "x-connector-config: {\"config\":{\"<PascalConnector>\":{ …auth fields… }}}"`. That wrapper is built by `build_wrapped_config` in `crates/internal/connector-creds/src/lib.rs`; read the PascalCase key out of that crate / `creds.json` rather than hand-casing the connector name — it does not always match a naive PascalCase.
- **Legacy:** `-H 'x-connector: {connector}' -H 'x-auth: <kind>'` plus `x-api-key` / `x-key1` / `x-key2` / `x-api-secret` as that kind requires. Valid `x-auth` values (`crates/types-traits/ucs_interface_common/src/auth.rs`): `header-key`, `body-key`, `signature-key`, `multi-auth-key`, `no-key`, `temporary-auth`, `currency-auth-key`. Header name constants live in `crates/common/common_utils/src/consts.rs`.

`x-merchant-id`, `x-tenant-id` and `x-request-id` are optional (they default to `DefaultMerchantId`, `public`, and a generated uuid v7) — send them anyway so the server logs stay greppable. Credential headers are **connector-specific**: populate them from `creds.json` (step 3), include only headers that connector actually has, and do not guess or add unused ones.

**When using field_probe proto_request (preferred):**

```bash
# Extract the proto_request payload
PROTO_REQ=$(jq -c '.flows.authorize.<Scenario>.proto_request' data/field_probe/{connector}.json)

# Run grpcurl with captured output
grpcurl -plaintext \
  -H 'x-connector: {connector}' \
  -H 'x-auth: header-key' \
  -H "x-api-key: $API_KEY" \
  -H 'x-merchant-id: test_merchant' \
  -H "x-request-id: $(uuidgen 2>/dev/null || date +%s)" \
  -d "$PROTO_REQ" \
  127.0.0.1:$PORT \
  types.PaymentService/Authorize
```

**When field_probe has no entry — derive the shape at runtime. NEVER paste a payload literal out of a prompt file.**

```bash
# Server up — reflection is registered, so no -proto flags are needed:
grpcurl -plaintext -msg-template 127.0.0.1:$PORT describe types.PaymentServiceAuthorizeRequest

# Server down — read it straight from the proto tree:
grpcurl -import-path crates/types-traits/grpc-api-types/proto -proto services.proto \
        -msg-template describe types.PaymentServiceAuthorizeRequest
```

Shape rules that hold today (sources: `crates/types-traits/grpc-api-types/proto/payment.proto` for the request message, `Money` and `PaymentAddress`; `crates/types-traits/grpc-api-types/proto/payment_methods.proto` for `PaymentMethod`, `SecretString` and the per-method messages):

- There is **no `request_ref_id` field anywhere in the proto tree.** The caller-side identifier is `merchant_transaction_id`, a plain `optional string`. Any payload carrying `"request_ref_id": {"id": …}` is rejected — if you saw that shape in an older doc, it is stale.
- `amount` is a `Money` **message**: `{"minor_amount": 1000, "currency": "USD"}`. There is no top-level `amount` / `minor_amount` / `currency` triple.
- `address` (`PaymentAddress`, field 8) is **required**. `{}` is accepted; omitting it returns `Missing required field: address`.
- Secret-typed fields are wrapper messages — `SecretString` is `{ "value": "…" }` — so card fields are `"card_number": {"value": "…"}`, `"card_exp_month": {"value": "…"}`, and so on.
- grpcurl accepts both `snake_case` and `lowerCamelCase` keys on input, but **prints** responses in lowerCamelCase (`statusCode`, `connectorTransactionId`, `redirectionData`) and enums as their SCREAMING_SNAKE proto variant names.
- `data/field_probe/*.json` renders some wrapper-typed fields flattened to bare strings. If grpcurl rejects a field from a probe payload, `describe` that message and use the shape the template prints.

**Per-connector adaptation:** `-H` headers from `creds.json` only; sandbox-safe amounts; currency matching the payment method; `merchant_account_metadata` only if the tech spec says the connector requires it; billing country matching the region.

### Deriving the payment-method sub-message (only when field_probe is unavailable):

`payment_method` is a `PaymentMethod` message whose `oneof payment_method` arm names the method. Print the real arm names and field shapes rather than copying a template — the arms and their field types change, a pasted literal does not:

```bash
grpcurl -plaintext -msg-template 127.0.0.1:$PORT describe types.PaymentMethod
grpcurl -plaintext -msg-template 127.0.0.1:$PORT describe types.Ach   # or Sepa / Bacs / Becs / CardDetails / …
```

Offline equivalent (server down):

```bash
grpcurl -import-path crates/types-traits/grpc-api-types/proto -proto services.proto \
        -msg-template describe types.PaymentMethod
```

Then pick currency and billing country to match the method — ACH -> `USD`/`US`, SEPA -> `EUR`/an EU country, BACS -> `GBP`/`GB`, BECS -> `AUD`/`AU` — and take the account/routing/IBAN test values from the tech spec or the connector's sandbox docs. Never put a real credential in a payload or in the report.

> **For payment methods other than `BankDebit`** (and for flows that are not `Authorize`): use the appropriate payment method from field_probe or the proto definitions. `BankDebit` is a `{PAYMENT_METHOD}`, not a `{FLOW}` — the flow here is still `Authorize`.

Must return a success status. `status` is the proto `PaymentStatus` enum, which grpcurl renders as the SCREAMING_SNAKE variant name from `payment.proto` — so the success values are `AUTHORIZED`, `CHARGED`, `PENDING`, or `AUTHENTICATION_PENDING` (3DS / redirect). If it fails, classify the error (see table below), fix, and retry. Do not exit the loop until Authorize succeeds for at least one payment method.

### IMPORTANT — Capture grpcurl output for the report

**After the FINAL successful grpcurl call (or the last failed attempt if returning FAILED), you MUST save the complete grpcurl interaction.** This means:

1. The **full grpcurl command** you ran (including all `-H` headers and `-d` payload)
2. The **full response JSON** returned by the server

Store this as `{GRPCURL_OUTPUT}` — it will be included in the output report and passed to the PR Agent for the PR description. Include ALL grpcurl calls if you tested multiple payment methods.

### CRITICAL — You MUST validate the grpcurl output. Running grpcurl is NOT the same as passing the test.

After every grpcurl call, inspect the FULL output and determine PASS or FAIL:

**PASS (all must be true):**

- No line starts with `Error invoking method` or `Failed to`
- Response contains a valid JSON object with `"status"` field
- `status_code` in the response is 2xx (200-299). Any other code (400, 401, 500, etc.) is a FAIL. grpcurl prints response fields in lowerCamelCase, so grep the output for `statusCode`, not `status_code`.
- Status is one of the `PaymentStatus` enum names `AUTHORIZED`, `CHARGED`, `PENDING`, `AUTHENTICATION_PENDING`. These are the literal proto variant names (`crates/types-traits/grpc-api-types/proto/payment.proto`, `enum PaymentStatus`); grpcurl prints them in SCREAMING_SNAKE, never lowercase.
- No `error` object in the response (the field is `error`, of type `ErrorInfo`), or it is null/empty

**FAIL (any one means test FAILED):**

- Output contains `Error invoking method` -> the call never reached the connector. This is a **client-side** failure: an unknown/misspelled field in your `-d` payload, a wrong message shape, a wrong method name, missing metadata headers, or connection refused. It is almost never a bug in `transformers.rs`.
- `status_code` is NOT 2xx (e.g., 400, 401, 403, 500) -> connector rejected the request
- grpcurl reports a non-OK gRPC code — `Internal`, `Unimplemented`, `Unknown`, `Unauthenticated`, `FailedPrecondition` (these are gRPC status codes; UCS maps its errors onto them in `crates/common/ucs_env/src/error.rs`)
- Response `"status"` is a failure variant of `PaymentStatus`: `FAILURE`, `AUTHORIZATION_FAILED`, `AUTHENTICATION_FAILED`, `CAPTURE_FAILED`, `VOID_FAILED`, `ROUTER_DECLINED`
- Response has a non-null `"error"` object (`ErrorInfo`: `unified_details` / `issuer_details` / `connector_details`)
- No JSON response at all (empty output, timeout, crash)

**If the test FAILS, you are STILL inside the loop. You MUST diagnose, fix, rebuild, and retest. You CANNOT return SUCCESS. Returning SUCCESS after a failed test is a critical violation.**

**First, decide which side failed.** `Error invoking method`, `unknown field`, `Missing required field: x-connector` / `x-auth` / `address`, or an `InvalidArgument` status mean **the request in this prompt is wrong, not the Rust**. Re-derive the payload (`grpcurl -msg-template … describe`, or `data/field_probe/{connector}.json`) and re-send **before** touching any source file — rebuilding on a bad payload burns loop iterations and can drive you to "fix" correct code. Only once the request is provably well-formed does an error implicate the connector implementation.

**Also read the status correctly.** grpcurl reports UCS errors as `Code: Internal … grpc-status-details-bin mismatch`; that `Internal` is a grpcurl artifact, not the server's status. The real status and message are inside that same line (`grpc-status=InvalidArgument, grpc-message="…"`). `-format-error` does not fix it.

**When a grpcurl call returns a server-side error (`status_code` 5xx, a gRPC `Internal` / `Unknown` code, or any non-success response from a well-formed request):**

1. **Check the server logs FIRST** — the grpc-server is running in the background. Check its stdout/stderr for the actual error:

   ```bash
   # `make start-grpc` backgrounds the server and writes its PID to .grpc-server.pid.
   PID=$(cat .grpc-server.pid)
   ps -o pid,cmd -p "$PID"                     # confirm it is still alive
   cat /proc/$PID/fd/1 2>/dev/null || true     # stdout, if still attached to a readable fd
   cat /proc/$PID/fd/2 2>/dev/null || true     # stderr
   ```

   If the server was started in this shell rather than by the Makefile, redirect it to a file
   (`... > /tmp/grpc-server.log 2>&1 &`) and `tail -n 200 /tmp/grpc-server.log` instead — the
   log is only greppable if you captured it.

   The server logs will contain the real error (e.g., serialization failure, missing field, wrong URL, auth rejection). The grpcurl response alone is often too vague to diagnose.

2. **Do NOT skip testing because you got an error.** An error means something needs to be fixed, not that testing should be abandoned. Diagnose -> fix -> rebuild -> retest.

### Error classification for step 4 failures:

| Type             | Signs                                    | Action                                                                                       |
| ---------------- | ---------------------------------------- | -------------------------------------------------------------------------------------------- |
| Bad grpcurl payload | `Error invoking method`, `unknown field`, `InvalidArgument`, `Missing required field: x-connector` / `x-auth` / `address` | **Do NOT edit Rust.** Re-derive the payload/headers (`grpcurl -msg-template … describe`, or field_probe) and re-send — retry from step 4 |
| gRPC config      | Connection refused, wrong method name    | Fix grpcurl command, check proto, retry from step 4                                          |
| Credentials      | 401/403, "unauthorized"                  | Ask user for correct creds, retry from step 3                                                |
| Request format (connector-side) | Connector returns 400/422 naming a field IT expected, from a payload the server already accepted | Check server logs, fix request struct in transformers.rs -> **go back to step 1 (rebuild)**  |
| Response parsing | Deserialization error, panic             | Check server logs, fix response struct in transformers.rs -> **go back to step 1 (rebuild)** |
| Server error     | `status_code` 5xx, gRPC `Internal` / `Unknown` | **Check server logs for root cause**, fix connector code -> **go back to step 1 (rebuild)**  |
| Code/logic       | Wrong status, wrong amount, wrong header | Check server logs, fix connector code -> **go back to step 1 (rebuild)**                     |

**Never say "skip the full end-to-end test" or "the build passed so the implementation is correct". A passing build only proves syntax. The grpcurl test proves correctness. You must keep looping until grpcurl succeeds — but every loop iteration MUST include a real code change. If you find yourself about to rerun a test without having changed any code, STOP — you are in an infinite loop. Return FAILED immediately.**

Keep looping as long as errors are changing and you are making meaningful fixes. Return FAILED when:

- Same error appears 3 times (3-strike rule)
- 7 total loop iterations reached
- You cannot diagnose the root cause after reading server logs
- The error is outside your connector's files and you cannot fix it

## Rules

1. **Code only** — this agent writes code and runs builds/tests. It does NOT generate tech specs or commit.
2. **No `cargo test`** — testing is done exclusively via grpcurl. Never run `cargo test`. Never edit or create test files.
3. **Anti-loop enforcement** (violation = immediate FAILED):
   - Never retry a build or grpcurl without changing code first.
   - 3-strike rule on identical errors.
   - Maximum 7 build+test iterations.
   - Must read error output / server logs between retries.
   - Maintain a fix log (error seen, file changed, what and why).
4. **Scoped changes** — connector logic goes only in `crates/integrations/connector-integration/src/connectors/{connector}*`. Registering a flow or connector may additionally require the registry / proto / config / connector_specs files listed under **Output**; touch those only where registration demands it, and report every one of them in `FILES_MODIFIED`. Do not edit unrelated connectors or core flow logic.
5. **Follow existing patterns** — never invent new patterns. Match what the codebase already does.
6. **Do NOT commit** — committing is the responsibility of the PR Agent (`2.4_pr.md`). `2_connector.md` Phase 5 spawns it; neither the Connector Agent nor the Orchestrator runs `git add`/`git commit` itself.
7. **Only do what's listed** — do not invent steps. Do not add features. Do not write tests.
