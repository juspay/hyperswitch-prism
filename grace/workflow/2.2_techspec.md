# Tech Spec Agent

You generate the tech spec for **{CONNECTOR}** via one of two paths, selected automatically by the environment check in Phase 0: `grace techspec` (Path A) or Claude-native generation (Path B). This must complete before any code work begins.

---

## Inputs

| Parameter | Description | Example |
|-----------|-------------|---------|
| `{CONNECTOR}` / `{Connector_Name}` | Connector name (exact casing from connector list) | `Adyen` |
| `{FLOW}` | Payment flow being implemented — a flow-marker name from `crates/types-traits/domain_types/src/connector_flow.rs` | `Authorize`, `Capture`, `Refund`, `RepeatPayment` |
| `{PAYMENT_METHOD}` | (Optional) Payment method to add to existing flow | `BankDebit`, `Wallet`, `PayLater` |

Use `{Connector_Name}` (exact casing) for `grace techspec` commands. Use `{connector}` (lowercase) for file names.

### Examples

**New Flow Implementation:**
- FLOW=RepeatPayment (the marker for merchant-initiated transactions; there is no `MIT` flow marker)
- PAYMENT_METHOD=(not set)
- Result: Creates new flow-specific request/response structs

**Payment Method Addition:**
- FLOW=Authorize
- PAYMENT_METHOD=BankDebit
- Result: Extends the connector's existing payment-method enum to support BankDebit within the Authorize flow. That enum is named `PaymentInformation` only in the Cybersource-family connectors — `cybersource`, `bankofamerica`, `wellsfargo` and `moneris` declare it in their `transformers.rs`, `barclaycard` in its `requests.rs`. For every other connector, find the equivalent enum in its `transformers.rs` by its use rather than by that name.

## Phase 0: Environment Check (select Path A or Path B)

Two execution paths are supported. Run this check first — it selects the path automatically and is never itself a failure condition:

- **Path A — Grace CLI** (`grace techspec`) when `grace/.env` is configured with real API keys.
- **Path B — Claude-Native** when `grace/.env` is missing or still holds the `your_…` placeholders from `grace/.env.example`. Path B uses Claude tools (WebFetch + in-place edits) to produce the same spec.

```bash
# From connector-service root:
if [ -f grace/.env ] \
   && grep -q '^AI_API_KEY=' grace/.env \
   && ! grep -q '^AI_API_KEY=your_' grace/.env \
   && grep -q '^FIRECRAWL_API_KEY=' grace/.env \
   && ! grep -q '^FIRECRAWL_API_KEY=your_' grace/.env; then
  echo "GRACE_ENV_READY"
else
  echo "GRACE_ENV_MISSING"
fi
```

This single check catches a missing `grace/.env`, an empty one, or one whose values are still the `your_api_key_here` / `your_firecrawl_api_key_here` placeholders copied from `grace/.env.example`.

**A missing or unconfigured `grace/.env` is NOT a failure.** Do NOT return FAILED here — it only selects Path B.

**Routing:**

| Check result | Phases 1a + 1b | Then |
|--------------|----------------|------|
| `GRACE_ENV_READY` | Run both — the URL file is Path A's stdin | **Phase 1c** — run `grace techspec` as written |
| `GRACE_ENV_MISSING` | Run both — the URL list is Path B's input | **SKIP Phase 1c** — follow Path B below |

Path A additionally requires the grace CLI itself to be installed. If `GRACE_ENV_READY` but the CLI is absent, treat the result as `GRACE_ENV_MISSING` and use Path B:

```bash
# From connector-service root:
ls -l grace/.venv/bin/grace
```

### Path B — Claude-Native (when `GRACE_ENV_MISSING`)

Read and execute the self-contained workflow at:

```
.skills/generate-tech-spec/references/techspec-generation-native.md
```

with these inputs:

- `CONNECTOR` / `CONNECTOR_NAME` = `{Connector_Name}` (exact casing)
- `FLOW` = `{FLOW}`
- URL list: from `data/integration-source-links.json` (extracted in Phase 1a) or `{connector_name}.txt` (created in Phase 1b)

That workflow has no `{PAYMENT_METHOD}` input of its own. When `{PAYMENT_METHOD}` is set, pass it as added context alongside `{FLOW}` (e.g. `FLOW=Authorize, extended for BankDebit`) so the generated spec still covers the payment method being added.

**Path B outputs:**

- Scraped sources at `grace/rulesbook/codegen/references/{connector}/source_{N}.md` (one per URL)
- The spec at `grace/rulesbook/codegen/references/specs/{Connector_Name}.md`
- `## API Call Sequences`, `## Field Dependency Analysis` and `## UNDECIDED Fields` appended to that spec by the field-analysis step inside that workflow

**Known limitations vs Path A:**

- Scraping uses WebFetch rather than Firecrawl, so JavaScript-heavy documentation pages may render less completely.
- Sources are processed one URL at a time rather than in parallel.
- No mock-server generation (no equivalent to the grace CLI's `-m` / `--mock-server` flag).

**Canonical output path (applies to both paths):** the downstream `new-connector` skill hard-stops unless the spec is at

```
grace/rulesbook/codegen/references/{connector}/technical_specification.md
```

That is the canonical path for this workflow. **Neither path writes there by itself** — both write `grace/rulesbook/codegen/references/specs/{Connector_Name}.md`:

- Path B, per `.skills/generate-tech-spec/references/techspec-generation-native.md`.
- Path A, because the grace CLI saves the spec under a `specs/` subdirectory of `TECHSPEC_OUTPUT_DIR` (`grace/src/tools/filemanager/filemanager.py`, `save_tech_spec`) named after the connector argument, `{Connector_Name}.md` (`grace/src/workflows/techspec/nodes/llm_analysis.py`), and `grace/.env.example` sets `TECHSPEC_OUTPUT_DIR=./rulesbook/codegen/references`.

So after **either** path completes, place a copy at the canonical path and report the canonical path in `TECHSPEC_PATH`:

```bash
# From connector-service root:
mkdir -p grace/rulesbook/codegen/references/{connector}
cp grace/rulesbook/codegen/references/specs/{Connector_Name}.md \
   grace/rulesbook/codegen/references/{connector}/technical_specification.md
```

Do not assume the consumer skill will find the spec under any other name.

Proceed to Phase 1d (Verify) once Path B completes. Path A does the same copy after Phase 1c.

## Phase 1a: Extract URLs for the connector

The Links Agent has already gathered documentation URLs and written them to `data/integration-source-links.json`. Extract the URLs for this connector:

```bash
# From connector-service root:
cat data/integration-source-links.json | jq -r '."{Connector_Name}" // ."{connector}" // empty | .[]' 2>/dev/null
```

If `data/integration-source-links.json` does not exist or has no entry for this connector, return FAILED with reason "No documentation links found for {CONNECTOR}. Run the Links Agent (2.1_links.md) first."

---

## Phase 1b: Create the URL file

Create a file `{connector_name}.txt` (lowercase) containing the URLs, one per line:

```bash
# From connector-service root:
cat data/integration-source-links.json | jq -r '."{Connector_Name}" // ."{connector}" // empty | .[]' > {connector_name}.txt
```

Verify the file is non-empty:
```bash
wc -l {connector_name}.txt
```

If the file is empty (0 lines), return FAILED with reason "No URLs extracted for {CONNECTOR}."

---

## Phase 1c: Run grace techspec (Path A)

```bash
# IMPORTANT: Switch to grace/ directory and activate virtualenv
# workdir: connector-service/grace
source .venv/bin/activate
cat ../{connector_name}.txt | grace techspec {Connector_Name} -e
```

**Wait for the `grace techspec` command to complete before proceeding.** This can take approximately 20 minutes. Do NOT interrupt or proceed until the techspec is fully generated.

**Critical**:
- The working directory MUST be `grace/` when running this command.
- The virtual environment MUST be activated first.
- The `-e` flag is required.

---

## Phase 1d: Verify tech spec output

After the chosen path finishes (and after the canonical-path copy above), verify the spec was created:

```bash
# From connector-service root:
find grace/rulesbook/codegen/references -iname "*{connector}*" | head -20
```

If no spec was generated, return FAILED.

## Rules

1. **No code generation** — this agent only produces the tech spec, nothing else.
2. **Verify before reporting success** — always confirm the file exists on disk.
3. **Clean up on failure** — if the chosen path fails, capture the error output and include it in the `REASON` field. Do NOT silently fall over from Path A to Path B mid-run: Phase 0 selects the path, and the chosen path either succeeds or fails.
4. **Idempotent** — if a tech spec already exists for this connector, report SUCCESS with the existing path (do not regenerate).
5. **URL source** — URLs come from `data/integration-source-links.json`, written by the Links Agent. Do NOT expect or require an integration details file.
6. **Same schema either way** — regardless of path, the produced spec must follow the section layout defined in `.skills/generate-tech-spec/references/techspec-generation-native.md`.
