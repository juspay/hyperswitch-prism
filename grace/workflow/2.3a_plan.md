# Codegen Planner Agent

You turn the canonical tech spec, the Hyperswitch (HS) scout and the baseline into **one implementation plan** for
every unit of **{CONNECTOR}** (stage S3). Codegen (`2.3b_codegen_unit.md`) implements plan items and nothing
else; codegen (`2.3b_codegen_unit.md`) transcribes §8 into the connector's committed `connector_specs/` JSON; review (`2.7_review.md`) checks the code against §5
and §7. Every decision that used to be improvised in codegen — contract changes, amount units, status arms,
guards per payment-method arm, HS parity — is made here, once, with evidence.

You write only the run dir. No repo edits, no builds, no network, no git write commands.

## RULES

1. **Write only `{RUN_DIR}/plan/`**: `plan.json`, `plan.md`, `plan.decisions.md` (and `plan.rev<N>.json` in AMEND).
   Write `<file>.tmp`, validate, then `mv`; `plan.md` is moved last. No `claimed.tsv` lines (no tree edits).
2. **Autonomous, no open questions.** Every unknown is resolved by the Phase 7 evidence order or the unit is marked
   `spec_gap`. Every judgement call is a row in `plan.decisions.md`
   (`| Decision | Options considered | Chosen | Why | Evidence / source |`).
3. **Evidence tokens** on every status row, amount unit, parity verdict, UNDECIDED choice and contract decision:
   `spec:<heading>` · `hs:<path>:<line>[-<line>]` (a range you opened) · `ucs:<path>:<line>` ·
   `proto:<file>#<Message>[.<field>]` · `run:<run-dir-relative path>#<id>` · `doc:<url>` (from `links/merged.json`).
   A grep hit on a type name is not evidence that a field is wired; open the call site.
4. **Oracle order**: tech spec and HS reference source, then proto. Existing UCS connector code is evidence of
   *pattern*, never of what the connector API does (it may be broken — §10). When spec and HS disagree on wire
   behaviour, follow HS unless the spec cites a newer API that supersedes it (then §5 `diverge`); record both and
   add a `verify_live` hook (§8).
5. **No contract change is decided outside §3.** Default is *no* proto/RPC/public-type change. 2.3b returns
   `PLAN_CONFLICT` for anything unplanned.
6. **Stable ids.** Plan items `P-<unit_fs>-NN` (`unit_fs` = unit with `/` → `__`; `P-foundation-NN`,
   `P-__hs__-NN`), guards `G-<unit_fs>-NN`, contracts `C-NN`, UNDECIDED `UD-NN`, invariants `INV-NN`. Never
   renumber or delete; withdrawn items get `"withdrawn": true`.
7. **No Rust in the plan** beyond names (structs, fields, enum variants, macro names). No plan item may create
   `#[cfg(test)]`, `#[test]`, `test.rs` or `tests.rs`.
8. **Secrets**: never copy a credential value. Sandbox trigger values are published test data with a citation;
   anything from creds is a `${ENV}` placeholder.
9. **Caps** live in `grace/workflow/2_connector.md` "## Caps": the orchestrator enforces the plan AMEND count; Phase 11
   reads `run.json .caps.validator_fix_iterations`.

10. **Context economy.** Every call re-sends everything this spawn has accumulated, so a lookup costs the whole pile, not the few KB it returns — in one measured run 96.6% of all tokens were context re-sent, and 21% of reads were of a file already in context. Two habits, both free: **(a)** issue independent lookups in **one** message — files you already know you need, a status and a diff, several `jq` projections — and never batch a call whose input depends on a previous result; **(b)** do not re-read a file you have already read in this spawn **unless something changed it since** — your own edit, another stage, a generator, a `make` target. That exception is load-bearing: a stale belief about a file you then edit costs far more than the re-read.

## Phase 0: Preconditions

Names used in every later block: `P` = `{RUN_DIR}/plan` (create it, delete stale `$P/*.tmp`), `C` = `{CONNECTOR}`,
`SRC` = `crates/integrations/connector-integration/src/connectors`.

  `preflight.json`, `links/merged.json` under `{RUN_DIR}`, non-empty → `JOINED <f> <sha1sum, first 12>`, else
  `ABSENT <f>`.
- `ALPHA` = `preflight.json .mode == "alpha"` (field absent or any other value → false). An alpha connector has no
  credentials, so every scenario §8 plans runs against a mock of the connector's own API
  (`{RUN_DIR}mock/mappings.json`, served by `grace/rulesbook/codegen/tools/mock_connector.py`; lifecycle in
  `2.6a_test_env.md`) instead of a sandbox. It changes Phase 9 and nothing else. Record it in `plan.json .alpha` and
  as a decision row. You never write `mock/` yourself (RULES 1): you decide its content in §8, 2.3b transcribes it.
- `HS_ROOT` / `HS_SHA` = `hs/scout.json` `.hs_repo_path` / `.hs_sha`, **only** when its `.hs_available == true`
  (file absent or `hs_available` not true → both empty).
- Record every `JOINED`/`ABSENT` line in `plan.json .inputs` and every `ABSENT` as a decision row ("proceed without").
  Baseline/capabilities are background joins: absent → §10 says "baseline not joined" and hooks carry
  `provisioned: "unknown"`. Scout absent → §5 and §9 say "no HS reference" (not a failure).
- Every HS read is pinned to the scouted commit (schema: `2.1a_hs_scout.md`), never the working tree (`__hs__` edits
  in the HS worktree shift lines): anchors via `git -C <hs_repo_path> show <hs_sha>:<file> | sed -n '<line_start>,<line_end>p'`,
  searches via `git -C <hs_repo_path> grep … <hs_sha> --`. `HS_ROOT`/`HS_SHA` empty → no HS reads; record it and
  write `hs_root`/`hs_sha` as `null`.
- `{MODE}=AMEND` → go to Phase 12 (`plan.json` missing → `FAILED`). `{MODE}=NEW` and `plan.md` exists → return
  `DONE`, REASON "plan exists".

1. **Normalize** each `{UNITS}` entry; keep the original as `requested`. Group aliases resolve through

   Exception: `IncomingWebhook` (aliases `webhook`, `webhooks`, any case) → unit `IncomingWebhook` (`markers:
   ["IncomingWebhook"]`), a non-marker trait unit with no `/PM` form: verify `pub trait IncomingWebhook` in
   `crates/types-traits/interfaces/src/connector_types.rs`,
   pattern `grace/rulesbook/codegen/guides/patterns/pattern_IncomingWebhook_flow.md`, declared = an
   `IncomingWebhook for` impl in `$SRC/$C.rs`.
2. **Dependencies** come from `.skills/add-connector-flow/SKILL.md` "## Flow Dependencies". Where the
   `.gracerules_add_flow` "## FLOW DEPENDENCIES" table disagrees (Refund, SetupMandate, PaymentMethodToken,
   IncomingWebhook, the token flows), the skill wins; flows absent from the skill table take the gracerules row.
   Conditional edges (Capture/Void/IncrementalAuthorization need manual-capture Authorize; Refund needs Capture only
   when the connector is manual-capture-only per spec) are resolved from the spec and recorded. A group's

3. **Resolve** each dependency: in the run → ordering edge; declared in `$SRC/$C.rs` → existing (a baseline FAIL on
   it goes to §10); neither → unit `blocked` (`missing dependency <Flow>`), dependents transitively `blocked`.
4. **impl_type** per 2.3 "## Phase 4a: Determine Implementation Type" → "### Decision Table" (`new_flow` |
   `flow_completion` | `payment_method_addition`); a group exists only if every marker is declared. A
   `flow_completion` unit with no gap against spec, §5 and §10 is `no_op` with reason.

## Phase 3a: 3DS call map (§4a) — only when a `ThreeDS` unit is planned

Skip this phase entirely when no `ThreeDS` unit is in `plan.json .order[]` with `status: "planned"`;
leave `three_ds` null. Otherwise it is mandatory, and `plan.json .three_ds` is where the leg count is
decided — not in codegen.

Read `grace/rulesbook/codegen/.gracerules_add_flow` `## FLOW-GROUP MAP (Authoritative)` and follow the
**LEG-COUNT PROCEDURE** there, then `guides/patterns/pattern_authentication_dispatch.md`. Both are
required reading before you write §4a.

1. From `{TECHSPEC_PATH}` `## API Call Sequences` `### ThreeDS`, list every HTTP call a 3DS card
   payment makes, in order, into `three_ds.calls[]`. Each call carries `charges` and
   `returns_redirect` copied from the spec's `Charges:` / `Redirect:` annotations, and `charges: true`
   must carry a verbatim `charge_evidence` quote.
2. Apply LEG-COUNT Step 1 and Step 2: exactly one call charges, and it maps to **`Authorize`**. If the
   same URL appears more than once, the charging call is the **last** occurrence.
3. Apply Step 3 to the calls before it, filling `maps_to` and `purpose`. Set `legs_used[]` to the
   markers actually selected — commonly one or two, sometimes none.
4. Cite the comparable shape from `pattern_postauthenticate.md` Appendix A (the per-connector leg
   roster) in `doc_refs[]`, or record "no comparable shape" there.
5. Fill `hs_reference` from `{RUN_DIR}hs/scout.json`: which flows Hyperswitch uses for this connector
   and where it puts the charge. **HS's `CompleteAuthorize` is UCS's `Authorize`, not UCS's
   `PostAuthenticate`** — if your mapping disagrees with HS about which call moves money, resolve it
   before writing the plan, and record the resolution in `plan.decisions.md`.
6. A marker not in `legs_used[]` stays in the connector's `not_implemented:`/`not_supported:` list.
   Add no §4 items for it.

`PostAuthenticate` may never be the charging call: that arm of the composite loop has no break, so
`Authorize` runs after it and charges a second time. The Phase 11 validator enforces this and will
fail the plan.

## Phase 4: Contract decisions (§3)

A row is required for any of: a change to `crates/types-traits/grpc-api-types/proto/*.proto` (field, enum value,
message, rpc); a unit served by a different RPC than `flow_to_suites` maps, or a flow that needs more caller RPCs
than today (1 → 2); a field or signature change in `crates/types-traits/domain_types/src/` or
`crates/types-traits/interfaces/src/`; an edit to code other connectors run through (`$SRC/macros.rs`,
`crates/grpc-server/`, `crates/internal/composite-service/`).

1. Prefer an existing carrier (existing proto field, `connector_feature_data`, metadata). Adopt a change only when
   no existing contract can express a spec requirement; never change an existing RPC's behaviour for other connectors.
2. **Caller analysis** for every adopted change, per symbol (message, rpc, field, type): whole-word search for it in
   `crates/grpc-server`, `crates/internal/composite-service`, `crates/ffi`, `crates/internal/field-probe`,
   `crates/internal/integration-tests/src/harness`, `crates/types-traits` and `sdk` (excluding `target` and
   `node_modules`); and, when `HS_SHA` is set, in HS pinned at it — `git -C "$HS_ROOT" grep -nw "$SYM" "$HS_SHA" --
   'crates/*.rs'` plus how HS consumes the proto (`grpc-api-types` / `rust-grpc-client` / `unified` in its
   `crates/*/Cargo.toml`; record the hit).
   Each hit → `callers[] {repo ucs|hs, path, line, impact none|compatible|breaking|regenerate}`. `breaking` in UCS →
   a plan item in the owning unit; in HS → a §9 item; `regenerate` (SDK/FFI generated files) → noted for finalize
   (`make generate`). A change with a `breaking` caller that cannot be fixed in this run → `reject`, and the unit
   records the alternative or becomes `blocked`.
3. **HS client compatibility.** A §9 `hs_changes[]` item builds against the UCS client version Hyperswitch
   *pins*, not this working tree. Read the pin from `{HS_REPO_PATH}/crates/router/Cargo.toml`
   (`unified-connector-service-client = { git = "…/connector-service", tag = "<tag>", … }`; the same tag is in
   `crates/hyperswitch_interfaces/` and `crates/external_services/`) and the resolved commit from
   `{HS_REPO_PATH}/Cargo.lock` (`name = "grpc-api-types"` → `source = git+…?tag=<tag>#<sha>`). Every proto field,
   enum value and message a §9 item names must exist **at that tag** — `HS_SHA` pins HS's own source, not its UCS
   client. It does not exist there → the §9 item also carries the pin bump, or the HS change waits for the next
   tag; record which, with the tag as evidence. Planning fields that are absent at the pinned tag costs a
   `PLAN_CONFLICT` round and a full plan revision.

## Phase 6: HS parity (§5)

For every scout parity item of an in-scope unit, open its anchor and classify exactly once:
`match` (cite the implementing `items`) | `diverge` (reason: spec contradicts HS, cite; contract rejected in §3, cite
`C-NN`; sandbox/product difference) | `out_of_scope` (reason names the flow/payment method not in `{UNITS}`). Add a row
(`parity_id: PL-NN`) for any HS capability you find in the anchored ranges that the scout did not list — mandate
revoke, network-token arms, first-recurring flags, 3DS on every card carrier, decline → failed-status mapping,
capture-method refusals, id forms.

The scout's list is a starting set, not the parity surface. When `hs/scout.json .hs_available` is true and HS
implements this connector, open `$HS_ROOT/crates/hyperswitch_connectors/src/connectors/$C.rs` and
`$C/transformers.rs` (pinned at `HS_SHA`, Phase 0) and compare **five axes** for every in-scope unit, each
producing rows even where the scout listed nothing:

| Axis | Compare |
|---|---|
| Request fields | every field HS puts on the wire per flow and arm vs. §4 `request_structs[]` — a field HS sends and we omit is a divergence, not an absence |
| Status mapping | HS's status enum and match arms vs. §4 `status_map[]`, including its unknown/other arm |
| Error mapping | the trigger predicate (which responses are errors), code/message fields, and the `attempt_status` HS sets vs. §4 `error` |
| Amount handling | HS's unit and converter, both directions, vs. §4 `amount` |
| Mandate / NTID | CIT vs. MIT markers, stored-credential token binding, network transaction id and scheme details vs. the mandate arms in §4 |

Each divergence is one of exactly two things: a **planned fix** (`verdict: diverge`, `items[]` non-empty), or an
**intentional difference** carrying both an `hs:` anchor and a `spec:`/`doc:` citation for why ours is right.
"Not looked at" is not a verdict. This is the comparison a post-hoc parity review performs; running it here is
what keeps it out of the test rounds. Theme-shaped findings (masking, typed amounts, inconclusive syncs, error
context) also belong in §4 `review_themes[]` — see `grace/rulesbook/codegen/guides/review_themes.md`.

## Phase 7: UNDECIDED resolutions (§6)

Inputs: `spec:## UNDECIDED Fields`, fields Phase 5 could not categorize, analysis.md multi-source fields. Resolve
each in this order and stop at the first that decides:
1. HS reference behaviour (`hs:` anchor).
2. Spec or doc text (`spec:` / `doc:`).
3. Proto contract: if the RPC request has no field for it, it cannot be USER_PROVIDED by the caller.
4. A UCS connector of the same pattern (`ucs:` anchor).
5. None decides → the fail-closed option (require it; refuse via a guard when absent; never default or empty) with
   `verify_live: true`, which adds a §8 hook.

Row: `{id, unit, field, options[], chosen, evidence[], verify_live}`.

## Phase 9: Test spec (§8)

One entry per planned unit. **§8 is the oracle and codegen is only the transcriber**: every expected
value here cites the techspec, the HS reference or the proto contract — never the code this run is
about to write. 2.3b copies §8 into the connector's committed
`crates/internal/integration-tests/src/connector_specs/<connector>/` files verbatim; it invents
nothing. That is what keeps "no run may write the code that judges its own code" true while the test
data lives in the same PR as the code.

**Confirm the mechanism before you plan the hook.** Open the harness and check that what the hook assumes
exists; do not infer it from another connector's JSON. Connector-specific scenario resolution:
`merge_connector_specific_scenarios` / `CONNECTOR_SCENARIOS_FILE` in
`crates/internal/integration-tests/src/harness/scenario_loader.rs`, called from `scenario_api.rs`. Suite
dependencies and their `dependency_scope`: `harness/scenario_types.rs`, dispatched in `harness/scenario_api.rs`.
`context_map` semantics: `ContextMap` in `harness/scenario_types.rs` and its `apply_context_map` call site.
Connector overrides: `harness/connector_override/<connector>.rs` and its registration. A hook whose mechanism is
not in that code is a `static:` / `cypress:` `harness_ref` or an escalation — never an optimistic §8 entry.
Assuming capability the harness does not have costs a plan revision per discovery, in the middle of the test loop.

**Choosing where a case goes** (first match wins; the bias is to reuse the global baseline):

| The case … | Goes in | §8 field |
|---|---|---|
| already exists globally and its assertions hold for this connector | nothing — just declare the suite | `global_scenarios[]` |
| exists globally but needs a connector-specific **input** (test card, metadata blob, 3DS lever) | `override.json` `grpc_req` | `overrides[]` |
| exists globally but its **expected outcome** differs for documented reasons | `override.json` `assert` | `overrides[]` |
| is a dimension only this connector has | `connector_specific_scenarios.json` | `connector_scenarios[]` |
| genuinely does not apply | `specs.json` `unsupported_scenarios` | `waivers[]` |
| cannot be expressed in the harness at all | a static gate, or Cypress | `static:`/`cypress:` in `harness_ref` |
| ought to be global (applies to ≥2 connectors) | propose it; a connector run may not edit `global_suites/` | `global_scenario_proposal[]` |

| Field | Content |
|---|---|
| `produces[]` | `{name, response_path, form, evidence}` — every id another flow, HS or a webhook consumes (transaction, refund, mandate, customer, token, `connector_feature_data`); `form` names the exact id form (e.g. global vs legacy id) |

### Alpha mode (`ALPHA` true) — the mock is planned here, not improvised at test time

`ALPHA` false → every `mock_exchanges[]` is `[]` and the rest of this subsection does not apply.

There are no credentials, so no request in this run reaches the connector. Every scenario above is answered by
`{RUN_DIR}mock/mappings.json`. That file is run-dir evidence: **never committed, never in `claimed.tsv`** — and its
content is decided in this phase, because this is the phase that already has the spec's documented examples open.
2.3b writes its unit's slice of it exactly as it transcribes `connector_specs/`, and invents nothing there either.

One `mock_exchanges[]` entry per scenario × connector call, in the mappings route shape (the tool's schema, plus
`scenario_ref`; 2.3b copies the route fields and drops it):

| Field | Content |
|---|---|
| `id` | route id, `<unit_fs>.<scenario>.<call>` — stable, and unique across the whole run: one file serves every unit |
| `scenario_ref` | the §8 hook this exchange serves: `<suite>/<scenario>`, or the `harness_ref` of the `status_arms[]`/`declines[]`/`negatives[]` row |
| `match` | the request predicate that identifies **this** exchange and no other: `{method, path (exact, or `/regex/`), query (subset), body_contains (recursive subset)}`. It cites the §4 `calls[]` row and the request field it keys on — the discriminator must be a field §4 says we send, not a field you hope we send |
| `response` | `{status, headers, body}` **copied from a documented example** — the spec's or the docs' example response for this call and this outcome, verbatim but for `{{req:<dot.path>}}` / `{{uuid}}` / `{{now}}` / `{{query:<k>}}` templates where the example carried a value that echoes the request |
| `cite` | `spec:<section> -> <the example the body was copied from>` (or `doc:<url> -> <example>`). The tool refuses to serve an uncited route; 2.3b enforces it before returning |
| `times` | `null`, or `<n>` when the exchange is part of a sequence: a PSync that is PENDING once and then CHARGED is **two** entries on the same `match`, the first with `times: 1`. Plan the sequence here — the order of `routes[]` is the order they serve |

**The anti-self-grading rule, stated once so it is not re-derived per unit.** A scenario's assertions come from the
**documented semantics** of the flow; the mock's response body comes from a **documented example**. Both cite the
docs, and they cite them independently — that is what makes the pair a test. What is forbidden is inventing a
response body and then asserting the value you invented: that is a test grading the run against itself, and it is
exactly what the no-self-grading rule of `grace/workflow/1_orchestrator.md` RULE 3 exists to prevent. It is easier
to do here than anywhere else in the run, because both halves are being written by the same agent in the same hour.
A flow whose documentation carries **no example response** cannot be mock-tested honestly: record it as unprovable
in alpha mode — a `waivers[]` row or an `unprovokable_reason`, citing the absence — rather than fabricating a body.
An unmatched request gets the mappings' `default_response` (501): that is a **missing** exchange, not a pass, and a
scenario whose only route is the default is not planned.

**What alpha changes about the rest of §8.** A live-only assertion is not provable against a mock and must not be
written as if it were: a real connector-issued id (beyond the form the example shows), real settlement or capture
of funds, a real decline or risk code, a real webhook the connector originates, anything with `provisioned` from
`capabilities.json`. Those rows carry an `unprovokable_reason` beginning `alpha:` (e.g.
`alpha: no credentials — settlement is not observable against the mock`) with the `spec:`/`doc:` citation of what
would be asserted live, and they go into `verify_live[]` for the day credentials arrive. Do not silently weaken an
assertion to whatever the mock happens to return. `sandbox_triggers[]` cannot be probed in alpha: each one is
`provisioned: "unknown"`, its `value` is the documented test value with its citation, and it is a `verify_live[]`
entry. Everything a mock **does** prove — the request shape the connector module builds, the response parser, the
status map, the error map and the guards executing on a documented body — is planned exactly as it is for a live
run, and the same `connector_specs/` scenarios run unchanged against the sandbox once credentials exist.

   | "§8 \($u): alpha run, scenarios planned, no mock_exchanges — every one of them would get the 501 default_response"),
 ($p | select(.alpha) | .test_hooks[] | .unit as $u | .mock_exchanges[]?
   | select(((.cite // "") | test("^(spec|doc):.+ -> .+") | not) or ((.response.body // null) == null)
            or ((.scenario_ref // "") == ""))
   | "§8 \($u): mock exchange \(.id) has no scenario_ref, no response body, or a cite that is not \"<spec|doc>:<section> -> <documented example>\" — an uncited body is a value this run invented"),
 ($p | select(.alpha) | [.test_hooks[].mock_exchanges[]?.id] | group_by(.)[] | select(length > 1)
   | "§8 duplicate mock exchange id \(.[0]) — mock/mappings.json is one file for the whole run"),
 ($p.test_hooks[] | .unit as $u | .waivers[]?
   | select((.reason // "") | test("^(PM_NOT_OFFERED|SANDBOX_NOT_PROVISIONED|FLOW_NOT_IN_SCOPE|CONNECTOR_API_LACKS): .+ [-\u2014] .+") | not)
   | "§8 \($u): waiver \(.suite)/\(.scenario) reason does not parse as \"<CLASS>: <evidence> - <line>\""),
 ($p.undecided[]? | select((.chosen // "") == "" or ((.evidence // []) | length) == 0) | "§6 \(.id) unresolved"),
 ($scout[0].units[]?.parity[]?.id as $id | select(([$p.hs_parity[]? | select(.parity_id == $id)] | length) != 1)
   | "§5 parity \($id) not classified exactly once"),
 ($p.hs_parity[]? | select((.verdict | IN("match", "diverge", "out_of_scope") | not)
   or (.verdict != "match" and ((.reason // "") == "")) or (.verdict == "match" and ((.items // []) | length) == 0))
   | "§5 \(.parity_id) invalid verdict/reason/items"),
 ($scout[0].hs_changes_required[]?.id as $id | select(any($p.hs_changes[]?; .scout_ref == $id) | not)
   | "§9 scout change \($id) has no __hs__ item"),
 ($p.contracts[]? | select(.decision == "adopt" and ((.callers // []) | length) == 0) | "§3 \(.id) adopted without callers")
] | .[]' "$P/plan.json.tmp"

## Phase 12: AMEND

1. `jq '{brief_id, bug_ids, units, origin, finding, evidence, required_change, fix, do_not_touch, upstream_no_change, amend_targets, withdraw}' {AMEND_BRIEF}`.
   Scope = `units` ∪ `.amend_targets[]? | select(.agent_file == "2.3a_plan.md") | .scope.plan_items[]?` ∪ plan items named
   by `fix[]` (by id, or by `file`+line range in `plan.md`/`plan.json`, or by a code `file` that an item targets). `do_not_touch` is never edited. Regeneration from scratch is forbidden.
2. `REV=$(jq .rev "$P/plan.json"); cp "$P/plan.json" "$P/plan.rev$REV.json"; for f in plan.json plan.md plan.decisions.md; do cp "$P/$f" "$P/$f.tmp"; done`;
   edit the `.tmp` copies only; `rev` + 1.
3. Edit only scoped items and tables. New items take the next free `NN`; removed items get `withdrawn: true`. A new
   proto/RPC/public change runs Phase 4 for it. A withdraw brief (boolean `withdraw == true`) sets the unit's `order.status` to
   `withdrawn` and adds items that restore `not_implemented` and drop its suites from `specs.json`, unless an item is
   `uses`d by another unit (then keep it and record why). It also sets `withdrawn: true` on every §9 `hs_changes[]`
   item whose `flows_unblocked` are now all withdrawn units — otherwise 2.8 Phase 8 raises a Hyperswitch PR enabling a
   flow UCS no longer implements. A change that needs a unit not in `{UNITS}` → `BLOCKED`; one
   that needs a spec fact the spec lacks → `SPEC_GAP`.
4. The plan already satisfies `required_change` → `NO_CHANGE` (append an Amendments row with the evidence; no other edit).
5. Compute changed units and test-hook changes:
   ```bash
   jq -nc --slurpfile a "$P/plan.rev$REV.json" --slurpfile b "$P/plan.json.tmp" '
   def one($p; $k; $u): [$p[$k][]? | select(.unit == $u)][0];
   $a[0] as $A | $b[0] as $B | ([$A.order[].unit, $B.order[].unit] | unique) as $all
   | {changed_units: ([$all[] as $u | select(one($A;"units";$u) != one($B;"units";$u) or one($A;"order";$u) != one($B;"order";$u)) | $u]
        + (if $A.hs_changes != $B.hs_changes then ["__hs__"] else [] end)
        + (if $A.foundation != $B.foundation then [$B.order[0].unit] else [] end) | unique),
      test_hooks_changed: [$all[] as $u | select(one($A;"test_hooks";$u) != one($B;"test_hooks";$u)) | $u]}'
   ```
6. Append `amendments[] {at, agent "2.3a_plan", brief_id, units (= step 5's `changed_units`, the same list the
   return block's `CHANGED_UNITS` carries — not the brief's `units`), items, test_hooks_changed, summary}`, the matching
   `## Amendments` row, and decision rows; run Phase 11 validation on the whole plan; `mv` as in Phase 11.
