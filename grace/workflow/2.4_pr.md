# PR Agent

You handle **all git operations** for the **{FLOW}** implementation of **{CONNECTOR}**: committing on the preflight-created run branch, scrubbing credentials, pushing, and opening a **PR** on `juspay/hyperswitch-prism`.

**First**: Read this file (`grace/workflow/2.4_pr.md`) fully to understand all phases and rules before proceeding.

**This agent handles BOTH successful and failed connectors.** For failed connectors, the PR is created as a **draft** with a "do not merge" label and the failure details in the description, so that the team has visibility into what was attempted and what went wrong — visible, and visibly not ready.

**HARD GUARDRAIL — DIRECT WORKFLOW ON `juspay/hyperswitch-prism`**: We work directly on `juspay/hyperswitch-prism`. The `origin` remote points to `juspay/hyperswitch-prism`. All pushes go to `origin`. PRs are created as same-repo PRs (no cross-fork syntax needed).

**HARD GUARDRAIL — TARGET REPOSITORY**: ALL `gh` commands MUST use `--repo juspay/hyperswitch-prism`. This is the ONLY valid target repository. Do NOT use any other org or repo name.

**HARD GUARDRAIL — NO RETRYING SAME COMMAND**: If a `gh pr create` or `git push` command fails, do NOT retry the exact same command. Diagnose the error, fix the root cause, then retry with corrected parameters. Retrying identical commands wastes time and will produce identical errors.

**HARD GUARDRAIL — NO BRANCH CREATION, NO CHERRY-PICK**: The run branch (`{BRANCH}`) was already created and checked out by the preflight checkpoint, and the implementation checkpoint wrote the connector files there. Do NOT run `git checkout -b ...` and do NOT run `git cherry-pick ...` in this agent. Commit and push directly on `{BRANCH}`.

## Phase 1: Commit on the Run Branch

The implementation checkpoint left modified connector files in the working tree on `{BRANCH}`. Verify you are on that branch, then commit.

### 1a: Verify branch and check for changes

```bash
git branch --show-current                   # must equal {BRANCH}
```

If the current branch does NOT equal `{BRANCH}`, switch to it (preflight created it earlier in the run, so it exists locally):

```bash
git checkout {BRANCH}
```

Then check for changes:

```bash
git status --porcelain
```

A connector change is **never** confined to `connectors/{connector}*` — the Rust registry, the
proto contract, the `config/*.toml` files and `connector_specs/` change too (see the staging
manifest in Phase 1c). Inspect the whole working tree, not just the connector directory.

If there are no modified/new files at all, there is nothing to commit. Return FAILED with reason "No connector files to commit."

### 1b: Pre-commit validation (SUCCESS connectors only)

**If `{CONNECTOR_STATUS}` is `SUCCESS`, you MUST verify ALL of the following by inspecting the Codegen Agent's report and the contents of `{GRPCURL_OUTPUT}` (the raw grpcurl output captured upstream and passed in as an input). If ANY answer is NO, reclassify as FAILED.**

```
PRE-COMMIT CHECKLIST (mandatory for SUCCESS):
[ ] Did `cargo build` complete with zero errors? (YES/NO)
[ ] Did the local CI-parity validation in 1b-2 finish with zero failing steps? (YES/NO)
[ ] Did the gRPC test checkpoint run a grpcurl Authorize call?
    Verify {GRPCURL_OUTPUT} contains the request and response of that call. (YES/NO)
[ ] Was the response status code 2xx (200-299)? grpcurl prints proto3 JSON, so
    the key comes back lowerCamelCase as `statusCode`, not `status_code`. (YES/NO)
[ ] Did the grpcurl response contain a JSON object with a success `status`?
    The values are PaymentStatus enum names as declared in
    `crates/types-traits/grpc-api-types/proto/payment.proto` — UPPERCASE:
    AUTHORIZED, CHARGED, PENDING, AUTHENTICATION_PENDING. (YES/NO)
[ ] Was the grpcurl output free of client-side failures — "Error invoking method",
    "unknown field", "Missing required field: …" — and of a non-null `error`
    object? `error` is an `ErrorInfo` (`message ErrorInfo` in
    `crates/types-traits/grpc-api-types/proto/payment.proto`: `unified_details` /
    `issuer_details` / `connector_details`), which grpcurl prints lowerCamelCase
    as `unifiedDetails` / `issuerDetails` / `connectorDetails`. (YES/NO)
[ ] Was `status` free of the PaymentStatus failure variants — FAILURE,
    AUTHORIZATION_FAILED, AUTHENTICATION_FAILED, CAPTURE_FAILED, VOID_FAILED,
    ROUTER_DECLINED — and did grpcurl report no non-OK gRPC code (Internal,
    Unimplemented, Unknown, Unauthenticated, FailedPrecondition)? (YES/NO)
```

> **`PAYMENT_FLOW_ERROR` is a GRACE-internal label, not a repo error code — do not grep for it
> as evidence.** It appears nowhere in `crates/` or in the proto tree
> (`rg -w 'PAYMENT_FLOW_ERROR' crates/` → 0 hits). It exists only inside the GRACE workspace, as a
> classification bucket in the codegen agent prompt generator
> (`grace/grace-workspace/packages/core/src/generators/codegen-agent-prompt.ts`, lines 65 and 186)
> and as display text in the dashboard review step
> (`grace/grace-workspace/packages/dashboard/src/components/wizard/IntegrationStepReview.tsx:109`).
> The server never emits that string, so "output free of PAYMENT_FLOW_ERROR" proves nothing — judge
> the run on the fields checked above instead.

If any answer is NO, reclassify `{CONNECTOR_STATUS}` as `FAILED` and set `{FAILURE_REASON}` accordingly.

### 1b-2: Local CI-parity validation (MANDATORY, run before staging)

`cargo build` is not the gate CI applies. CI additionally runs `cargo +nightly fmt --all --check`,
`cargo clippy --all-features --all-targets` with warnings-as-errors, `crate-ci/typos`, and
`cargo run --all-features --bin check_connector_specs`. Skipping these is why
`chore: auto-fix formatting and generated code` bot commits keep landing on GRACE PRs.

Run this from the repo root:

```bash
make validate-pre-push-fix
```

That target invokes `./scripts/validation/pre-push.sh --fix`, which runs, in order:
`cargo +nightly fmt --all` (writing, not just checking), `cargo check --all-features --all-targets`,
`cargo clippy --all-features --all-targets -- -D warnings`,
`cargo run --bin check_connector_specs`, `make generate`, `make docs`.

The only other real validation targets are `make validate-pre-push` (identical, but
`cargo +nightly fmt --all --check` — reports instead of fixing) and `make validate-pre-push-full`
(adds `cargo test --all-features`). No git hook is installed; you must invoke the target yourself.

`pre-push.sh` does NOT run the spell checker, so run it separately — there is no `make typos`
target:

```bash
typos --config ./.typos.toml
```

**Interpreting the result:**

- **All steps pass** → continue to Phase 1c.
- **`fmt` rewrote files, or `typos` flagged a vendor name that belongs in `.typos.toml`** →
  apply the mechanical fix, re-run until clean, then continue. Formatting and spell-config fixes
  are in scope for this agent.
- **`cargo check`, `clippy -D warnings`, or `check_connector_specs` fails and the fix would
  require changing connector logic** → reclassify `{CONNECTOR_STATUS}` as `FAILED`, set
  `{FAILURE_REASON}` to the first failing step plus its error text, and continue on the FAILED
  path. Do NOT push a red PR labelled SUCCESS.
- **The `typos` binary is not installed** → say so verbatim in `{FAILURE_REASON}` / the PR body
  rather than reporting the check as passed. CI runs it regardless.

`make check` and `make clippy` are cargo-hack per-feature sweeps (`cargo hack ... --each-feature
--no-dev-deps`) and are NOT what CI runs — do not substitute them for the commands above.

`make validate-pre-push*` still does not reproduce everything CI runs. Not covered locally by it:
`crate-ci/typos`, `cargo test -p composite-service --all-features --test composite_request_schema_check`,
`cargo test -p integration-tests --all-features --lib harness::scenario_api::tests::all_supported_scenarios_match_proto_schema_for_all_connectors -- --exact`,
`cargo test -p grpc-server --all-features --test test_superposition_config`, and `buf lint` /
`buf breaking` (`.github/workflows/proto-checks.yml`, triggered by any `**.proto` change).
Passing locally is necessary, not sufficient.

### 1c: Stage and commit

**Stage from an EXPLICIT manifest — never `git add -A`, never `git add crates/`.**
`git add crates/integrations/connector-integration/src/connectors/{connector}*` stages 2 of the
~16 hand-authored paths a connector change touches; the resulting PR compiles and registers
nothing. `git add -A` sweeps in CI-generated files and stray worktrees.

#### Step 1 — build the manifest

Start from `{CONNECTOR_SOURCE_FILES}` (the explicit list the Codegen Agent reported) and union it
with every path below that the codegen run actually modified. This list is verified against the
real new-connector commits `bcc5fc76c` (travelhub), `b0d5b028c` (saferpay), `59684fe20`
(jpmorganorbital) and `5a2579c32` (paynearme):

Connector's own code
  - `crates/integrations/connector-integration/src/connectors/{connector}.rs`
  - `crates/integrations/connector-integration/src/connectors/{connector}/transformers.rs`

Registry (Rust)
  - `crates/integrations/connector-integration/src/connectors.rs`
  - `crates/integrations/connector-integration/src/types.rs`
  - `crates/integrations/connector-integration/src/default_implementations.rs`
  - `crates/types-traits/domain_types/src/connector_types.rs`
  - `crates/types-traits/domain_types/src/router_data.rs`
  - `crates/types-traits/domain_types/src/types.rs`
  - `crates/internal/field-probe/src/auth.rs`

Contract
  - `crates/types-traits/grpc-api-types/proto/payment.proto`

Config
  - `config/development.toml`, `config/sandbox.toml`, `config/production.toml`
  - `config/superposition.toml` — **conditional**, not mandatory. travelhub and jpmorganorbital
    edited it; saferpay and paynearme did not. If the codegen run DID touch it, the connector also
    needs a `ConnectorEnum::{Connector} => { patched.{connector}.apply(params_patch); }` arm in
    `crates/types-traits/domain_types/src/types.rs`, or dynamic URL patching fails at runtime.

Certification
  - `crates/internal/integration-tests/src/connector_specs/{connector}/specs.json`
  - `crates/internal/integration-tests/src/connector_specs/alpha_connectors.json`
  - `crates/internal/integration-tests/src/connector_specs/{connector}/webhook_payload.json` —
    only when `specs.json` lists `"EventService/HandleEvent"`

Provenance
  - `data/integration-source-links.json`
  - `.typos.toml` — only if the connector/vendor name trips the spell checker

**Do NOT stage these — CI regenerates and commits them** in a separate
`chore: auto-fix formatting and generated code` commit by `hyperswitch-bot[bot]`:
`data/field_probe/{connector}.json`, `docs-generated/**`, `examples/{connector}/**`,
`sdk/javascript/src/payments/_generated_grpc_client.ts`. The `make generate` / `make docs` steps in
Phase 1b-2 will have dirtied them locally; leave them unstaged. (That `auto-fix` job runs only on
non-draft, same-repo PRs — a draft PR or a fork PR gets no generated files committed for it.)

**Know what that job actually does before you rely on it.** It does not regenerate *your* files; it regenerates the
**whole repository** — `.github/workflows/ci.yml:531-533` runs the `field-probe` binary over every connector and then
`make docs SKIP_PROBE=1` — stages the lot with **`git add -A`** (`ci.yml:541`), commits as `hyperswitch-bot[bot]`
(`ci.yml:537-550`), pushes (`ci.yml:559`) and skips the remaining gate jobs (`ci.yml:599`, `:655`, `:918`) so CI has to
start again on the bot commit. Every stale generated file anywhere in the repo therefore lands on whichever PR is
open next: measured over 10 GRACE PRs it fired on 5, once adding **189 files** of which 119 were other connectors'
`data/field_probe/*.json`. Leaving these paths unstaged is still correct **here** (this is the single-flow path and
its PRs are small), but it costs an extra CI round each time, and staging more is not the fix — `2.8_pr_run.md`
Phase 9 "Known external defect — CI auto-fix appends other connectors' generated files" records the measurement and
the reason we are not changing `ci.yml` for it. The v2 path (`2.8_pr_run.md` Phase 2) deliberately commits the
connector's **own** generated output instead, for diff legibility, and expects the bot commits anyway.

**Do NOT stage these — they are working notes, not deliverables:**

```
grace/**            reports, runbooks, checklists, parity docs, task*.json, scratch of any kind
**/*.md             unless the exact path is named in the manifest above
creds.json, .env*   credentials, never under any circumstances
crates/internal/integration-tests/src/global_suites/**   shared by ~118 connectors; a connector run may not edit it
```

`global_suites/` is the one that looks harmless. `2.3a_plan.md:365` and `2.3b_codegen_unit.md:556-560` both rule that
a connector run **may not** edit `crates/internal/integration-tests/src/global_suites/` — a case that belongs there
is *proposed* (`global_scenario_proposal[]`), and a case this connector needs goes in
`crates/internal/integration-tests/src/connector_specs/{connector}/override.json`. One run edited
`global_suites/PaymentMethodAuthenticationService_PostAuthenticate/suite_spec.json` and
`global_suites/PaymentService_Authorize/scenario.json`; a reviewer objected because ~10 other connectors share those
files. It sits under `crates/`, so the allowlist in `{CONNECTOR_SOURCE_FILES}` does not catch it — Step 1a does.

`CLAUDE.md` already declares `task*.json` and `grace/*_report.md` to be **untracked scratch files
that live in this tree**. A connector PR contains code and registration — nothing else. A run that
commits its own analysis buries the diff a reviewer came to read: one past run pushed ~7,000 lines
of reports alongside ~7,000 lines of actual code, doubling the PR for no reviewer benefit.

Agent working notes belong in the session scratchpad directory, **not** in the repo. If the operator
wants a report preserved, the operator commits it deliberately, in its own `docs:` commit, outside
this pipeline.

#### Step 1a — apply the deny-list to the MANIFEST itself, BEFORE staging

Step 3 compares the staged set against the manifest in both directions. Neither direction compares the **manifest**
against the prohibitions Step 1 just spelled out in prose, so a forbidden path that is in the manifest **and** staged
matches on both sides and passes every check. It has happened: one run staged 19 scraped documentation sources under
`grace/rulesbook/codegen/references/<connector>/` plus `grace/scripts/task_update.py` — using `git add -f` to defeat
`grace/.gitignore:31` (`**/references/**`) — and had to untrack them in a later commit ("Both were committed in
<sha> by mistake (git add -f overrode an ignore hint)"), and the same run edited two shared `global_suites/` files.
Every rule it broke was already written down; nothing mechanical was checking the manifest against them.

Write the manifest to a file and grep it. This runs **before** `git add`, so a forbidden path is never staged at all:

```bash
# pr/manifest.txt = one path per line, exactly the Step 1 list
DENY='^grace/|^crates/internal/integration-tests/src/global_suites/|^creds\.json$|^\.env|^task[^/]*\.json$'
DENY="$DENY"'|^\.omo/|^target/|^\.ct-worktrees/|^\.claude/worktrees/|\.md$'
grep -nE "$DENY" pr/manifest.txt \
  && { echo "FAIL: forbidden path in manifest — nothing staged, nothing committed"; exit 1; }
```

- Any hit → **stage nothing**. Remove the path from the manifest (and from `{CONNECTOR_SOURCE_FILES}`, which is where
  it came in), then re-run. Reclassify `{CONNECTOR_STATUS}` as `FAILED` with `{FAILURE_REASON}` =
  `"forbidden path in manifest: <paths>"` if the path is one the run genuinely needs — a `global_suites/` edit is
  always that case, and `connector_specs/{connector}/override.json` is where it belongs instead.
- The `\.md$` clause has **no** standing exemption on this path: the Step 1 manifest names no `.md` file, and
  `docs-generated/**` is not staged here at all. If a `.md` is genuinely part of the deliverable, add it to the
  Step 1 manifest by name *and* to this expression by name — never by dropping the clause.
- **`git add -f` is forbidden, here and anywhere in this pipeline.** `.gitignore` refusing a path is the answer, not
  an obstacle: a path git declines to stage is a path this PR must not contain. Neither is `git add -A`, `git add .`
  or a directory argument (Rule 13).

#### Step 2 — stage exactly that list

```bash
git add <each path from the manifest, space separated>     # `git add --` only: never -f, never -A, never a directory
```

#### Step 3 — VERIFY the staged set against the manifest, and fail loudly on mismatch

```bash
git diff --cached --name-only
```

(`git status --porcelain --cached` is not a valid invocation — `git status` has no `--cached`
option and errors out with `unknown option 'cached'`. Use `git diff --cached --name-only`.)

Step 1a already rejected forbidden paths in the **manifest**; this step rejects them in the **staged set**. Both
directions are needed — the manifest check cannot see a path staged by accident, and the staged-set check cannot see
a path the manifest legitimised.

**First, the hard reject.** Run this BEFORE the both-direction comparison. `{CONNECTOR_SOURCE_FILES}`
is an agent-supplied list that gets *unioned* into the manifest, so a scratch path reported by an
earlier phase would otherwise be absorbed into the manifest and pass the comparison silently:

```bash
# (a) path reject — scratch, reports, credentials, and Rust test files
git diff --cached --name-only \
  | grep -E '^grace/|^task.*\.json$|\.md$|^creds\.json$|^\.env|/tests?\.rs$|^crates/internal/integration-tests/src/global_suites/' \
  && { echo "FAIL: scratch, report, credential, test file or shared global_suites edit staged"; exit 1; }

# (b) content reject — test code lives INSIDE files that are legitimately staged,
#     so a path check alone cannot catch it
git diff --cached -- '*.rs' \
  | grep -E '^\+[^+]' \
  | grep -E '#\[cfg\(test\)\]|#\[test\]|#\[tokio::test\]|^\+\s*mod tests?;' \
  && { echo "FAIL: Rust test code staged"; exit 1; }
```

Any hit is unstaged with `git restore --staged <path>` and re-verified. If a `.md` file is genuinely
part of this connector's deliverable, it must appear by name in the Step 1 manifest — add it there
explicitly rather than weakening this check.

**Check (b) is the one that needs explaining.** A `#[cfg(test)]` module lives *inside*
`{connector}/transformers.rs`, which is a file the manifest legitimately stages — so no path-based
rule can ever see it. It has to be caught on the content of the staged diff. Per the orchestrator's
Rule 3, connector correctness is proven by the `test_ucs` harness and by the Hyperswitch → UCS →
connector run, against the real connector — not by unit tests a run authored against its own code in
the same pass. One run pushed **73 `#[test]` functions** it wrote itself, none of which exercised the
connector.

**These checks reject Rust test *code*. They do not reject test *data*, and must never be widened
to.** `crates/internal/integration-tests/src/connector_specs/{connector}/` — `specs.json`,
`override.json`, `connector_specific_scenarios.json`, `webhook_payload.json` — is part of the
deliverable and is staged by the manifest. Check (a) matches none of them (its only
`.json` clauses are anchored on `task*.json` and on `global_suites/`, neither of which is under
`connector_specs/`, and `\.md$` catches only the harness's rendered reports, which are never staged) and check (b)
cannot, since they contain no Rust. `connector_specs/{connector}/override.json` in particular is the **sanctioned**
place for a scenario override and must stay stageable — it is the alternative the `global_suites/` clause pushes work
towards. If check (a) is ever extended, it must keep
`connector_specs/**/*.json` staged: a connector shipped without them declares suites that CI cannot
run, which is the exact failure Rule 3 exists to prevent.

If check (b) fires, remove the test code from the working tree — do not merely unstage it, or the
next phase will stage it again. If the removed test was pinning something genuinely non-obvious, say
so in the PR body so a human can add it deliberately.

Then compare that output against your manifest in **both** directions:

- **A manifest path missing from the staged list** → a registry/config/spec edit was never staged.
  Stage it and re-verify. Do NOT commit.
- **A staged path that is not in the manifest** → especially anything under `docs-generated/`,
  `examples/`, `data/field_probe/`, `sdk/`, `.ct-worktrees/`, or any `creds.json` / `.env` →
  `git restore --staged <path>` and re-verify. Do NOT commit.

If after two correction rounds the staged set still does not match the manifest, STOP: reclassify
`{CONNECTOR_STATUS}` as `FAILED` with `{FAILURE_REASON}` = `"staging manifest mismatch: <paths>"`
rather than committing an unknown file set.

For a NEW connector, also confirm the registry edits actually landed — a `0` is a missed edit:

```bash
for f in \
  crates/integrations/connector-integration/src/connectors.rs \
  crates/integrations/connector-integration/src/types.rs \
  crates/integrations/connector-integration/src/default_implementations.rs \
  crates/types-traits/domain_types/src/connector_types.rs \
  crates/types-traits/domain_types/src/router_data.rs \
  crates/types-traits/domain_types/src/types.rs \
  crates/internal/field-probe/src/auth.rs \
  crates/types-traits/grpc-api-types/proto/payment.proto \
  config/development.toml config/sandbox.toml config/production.toml ; do
    n=$(grep -ci "{connector}" "$f" 2>/dev/null || echo 0)
    [ "$n" = 0 ] && printf 'MISSING  %s\n' "$f" || printf 'ok  %-3s %s\n' "$n" "$f"
done
```

When `{FLOW}` is an added flow on an **existing** connector, only the connector's own files,
`specs.json` and possibly `payment.proto` change — the Codegen Agent's reported manifest is the
source of truth, not this full list.

#### Step 4 — commit

The PR title (and, on the merge queue, the merge-commit message) is checked by
`.github/workflows/pr-convention-checks.yml`, which runs `cog verify` against `cog.toml`. The
commit type must be the FIRST characters of the subject and must be one of:

    feat  fix  perf  refactor  test  docs  proto  chore  build  revert  ci

`wip` and `draft` are NOT in that list, so `cog verify` rejects them. Scopes are not restricted by `cog.toml`; `(connector)` is house
style, not an enforced allowlist.

**For SUCCESS connectors:**

```bash
git commit -m "feat(connector): implement {FLOW} for {connector}"
```

**For FAILED connectors:**

```bash
git commit -m "chore(connector): [{CONNECTOR}] GRACE run incomplete — {FLOW} not implemented"
```

Never put a marker *before* the type: `[GRACE-FAILED] feat(connector): ...` is a hard `cog verify`
parse error — the type is not the first thing in the subject. If the marker must be visible in the subject, append it as a
suffix — `feat(connector): implement {FLOW} for {connector} [GRACE-FAILED]` passes.

Capture the commit SHA for the JSON output:

```bash
git log -1 --format='%H'
```

Store as `{COMMIT_HASH}`.

## Phase 2: Credential Scrub (MANDATORY)

**You MUST verify that no credentials, API keys, or secrets are present in the committed files before pushing.**

### 2a: Inspect the diff

```bash
git diff origin/main..{BRANCH} -- crates/integrations/connector-integration/src/connectors/{connector}*
```

### 2b: Search for credential patterns

Scan the diff output for any of these patterns:
- Hardcoded API keys (long alphanumeric strings that look like secrets)
- Bearer tokens
- `x-api-key: <actual_value>` (not a placeholder)
- `Authorization: Basic <actual_value>`
- Strings from `creds.json` values
- Any test credentials embedded in source code (account numbers, IBANs, routing numbers that match real test creds)

**Source code should NEVER contain credentials.** Connector implementations read credentials at runtime from the request context — they do not hardcode them. If you find hardcoded credentials in source files, that is a bug in the codegen output. Fix it:

```bash
# Edit the file to remove the hardcoded credential
# Replace with the correct runtime credential access pattern used by other connectors
```

### 2c: Verify creds.json is NOT staged

```bash
git diff --name-only origin/main..{BRANCH}
```


`git reset HEAD~ -- <paths>` + `git commit --amend` drops the file from the commit while leaving
it in the working tree — verified. **But it only rewrites the tip commit.** If the secret was
introduced in an *earlier* commit on `{BRANCH}` (this agent's own commit is the tip, but a retry
may have left more than one), the amend will not remove it from history.

In that case, do NOT push. `git filter-repo` is **not installed in this environment**
(`command -v git-filter-repo` returns nothing; `git filter-repo --version` reports
`git: 'filter-repo' is not a git command`), so there is no history-rewrite tool available here.
Use only what is present:

```bash
# How many commits on this branch are yours to rewrite?
git rev-list --count origin/main..{BRANCH}
```

- **Exactly 1 commit** → the `git reset HEAD~` + `--amend` recipe above is sufficient.
- **More than 1 commit** → return FAILED with
  `{FAILURE_REASON}` = `"credential found in commit <sha>, cannot scrub: git-filter-repo not
  installed"`, and do NOT push. Removing it would require installing `git-filter-repo` (not
  present here) or a human rebuilding the branch by hand. Never push a branch you know contains
  a secret.

### 4b-0: State the end-to-end result and any Hyperswitch dependency

The PR description MUST carry an **End-to-end** section built from `{E2E_STATUS}`, `{HS_PR}`,
`{HS_CHANGES_REQUIRED}` and `{E2E_EVIDENCE}`. A reviewer cannot tell from a grpcurl transcript
whether Hyperswitch can actually reach this code, and several flows are dead until a Hyperswitch-side
gate is overridden — so this is a merge-blocking fact, not a footnote:

- `{E2E_STATUS}` = `SUCCESS` → state that a real Hyperswitch call reached the connector through UCS,
  and paste `{E2E_EVIDENCE}`.
- `{E2E_STATUS}` = `E2E_BLOCKED` → state plainly that the sandbox account cannot perform this flow,
  that the code is therefore **unverified rather than broken**, and what would unblock it. Say so in
  the PR title area too if the whole PR rests on it.
- `{E2E_STATUS}` = `E2E_SKIPPED` → state that no Hyperswitch checkout was available and the
  end-to-end path is unproven.
- `{HS_CHANGES_REQUIRED}` ≠ `none` → add a **"Requires Hyperswitch PR {HS_PR}"** line near the top of
  the body and name the gate. Without it this UCS PR merges into a state where the flow exists and
  Hyperswitch can never call it.

**`HS_PR` is mandatory in the body, and it is derived, not chosen.** It goes in the machine-readable block of both
Phase 4b templates, exactly once. Three GRACE PRs shipped with no `HS_PR` field at all (an older template omitted
it) and one of those had a paired `juspay/hyperswitch` PR the description never named in machine-readable form; two
more rendered `none required` while a paired HS PR existed, one of them contradicting its own "Requires Hyperswitch
PR …" prose in the same document. Derive it from **whether the Hyperswitch side was actually examined and reached a
verdict** — first match wins:

| # | Input state | `HS_PR` |
|---|---|---|
| 1 | No Hyperswitch checkout existed in this run (`{E2E_STATUS}` = `E2E_SKIPPED` for want of one), so nothing was ruled in or out | `not assessed` |
| 2 | The E2E agent never ran, was skipped, timed out or died before reporting on the Hyperswitch side — **whatever `{HS_CHANGES_REQUIRED}` says** | `not assessed` |
| 3 | The E2E agent examined Hyperswitch and reported `{HS_CHANGES_REQUIRED}` = `none` | `none required` |
| 4 | Changes were required and a PR was raised for them | `<url>` |
| 5 | Changes were required and an existing HS PR already carries them | `pre-existing:<url>` |
| 6 | Changes were required and no PR was raised | `NOT_RAISED:<reason>` (name the reason: `no_push_access`, `gate_failed`, `conflict:<paths>`, `push_failed:<line>`) |

`none required` is reachable only through row 3. A run that did not look does not get to say nothing was needed:
that is row 1 or 2, and `not assessed` is the honest word for it. `2.8_pr_run.md` Phase 8 states the same derivation
against v2's own evidence (`plan.json .hs_changes`, the `S4:*:__hs__` row, `events.log` `SKIP` reasons) and
**overrides this table on the v2 path**.

**Contradiction check — run it before the body is posted or edited, and fail rather than publish.** This is the
staged-set verification of Step 3 applied to a claim instead of a file set, and like Step 3 it runs in both
directions:

```bash
# $BODY = the rendered description, $HSPR = the value the table above selected
[ "$(grep -c '^HS_PR=' "$BODY")" = 1 ] || { echo "FAIL: HS_PR missing or duplicated in body"; exit 1; }
grep -qxF "HS_PR=$HSPR" "$BODY" || { echo "FAIL: body HS_PR line disagrees with the derived value"; exit 1; }
case "$HSPR" in "none required"|"not assessed")
  gh pr list --repo juspay/hyperswitch --state all --search "{CONNECTOR} in:title" --json url --jq '.[].url' \
    | tee /dev/stderr | grep -q . && echo "FAIL: HS_PR=$HSPR but a Hyperswitch PR exists for this connector"
  [ "{HS_CHANGES_REQUIRED}" = none ] || echo "FAIL: HS_PR=$HSPR with HS_CHANGES_REQUIRED={HS_CHANGES_REQUIRED}"
  grep -niE 'requires hyperswitch pr|github\.com/juspay/hyperswitch/pull/' "$BODY" \
    && echo "FAIL: HS_PR=$HSPR but the body's own prose names a Hyperswitch PR" ;;
esac
```

Any `FAIL:` → **do not post**. Re-derive from the table, re-render, re-check. A listed HS PR that is genuinely
unrelated to this flow is recorded as an unverified candidate with those words, and only after checking its touched
files; the `HS_CHANGES_REQUIRED` and `^HS_PR=` checks must still be clean. Still contradictory after two rounds →
reclassify `{CONNECTOR_STATUS}` as `FAILED` with `{FAILURE_REASON}` = `"HS_PR contradiction: <tokens>"`, the same
terminal as Step 3's two-round rule: a description whose two halves disagree is worse than no description.

## Output

Return your final answer as JSON. This is the only output format the engine accepts; the legacy `STATUS:`/`PR_URL:` free-text format is no longer parsed. Reply with ONLY the JSON object — no prose, no markdown fences.

```json

  "approved": true,
  "status": "SUCCESS",
```

**`approved` and `comments` are HARD-REQUIRED.** The consumer is the `pr_review` checkpoint
(`grace/grace-workspace/packages/core/src/checkpoints/pr-review.ts`), which rejects the whole
checkpoint with `Invalid PR review JSON` unless `typeof parsed.approved === "boolean"` **and**
`Array.isArray(parsed.comments)`. Omitting `comments` fails the run even when the PR was created
successfully. Emit `"comments": []` when you have nothing to say.

Field rules:

- `comments` is an array (possibly empty) of
  `{ "file": string, "line": number | null, "comment": string, "severity": "info" | "warning" | "blocking" }`.
  The engine prints every entry, so `severity` must be one of those three strings.
- `specComplianceScore` is a number in `0..1`. The engine auto-passes only when
  `approved === true && specComplianceScore >= 0.6`; a missing or lower score drops the run into
  the human-approval gate. Always emit it.
- `approved` tracks the PR, not the run: `approved = (PR_STATUS == "READY")`. A `PARTIAL` run reaches `STATUS: SUCCESS` (`2_connector.md` "Final status") on the strength of a withdrawal, and a withdrawal is not an approval — so `PARTIAL` emits `approved=false` with `status="SUCCESS"`. For `READY` connectors: `approved=true`, `status="SUCCESS"`, `prUrl` is the URL captured from `gh pr create` output (or from the existing-PR check in Phase 5a), `reason` is empty.
- For FAILED connectors: `approved=false`, `status="FAILED"`, `prUrl` is still the URL of the do-not-merge PR (Rule 11: every connector gets a PR), `reason` explains the failure.
- `branchName` is always `{BRANCH}` — the suffixed run branch from preflight (e.g. `feat/grace-cybersource-bankdebit-3f69a1`).
- `commitHash` is the SHA stored in Phase 1c.

Use a conventional `chore(connector): …` title instead.
11. **Always create a PR** — both successful and failed connectors get PRs. The only reason to NOT create a PR is if there are no connector files to commit (Phase 1a). **Creating a PR is not the same as offering one for merge**: whether it is a draft is the `PR_STATUS` row's decision (`2.8_pr_run.md` Phase 1), and anything short of `READY` or `PARTIAL` is created `--draft`, labelled `do not merge`, with its gaps named in the body. The rule exists so unfinished work stays visible, not so it looks finished.
12. **Never retry identical commands** — if `gh pr create` or `git push` fails, diagnose the error first. Common causes: (a) permission denied, (b) PR already exists (treat as idempotency hit, see Phase 5a). Fix the root cause, then retry with corrected parameters.
13. **Explicit-manifest git staging** — stage the explicit manifest from Phase 1c (the Codegen Agent's `{CONNECTOR_SOURCE_FILES}` unioned with the registry / proto / config / connector_specs paths it touched), then VERIFY with `git diff --cached --name-only` that the staged set matches that manifest in both directions, and fail loudly on any mismatch. `git add crates/integrations/connector-integration/src/connectors/{connector}*` alone is NOT sufficient — it stages 2 of ~16 paths and yields a PR that registers nothing. Never `git add -A`. Never `git add crates/`. Never stage `creds.json`, `.env`, the CI-generated `data/field_probe/`, `docs-generated/`, `examples/`, `sdk/` files, any working note — `grace/**`, `task*.json`, and any `.md` not named explicitly in the manifest — or any Rust test code: `test.rs` / `tests.rs` files, and `#[cfg(test)]` / `#[test]` / `#[tokio::test]` blocks inside otherwise-staged files. Step 3 rejects these before the manifest comparison, because `{CONNECTOR_SOURCE_FILES}` is unioned into the manifest and would otherwise absorb them silently. **The `connector_specs/{connector}/*.json` files are not "Rust test code" and are required members of the manifest** — they are the connector's certification data, the thing `check_connector_specs` gates in CI, and staging them is mandatory, not optional.
14. **Validate before committing** — run `make validate-pre-push-fix` and `typos --config ./.typos.toml` (Phase 1b-2) before staging. `cargo build` alone is not the CI gate; CI also enforces `cargo +nightly fmt --all --check`, `clippy --all-features --all-targets -D warnings`, `crate-ci/typos`, and `check_connector_specs`. If a failure is mechanical (formatting, spelling), fix it and re-run. If it is not fixable without changing connector logic, reclassify the connector as `FAILED` — do not push a red PR as SUCCESS.
15. **Conventional titles and commit types only** — the type must be the first characters of the subject and must be one of `feat fix perf refactor test docs proto chore build revert ci` (from `cog.toml`). `wip` and `draft` are rejected. Scopes are unrestricted; `(connector)` is house style. Add labels to an existing PR with `gh pr edit --add-label` (`gh pr label add` does not exist).
16. **The manifest is checked in three directions, not two** — staged set vs manifest (both ways, Step 3) **plus**
    manifest vs the deny-list (Step 1a, before any `git add`). A forbidden path that is in the manifest *and* staged
    matches on both sides and passes Step 3 silently; Step 1a is the only check that sees it. `git add -f` is never
    a way around an ignore rule — a path git declines to stage is a path the PR must not contain — and
    `crates/internal/integration-tests/src/global_suites/**` is forbidden however legitimately it sits under
    `crates/`: the override belongs in `connector_specs/{connector}/override.json`.
17. **`HS_PR` is mandatory in the body and derived, not chosen** — exactly one `HS_PR=` line, from the 4b-0 table.
    `none required` means the Hyperswitch side was examined and needs nothing; a run that never looked is
    `not assessed`. Before posting or editing the body, run 4b-0's contradiction check: `none required` /
    `not assessed` alongside a live Hyperswitch PR, a non-`none` `{HS_CHANGES_REQUIRED}`, or the body's own
    "Requires Hyperswitch PR …" prose is a failure to fix, not a body to publish.
18. **Expect CI to append other connectors' generated files** — the `auto-fix` job regenerates the whole repo and
    stages with `git add -A` (`ci.yml:531-533`, `:541`), so bot commits carrying unrelated `data/field_probe/*.json`,
    `docs-generated/**` and `examples/**` are external behaviour, not this run's dirt. Never revert them, never
    re-push a cleaned branch, and never widen the staging manifest to pre-empt them. Measured: 5 of 10 GRACE PRs,
    once 189 files. Details and the decision not to change `ci.yml`: `2.8_pr_run.md` Phase 9.
19. **A draft PR's green CI is not evidence** — drafts skip typos, clippy, `auto-fix`, the Compilation Check, tests and sdk-tests while `CI Result` still reports success (the `formatting` job never runs on a PR at all). Never treat a draft run as proof; open SUCCESS PRs non-draft, and use `gh pr ready` before reading CI as signal.
