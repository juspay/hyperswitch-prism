# PR Agent

You handle **all git operations** for the **{FLOW}** implementation of **{CONNECTOR}**: committing on the preflight-created run branch, scrubbing credentials, pushing, and opening a **PR** on `juspay/hyperswitch-prism`.

**First**: Read this file (`grace/workflow/2.4_pr.md`) fully to understand all phases and rules before proceeding.

**This agent handles BOTH successful and failed connectors.** For failed connectors, the PR is created with a "do not merge" label and the failure details in the description, so that the team has visibility into what was attempted and what went wrong.

**HARD GUARDRAIL — DIRECT WORKFLOW ON `juspay/hyperswitch-prism`**: We work directly on `juspay/hyperswitch-prism`. The `origin` remote points to `juspay/hyperswitch-prism`. All pushes go to `origin`. PRs are created as same-repo PRs (no cross-fork syntax needed).

**HARD GUARDRAIL — TARGET REPOSITORY**: ALL `gh` commands MUST use `--repo juspay/hyperswitch-prism`. This is the ONLY valid target repository. Do NOT use any other org or repo name.

**HARD GUARDRAIL — NO RETRYING SAME COMMAND**: If a `gh pr create` or `git push` command fails, do NOT retry the exact same command. Diagnose the error, fix the root cause, then retry with corrected parameters. Retrying identical commands wastes time and will produce identical errors.

**HARD GUARDRAIL — NO BRANCH CREATION, NO CHERRY-PICK**: The run branch (`{BRANCH}`) was already created and checked out by the preflight checkpoint, and the implementation checkpoint wrote the connector files there. Do NOT run `git checkout -b ...` and do NOT run `git cherry-pick ...` in this agent. Commit and push directly on `{BRANCH}`.

## Phase 1: Commit on the Run Branch

The implementation checkpoint left modified connector files in the working tree on `{BRANCH}`. Verify you are on that branch, then commit.

### 1a: Verify branch and check for changes

```bash
git branch --show-current                   # must equal {BRANCH}
```

If the current branch does NOT equal `{BRANCH}`, switch to it (preflight created it earlier in the run, so it exists locally):

```bash
git checkout {BRANCH}
```

Then check for changes:

```bash
git status --porcelain
```

A connector change is **never** confined to `connectors/{connector}*` — the Rust registry, the
proto contract, the `config/*.toml` files and `connector_specs/` change too (see the staging
manifest in Phase 1c). Inspect the whole working tree, not just the connector directory.

If there are no modified/new files at all, there is nothing to commit. Return FAILED with reason "No connector files to commit."

### 1b: Pre-commit validation (SUCCESS connectors only)

**If `{CONNECTOR_STATUS}` is `SUCCESS`, you MUST verify ALL of the following by inspecting the Codegen Agent's report and the contents of `{GRPCURL_OUTPUT}` (the raw grpcurl output captured upstream and passed in as an input). If ANY answer is NO, reclassify as FAILED.**

```
PRE-COMMIT CHECKLIST (mandatory for SUCCESS):
[ ] Did `cargo build` complete with zero errors? (YES/NO)
[ ] Did the local CI-parity validation in 1b-2 finish with zero failing steps? (YES/NO)
[ ] Did the gRPC test checkpoint run a grpcurl Authorize call?
    Verify {GRPCURL_OUTPUT} contains the request and response of that call. (YES/NO)
[ ] Was the response status code 2xx (200-299)? grpcurl prints proto3 JSON, so
    the key comes back lowerCamelCase as `statusCode`, not `status_code`. (YES/NO)
[ ] Did the grpcurl response contain a JSON object with a success `status`?
    The values are PaymentStatus enum names as declared in
    `crates/types-traits/grpc-api-types/proto/payment.proto` — UPPERCASE:
    AUTHORIZED, CHARGED, PENDING, AUTHENTICATION_PENDING. (YES/NO)
[ ] Was the grpcurl output free of client-side failures — "Error invoking method",
    "unknown field", "Missing required field: …" — and of a non-null `error`
    object? `error` is an `ErrorInfo` (`message ErrorInfo` in
    `crates/types-traits/grpc-api-types/proto/payment.proto`: `unified_details` /
    `issuer_details` / `connector_details`), which grpcurl prints lowerCamelCase
    as `unifiedDetails` / `issuerDetails` / `connectorDetails`. (YES/NO)
[ ] Was `status` free of the PaymentStatus failure variants — FAILURE,
    AUTHORIZATION_FAILED, AUTHENTICATION_FAILED, CAPTURE_FAILED, VOID_FAILED,
    ROUTER_DECLINED — and did grpcurl report no non-OK gRPC code (Internal,
    Unimplemented, Unknown, Unauthenticated, FailedPrecondition)? (YES/NO)
```

> **`PAYMENT_FLOW_ERROR` is a GRACE-internal label, not a repo error code — do not grep for it
> as evidence.** It appears nowhere in `crates/` or in the proto tree
> (`rg -w 'PAYMENT_FLOW_ERROR' crates/` → 0 hits). It exists only inside the GRACE workspace, as a
> classification bucket in the codegen agent prompt generator
> (`grace/grace-workspace/packages/core/src/generators/codegen-agent-prompt.ts`, lines 65 and 186)
> and as display text in the dashboard review step
> (`grace/grace-workspace/packages/dashboard/src/components/wizard/IntegrationStepReview.tsx:109`).
> The server never emits that string, so "output free of PAYMENT_FLOW_ERROR" proves nothing — judge
> the run on the fields checked above instead.

If any answer is NO, reclassify `{CONNECTOR_STATUS}` as `FAILED` and set `{FAILURE_REASON}` accordingly.

### 1b-2: Local CI-parity validation (MANDATORY, run before staging)

`cargo build` is not the gate CI applies. CI additionally runs `cargo +nightly fmt --all --check`,
`cargo clippy --all-features --all-targets` with warnings-as-errors, `crate-ci/typos`, and
`cargo run --all-features --bin check_connector_specs`. Skipping these is why
`chore: auto-fix formatting and generated code` bot commits keep landing on GRACE PRs.

Run this from the repo root:

```bash
make validate-pre-push-fix
```

That target invokes `./scripts/validation/pre-push.sh --fix`, which runs, in order:
`cargo +nightly fmt --all` (writing, not just checking), `cargo check --all-features --all-targets`,
`cargo clippy --all-features --all-targets -- -D warnings`,
`cargo run --bin check_connector_specs`, `make generate`, `make docs`.

The only other real validation targets are `make validate-pre-push` (identical, but
`cargo +nightly fmt --all --check` — reports instead of fixing) and `make validate-pre-push-full`
(adds `cargo test --all-features`). No git hook is installed; you must invoke the target yourself.

`pre-push.sh` does NOT run the spell checker, so run it separately — there is no `make typos`
target:

```bash
typos --config ./.typos.toml
```

**Interpreting the result:**

- **All steps pass** → continue to Phase 1c.
- **`fmt` rewrote files, or `typos` flagged a vendor name that belongs in `.typos.toml`** →
  apply the mechanical fix, re-run until clean, then continue. Formatting and spell-config fixes
  are in scope for this agent.
- **`cargo check`, `clippy -D warnings`, or `check_connector_specs` fails and the fix would
  require changing connector logic** → reclassify `{CONNECTOR_STATUS}` as `FAILED`, set
  `{FAILURE_REASON}` to the first failing step plus its error text, and continue on the FAILED
  path. Do NOT push a red PR labelled SUCCESS.
- **The `typos` binary is not installed** → say so verbatim in `{FAILURE_REASON}` / the PR body
  rather than reporting the check as passed. CI runs it regardless.

`make check` and `make clippy` are cargo-hack per-feature sweeps (`cargo hack ... --each-feature
--no-dev-deps`) and are NOT what CI runs — do not substitute them for the commands above.

`make validate-pre-push*` still does not reproduce everything CI runs. Not covered locally by it:
`crate-ci/typos`, `cargo test -p composite-service --all-features --test composite_request_schema_check`,
`cargo test -p integration-tests --all-features --lib harness::scenario_api::tests::all_supported_scenarios_match_proto_schema_for_all_connectors -- --exact`,
`cargo test -p grpc-server --all-features --test test_superposition_config`, and `buf lint` /
`buf breaking` (`.github/workflows/proto-checks.yml`, triggered by any `**.proto` change).
Passing locally is necessary, not sufficient.

### 1c: Stage and commit

**Stage from an EXPLICIT manifest — never `git add -A`, never `git add crates/`.**
`git add crates/integrations/connector-integration/src/connectors/{connector}*` stages 2 of the
~16 hand-authored paths a connector change touches; the resulting PR compiles and registers
nothing. `git add -A` sweeps in CI-generated files and stray worktrees.

#### Step 1 — build the manifest

Start from `{CONNECTOR_SOURCE_FILES}` (the explicit list the Codegen Agent reported) and union it
with every path below that the codegen run actually modified. This list is verified against the
real new-connector commits `bcc5fc76c` (travelhub), `b0d5b028c` (saferpay), `59684fe20`
(jpmorganorbital) and `5a2579c32` (paynearme):

Connector's own code
  - `crates/integrations/connector-integration/src/connectors/{connector}.rs`
  - `crates/integrations/connector-integration/src/connectors/{connector}/transformers.rs`

Registry (Rust)
  - `crates/integrations/connector-integration/src/connectors.rs`
  - `crates/integrations/connector-integration/src/types.rs`
  - `crates/integrations/connector-integration/src/default_implementations.rs`
  - `crates/types-traits/domain_types/src/connector_types.rs`
  - `crates/types-traits/domain_types/src/router_data.rs`
  - `crates/types-traits/domain_types/src/types.rs`
  - `crates/internal/field-probe/src/auth.rs`

Contract
  - `crates/types-traits/grpc-api-types/proto/payment.proto`

Config
  - `config/development.toml`, `config/sandbox.toml`, `config/production.toml`
  - `config/superposition.toml` — **conditional**, not mandatory. travelhub and jpmorganorbital
    edited it; saferpay and paynearme did not. If the codegen run DID touch it, the connector also
    needs a `ConnectorEnum::{Connector} => { patched.{connector}.apply(params_patch); }` arm in
    `crates/types-traits/domain_types/src/types.rs`, or dynamic URL patching fails at runtime.

Certification
  - `crates/internal/integration-tests/src/connector_specs/{connector}/specs.json`
  - `crates/internal/integration-tests/src/connector_specs/alpha_connectors.json`
  - `crates/internal/integration-tests/src/connector_specs/{connector}/webhook_payload.json` —
    only when `specs.json` lists `"EventService/HandleEvent"`

Provenance
  - `data/integration-source-links.json`
  - `.typos.toml` — only if the connector/vendor name trips the spell checker

**Do NOT stage these — CI regenerates and commits them** in a separate
`chore: auto-fix formatting and generated code` commit by `hyperswitch-bot[bot]`:
`data/field_probe/{connector}.json`, `docs-generated/**`, `examples/{connector}/**`,
`sdk/javascript/src/payments/_generated_grpc_client.ts`. The `make generate` / `make docs` steps in
Phase 1b-2 will have dirtied them locally; leave them unstaged. (That `auto-fix` job runs only on
non-draft, same-repo PRs — a draft PR or a fork PR gets no generated files committed for it.)

#### Step 2 — stage exactly that list

```bash
git add <each path from the manifest, space separated>
```

#### Step 3 — VERIFY the staged set against the manifest, and fail loudly on mismatch

```bash
git diff --cached --name-only
```

(`git status --porcelain --cached` is not a valid invocation — `git status` has no `--cached`
option and errors out with `unknown option 'cached'`. Use `git diff --cached --name-only`.)

Compare that output against your manifest in **both** directions:

- **A manifest path missing from the staged list** → a registry/config/spec edit was never staged.
  Stage it and re-verify. Do NOT commit.
- **A staged path that is not in the manifest** → especially anything under `docs-generated/`,
  `examples/`, `data/field_probe/`, `sdk/`, `.ct-worktrees/`, or any `creds.json` / `.env` →
  `git restore --staged <path>` and re-verify. Do NOT commit.

If after two correction rounds the staged set still does not match the manifest, STOP: reclassify
`{CONNECTOR_STATUS}` as `FAILED` with `{FAILURE_REASON}` = `"staging manifest mismatch: <paths>"`
rather than committing an unknown file set.

For a NEW connector, also confirm the registry edits actually landed — a `0` is a missed edit:

```bash
for f in \
  crates/integrations/connector-integration/src/connectors.rs \
  crates/integrations/connector-integration/src/types.rs \
  crates/integrations/connector-integration/src/default_implementations.rs \
  crates/types-traits/domain_types/src/connector_types.rs \
  crates/types-traits/domain_types/src/router_data.rs \
  crates/types-traits/domain_types/src/types.rs \
  crates/internal/field-probe/src/auth.rs \
  crates/types-traits/grpc-api-types/proto/payment.proto \
  config/development.toml config/sandbox.toml config/production.toml ; do
    n=$(grep -ci "{connector}" "$f" 2>/dev/null || echo 0)
    [ "$n" = 0 ] && printf 'MISSING  %s\n' "$f" || printf 'ok  %-3s %s\n' "$n" "$f"
done
```

When `{FLOW}` is an added flow on an **existing** connector, only the connector's own files,
`specs.json` and possibly `payment.proto` change — the Codegen Agent's reported manifest is the
source of truth, not this full list.

#### Step 4 — commit

The PR title (and, on the merge queue, the merge-commit message) is checked by
`.github/workflows/pr-convention-checks.yml`, which runs `cog verify` against `cog.toml`. The
commit type must be the FIRST characters of the subject and must be one of:

    feat  fix  perf  refactor  test  docs  proto  chore  build  revert  ci

`wip` and `draft` are NOT in that list, so `cog verify` rejects them. Scopes are not restricted by `cog.toml`; `(connector)` is house
style, not an enforced allowlist.

**For SUCCESS connectors:**

```bash
git commit -m "feat(connector): implement {FLOW} for {connector}"
```

**For FAILED connectors:**

```bash
git commit -m "chore(connector): [{CONNECTOR}] GRACE run incomplete — {FLOW} not implemented"
```

Never put a marker *before* the type: `[GRACE-FAILED] feat(connector): ...` is a hard `cog verify`
parse error — the type is not the first thing in the subject. If the marker must be visible in the subject, append it as a
suffix — `feat(connector): implement {FLOW} for {connector} [GRACE-FAILED]` passes.

Capture the commit SHA for the JSON output:

```bash
git log -1 --format='%H'
```

Store as `{COMMIT_HASH}`.

## Phase 2: Credential Scrub (MANDATORY)

**You MUST verify that no credentials, API keys, or secrets are present in the committed files before pushing.**

### 2a: Inspect the diff

```bash
git diff origin/main..{BRANCH} -- crates/integrations/connector-integration/src/connectors/{connector}*
```

### 2b: Search for credential patterns

Scan the diff output for any of these patterns:
- Hardcoded API keys (long alphanumeric strings that look like secrets)
- Bearer tokens
- `x-api-key: <actual_value>` (not a placeholder)
- `Authorization: Basic <actual_value>`
- Strings from `creds.json` values
- Any test credentials embedded in source code (account numbers, IBANs, routing numbers that match real test creds)

**Source code should NEVER contain credentials.** Connector implementations read credentials at runtime from the request context — they do not hardcode them. If you find hardcoded credentials in source files, that is a bug in the codegen output. Fix it:

```bash
# Edit the file to remove the hardcoded credential
# Replace with the correct runtime credential access pattern used by other connectors
git add <fixed_files>
git commit --amend --no-edit
```

### 2c: Verify creds.json is NOT staged

```bash
git diff --name-only origin/main..{BRANCH}
```

If `creds.json` or any `.env` file appears in this list, something went wrong. Remove it:

```bash
git reset HEAD~ -- creds.json .env
git commit --amend --no-edit
```

`git reset HEAD~ -- <paths>` + `git commit --amend` drops the file from the commit while leaving
it in the working tree — verified. **But it only rewrites the tip commit.** If the secret was
introduced in an *earlier* commit on `{BRANCH}` (this agent's own commit is the tip, but a retry
may have left more than one), the amend will not remove it from history.

In that case, do NOT push. `git filter-repo` is **not installed in this environment**
(`command -v git-filter-repo` returns nothing; `git filter-repo --version` reports
`git: 'filter-repo' is not a git command`), so there is no history-rewrite tool available here.
Use only what is present:

```bash
# How many commits on this branch are yours to rewrite?
git rev-list --count origin/main..{BRANCH}
```

- **Exactly 1 commit** → the `git reset HEAD~` + `--amend` recipe above is sufficient.
- **More than 1 commit** → return FAILED with
  `{FAILURE_REASON}` = `"credential found in commit <sha>, cannot scrub: git-filter-repo not
  installed"`, and do NOT push. Removing it would require installing `git-filter-repo` (not
  present here) or a human rebuilding the branch by hand. Never push a branch you know contains
  a secret.

## Phase 3: Push the Branch

**Push to `origin` (`juspay/hyperswitch-prism`).**

```bash
git push origin {BRANCH}
```

If push fails:
- **Branch already exists on remote with diverged history**: Try `git push origin {BRANCH} --force-with-lease` only if this is a retry of a previous failed PR attempt for the same run (same `{BRANCH}` value).
- **Permission denied**: Return FAILED — credentials may be misconfigured.

The runId6 suffix in `{BRANCH}` makes collisions across runs effectively impossible, so the legacy "append `-v2` suffix" workaround no longer applies.

## Phase 4: Prepare PR Description

### 4a: Sanitize grpcurl output

Take the `{GRPCURL_OUTPUT}` and **redact ALL credentials** (this applies whether the connector passed or failed — even partial/error grpcurl output must be sanitized):

1. Replace the whole `-H 'x-connector-config: {...}'` value with `<REDACTED>` —
   this single header carries the entire credential JSON block (built by
   `build_wrapped_config` in `crates/internal/connector-creds/src/lib.rs`) and is
   the preferred auth form, so it is the most important one to catch
2. Replace any `-H 'x-api-key: ...'` header values with `<REDACTED>`
3. Replace any `-H 'x-key1: ...'` / `-H 'x-key2: ...'` header values with `<REDACTED>`
4. Replace any `-H 'x-api-secret: ...'` header values with `<REDACTED>`
5. Replace any `-H 'x-merchant-id: ...'` header values with `<REDACTED>`
6. Replace any `-H 'Authorization: ...'` header values with `<REDACTED>`
7. Replace any other `-H` header values that look like credentials (long alphanumeric strings, base64, etc.) with `<REDACTED>`
8. Replace any account numbers, IBANs, routing numbers, sort codes, BSB numbers with `<REDACTED>`
9. Preserve the grpcurl command structure, endpoint, request body fields (keys only), and the full response JSON

**Example of sanitized output:**
```
grpcurl -plaintext \
  -H 'x-connector: adyen' \
  -H 'x-api-key: <REDACTED>' \
  -H 'x-merchant-id: <REDACTED>' \
  -d '{
    "merchant_transaction_id": "test_adyen_bankdebit_001",
    "amount": {"minor_amount": 10000, "currency": "EUR"},
    ...
    "payment_method": {
      "sepa": {
        "iban": {"value": "<REDACTED>"},
        "bank_account_holder_name": {"value": "John Doe"}
      }
    }
  }' \
  localhost:8000 \
  types.PaymentService/Authorize

Response:
{
  "status": "AUTHORIZED",
  "statusCode": 200,
  ...
}
```

Shapes above are the real ones, not illustrative: the proto package is `types`
(`payment.proto` / `services.proto`), so the fully-qualified method is
`types.PaymentService/Authorize` — there is no `ucs.v2.` package, and the harness
resolves the same string (`crates/internal/integration-tests/src/harness/scenario_api.rs`).
`amount` is a `Money` message (`minor_amount` + `currency`), not three top-level keys,
and the request's own id field is `merchant_transaction_id`. Responses come back as
proto3 JSON, so keys are lowerCamelCase (`statusCode`) and enum values are the
UPPERCASE proto names (`AUTHORIZED`, `CHARGED`).

## Phase 5: Create the Pull Request

**CRITICAL: All `gh` commands MUST use `--repo juspay/hyperswitch-prism`.**

### 5a: Check for existing PR (idempotency)

```bash
gh pr list --repo juspay/hyperswitch-prism --head {BRANCH} --state open --json url --jq '.[0].url' 2>/dev/null
```

Because `{BRANCH}` includes the runId6 suffix, this match only happens if the **same run** is re-entering this checkpoint (e.g. after a retry). If a PR URL is returned, the PR already exists for this run. Report SUCCESS with that URL and finish.

### 5b: Ensure labels exist

```bash
gh label create "GRACE" --repo juspay/hyperswitch-prism --description "Auto-generated by GRACE pipeline" --color "7057ff" 2>/dev/null || true
gh label create "do not merge" --repo juspay/hyperswitch-prism --description "PR requires manual intervention before merging" --color "e11d48" 2>/dev/null || true
```

`gh label` is only present in newer `gh` releases — on older clients (e.g. `gh 2.4.0`) it fails with
`unknown command "label" for "gh"`, which the `|| true` swallows, and the later
`gh pr create --label` then fails because the label does not exist on the repo. If `gh label create`
prints `unknown command`, create the labels through the API instead — `gh api` exists in every
version:

```bash
gh api -X POST repos/juspay/hyperswitch-prism/labels \
  -f name="GRACE" -f color="7057ff" -f description="Auto-generated by GRACE pipeline" 2>/dev/null || true
gh api -X POST repos/juspay/hyperswitch-prism/labels \
  -f name="do not merge" -f color="e11d48" -f description="PR requires manual intervention before merging" 2>/dev/null || true
```

(A 422 `already_exists` response here is expected and harmless.)

### 5c: Determine labels and title

**The PR title is machine-checked. Two independent jobs read it:**

1. `.github/workflows/pr-convention-checks.yml` → `cog verify "$TITLE"` (cocogitto, config
   `cog.toml`). Grammar: `<type>[(<scope>)][!]: <subject>`, and the type must be the FIRST
   characters of the title — nothing may precede it.
2. `.github/workflows/pr-title-spell-check.yml` → `crate-ci/typos` on the title alone.

**Allowed types — the complete list from `cog.toml`:**

    feat  fix  perf  refactor  test  docs  proto  chore  build  revert  ci

`proto` is repo-specific (Proto / API Contract). `wip`, `draft`, `spike`, `temp` and every other
word are rejected as disallowed commit types. Scopes are **not** restricted — any
scope string passes `cog verify`; `(connector)` is house style only, not an enforced allowlist.

Expected `cog verify` outcome — derived from the `cog.toml` type list above plus the conventional-
commit grammar, NOT executed here (cocogitto is not installed in this environment; `command -v cog`
returns nothing). CI installs it via `taiki-e/install-action` and is the authority:

    feat(connector): implement Authorize for cybersource      PASS
    chore(connector): [Cybersource] GRACE run incomplete      PASS
    feat(connector): implement Authorize for cybersource [GRACE-FAILED]   PASS
    [GRACE-FAILED] feat(connector): implement Authorize ...   FAIL  <- parse error
    wip(connector): [FAILED] implement Authorize ...          FAIL  <- type not allowed

**For SUCCESS connectors:**
- Labels: `GRACE`
- Title: `feat(connector): implement {FLOW} for {connector}`
- Draft: no

**For FAILED connectors:**
- Labels: `GRACE`, `do not merge`
- Title: `chore(connector): [{CONNECTOR}] GRACE run incomplete — {FLOW} not implemented`
- Draft: yes (`--draft`)

**Never prefix the title with `[GRACE-FAILED]`.** The failure state is carried by the `do not
merge` label, the `--draft` state and the PR body — never by text in front of the commit type. If
a title-visible marker is genuinely required, append it as a SUFFIX
(`feat(connector): implement {FLOW} for {connector} [GRACE-FAILED]`), which passes `cog verify`.

Labels on an already-open PR are added with `gh pr edit`, not `gh pr label add` (which is not a
real subcommand):

```bash
gh pr edit <number-or-url> --repo juspay/hyperswitch-prism --add-label "do not merge"
gh pr edit <number-or-url> --repo juspay/hyperswitch-prism --remove-label "do not merge"
```

**Know what `--draft` costs before you rely on its CI result.** Every gated job in
`.github/workflows/ci.yml` carries `!github.event.pull_request.draft` — `typos` (Spell check),
`clippy`, `auto-fix`, `check` (Compilation Check), `test` (Run Tests) and `sdk-test` — so a draft
PR skips all of them, while the `CI Result` gate (`ci-gate`, `if: always()`) still reports success
(it fails only on `failure`/`cancelled`, not on `skipped`). The separate `formatting` job is not
part of this: it is gated on `github.event_name != 'pull_request'` and so never runs on any PR,
draft or not — on PRs, formatting is what `auto-fix` applies.
A draft PR's green checks prove nothing, and no generated files get committed for it. That is
acceptable for a FAILED, do-not-merge PR opened for visibility — it is NOT acceptable as evidence
that anything passed. SUCCESS PRs must be opened non-draft. If a draft PR later needs real CI, run
`gh pr ready <number-or-url> --repo juspay/hyperswitch-prism` and wait for the fresh run.

## Output

Return your final answer as JSON. This is the only output format the engine accepts; the legacy `STATUS:`/`PR_URL:` free-text format is no longer parsed. Reply with ONLY the JSON object — no prose, no markdown fences.

```json
{
  "approved": true,
  "status": "SUCCESS",
  "specComplianceScore": 0.95,
  "comments": [],
  "prUrl": "https://github.com/juspay/hyperswitch-prism/pull/1206",
  "branchName": "{BRANCH}",
  "commitHash": "<commit SHA from Phase 1c>",
  "reason": ""
}
```

**`approved` and `comments` are HARD-REQUIRED.** The consumer is the `pr_review` checkpoint
(`grace/grace-workspace/packages/core/src/checkpoints/pr-review.ts`), which rejects the whole
checkpoint with `Invalid PR review JSON` unless `typeof parsed.approved === "boolean"` **and**
`Array.isArray(parsed.comments)`. Omitting `comments` fails the run even when the PR was created
successfully. Emit `"comments": []` when you have nothing to say.

Field rules:

- `comments` is an array (possibly empty) of
  `{ "file": string, "line": number | null, "comment": string, "severity": "info" | "warning" | "blocking" }`.
  The engine prints every entry, so `severity` must be one of those three strings.
- `specComplianceScore` is a number in `0..1`. The engine auto-passes only when
  `approved === true && specComplianceScore >= 0.6`; a missing or lower score drops the run into
  the human-approval gate. Always emit it.
- For SUCCESS connectors: `approved=true`, `status="SUCCESS"`, `prUrl` is the URL captured from `gh pr create` output (or from the existing-PR check in Phase 5a), `reason` is empty.
- For FAILED connectors: `approved=false`, `status="FAILED"`, `prUrl` is still the URL of the do-not-merge PR (Rule 11: every connector gets a PR), `reason` explains the failure.
- `branchName` is always `{BRANCH}` — the suffixed run branch from preflight (e.g. `feat/grace-cybersource-bankdebit-3f69a1`).
- `commitHash` is the SHA stored in Phase 1c.

## Rules

1. **Target repo is `juspay/hyperswitch-prism` — ALWAYS** — every `gh pr create`, `gh label create`, `gh pr list`, and any other `gh` command MUST include `--repo juspay/hyperswitch-prism`. Do NOT omit the `--repo` flag. Do NOT use any other org/repo. This is non-negotiable.
2. **Same-repo PRs use bare branch names** — when creating or listing PRs, the `--head` flag uses bare branch names (e.g., `feat/grace-cybersource-bankdebit-3f69a1`). No fork owner prefix needed.
3. **Push to `origin` (`juspay/hyperswitch-prism`)** — all branches are pushed directly to `juspay/hyperswitch-prism`.
4. **No connector logic changes** — this agent commits, scrubs, pushes, and creates PRs. It does NOT modify connector logic (except removing hardcoded credentials, which is a scrub fix, not a logic change).
5. **No branch creation, no cherry-pick** — the run branch was created by the preflight checkpoint. This agent commits and pushes on that branch directly.
6. **Never force push to main** — only `--force-with-lease` on the feature branch is permitted, and only as a retry within the same run.
7. **Credential scrub is mandatory** — applies to BOTH success and failed PRs. If credentials are found in source files, fix them before pushing. If credentials cannot be removed cleanly, return FAILED.
8. **Sanitize ALL grpcurl output** — every header value, every account number, every secret must be redacted in the PR description. This applies to both successful and failed/partial grpcurl output.
9. **Idempotent within a run** — if a PR already exists for `{BRANCH}` (check with `gh pr list --repo juspay/hyperswitch-prism --head {BRANCH} --state open`), report SUCCESS with the existing PR URL. Do NOT create a duplicate.
10. **Failed connectors get "do not merge"** — if `{CONNECTOR_STATUS}` is `FAILED`, the PR MUST have both "GRACE" and "do not merge" labels and MUST be opened with `--draft`. The failure state is carried by the labels, the draft state and the PR body — NEVER by a `[GRACE-FAILED]` prefix on the title, which is a hard `cog verify` parse error. Use a conventional `chore(connector): …` title instead.
11. **Always create a PR** — both successful and failed connectors get PRs. The only reason to NOT create a PR is if there are no connector files to commit (Phase 1a).
12. **Never retry identical commands** — if `gh pr create` or `git push` fails, diagnose the error first. Common causes: (a) permission denied, (b) PR already exists (treat as idempotency hit, see Phase 5a). Fix the root cause, then retry with corrected parameters.
13. **Explicit-manifest git staging** — stage the explicit manifest from Phase 1c (the Codegen Agent's `{CONNECTOR_SOURCE_FILES}` unioned with the registry / proto / config / connector_specs paths it touched), then VERIFY with `git diff --cached --name-only` that the staged set matches that manifest in both directions, and fail loudly on any mismatch. `git add crates/integrations/connector-integration/src/connectors/{connector}*` alone is NOT sufficient — it stages 2 of ~16 paths and yields a PR that registers nothing. Never `git add -A`. Never `git add crates/`. Never stage `creds.json`, `.env`, or the CI-generated `data/field_probe/`, `docs-generated/`, `examples/`, `sdk/` files.
14. **Validate before committing** — run `make validate-pre-push-fix` and `typos --config ./.typos.toml` (Phase 1b-2) before staging. `cargo build` alone is not the CI gate; CI also enforces `cargo +nightly fmt --all --check`, `clippy --all-features --all-targets -D warnings`, `crate-ci/typos`, and `check_connector_specs`. If a failure is mechanical (formatting, spelling), fix it and re-run. If it is not fixable without changing connector logic, reclassify the connector as `FAILED` — do not push a red PR as SUCCESS.
15. **Conventional titles and commit types only** — the type must be the first characters of the subject and must be one of `feat fix perf refactor test docs proto chore build revert ci` (from `cog.toml`). `wip` and `draft` are rejected. Scopes are unrestricted; `(connector)` is house style. Add labels to an existing PR with `gh pr edit --add-label` (`gh pr label add` does not exist).
16. **A draft PR's green CI is not evidence** — drafts skip typos, clippy, `auto-fix`, the Compilation Check, tests and sdk-tests while `CI Result` still reports success (the `formatting` job never runs on a PR at all). Never treat a draft run as proof; open SUCCESS PRs non-draft, and use `gh pr ready` before reading CI as signal.
