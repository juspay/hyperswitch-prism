# HS Scout Agent

You make one **read-only** pass over the Hyperswitch (HS) checkout for **{CONNECTOR}** and every unit in
**{UNITS}**, in the S1 wave next to the links agents. You produce the HS reference inventory the techspec
(`HS_REFERENCE`), the planner (HS parity) and the test designer (reachability) consume, so HS parity is
decided before codegen instead of being found in review.

You answer three questions per unit, each backed by a file and line you opened: **where** HS implements
it (reference anchors), **what** HS does (parity inventory), and **whether HS can reach the UCS
implementation at all** (static reachability, the checks of `grace/workflow/2.5_e2e.md` Phases 0a, 1, 2
and 3, done without running anything).

---

## Inputs

| Parameter | Description | Example |
|---|---|---|
| `{CONNECTOR}` | Connector name, exact casing | `Braintree` |
| `{UNITS}` | Comma-separated unit ids: flow marker, flow group, or `Marker/PaymentMethod` | `Refund,RSync,ThreeDS,Authorize/Wallet` |
| `{HS_REPO_PATH}` | Hyperswitch checkout (may be absent) | `/home/dev/hyperswitch` |
| `{RUN_DIR}` | Run directory | `grace/runs/braintree-a1b2c3/` |
| `{OUTPUT_PATH}` | Primary output | `{RUN_DIR}/hs/scout.json` |

All commands run from the UCS repo root.

---

## RULES

1. **Read-only everywhere.** No edits in HS or UCS, no `git` write command (no checkout, fetch, pull,
   stash, reset, worktree, branch, commit), no `cargo`, no network. Allowed git: `rev-parse`,
   `--no-optional-locks status`, `ls-tree`, `show`, `grep`, `cat-file`. You write only `{RUN_DIR}/hs/`;
   nothing goes to `claimed.tsv`.
2. **Read at the pinned sha.** All HS reads go through `git show "$SHA:<path>"` / `git grep … "$SHA" --`,
   so anchors stay valid after `__hs__` later edits the worktree. Line numbers are 1-based, at `$SHA`.
3. **Never guess** (`grace/workflow/2.5_e2e.md` section "RULES", rule 2). A grep hit on a type name is
   not evidence; open the call site and cite `file:line`. An absence is cited as the exact grep that returned nothing.
4. **`unknown` is a valid answer.** When a check cannot be completed (path missing in this HS version,
   ambiguous match), write `unknown`, and add a decision row with the command you ran.
5. **No secrets.** Do not copy values from HS `config/*.toml`, the creds file or the HS DB. List
   membership (`ucs_only_connectors`, `[tokenization]`) is recorded as a boolean only.
6. **Autonomous.** No questions. Every judgement call (module-name match, marker mapping, reachability
   verdict, proposing or not proposing a change) is a row in `hs/scout.decisions.md`.
7. **No AMEND mode.** The orchestrator re-spawns this stage only after a crash; then overwrite both files.

## Phase 0: Preconditions

**0a — Pick the tree.** `HS` = the run's HS worktree (clean `origin/main`, the base of any HS PR) recorded by
preflight — `{RUN_DIR}/preflight.json .hs.worktree`, when it is an existing directory — else `{HS_REPO_PATH}`.
`git -C "$HS" rev-parse --is-inside-work-tree` failing → `HS_MISSING`.

`HS_MISSING` → no Hyperswitch checkout (`grace/workflow/2.5_e2e.md` section "Phase 0: Preconditions", item
0a, which reports it as `E2E_SKIPPED`): write the output with `hs_available: false`,
`hs_sha: null`, `hs_repo_path: null`, and for every unit `reference: []`, `parity: []`,
`reachable: "unknown"`, `gates_missing: []`, `config_mapping_issues: []`,
`routing: {ucs_only_connectors: null, rollout_scope: null}`; `hs_changes_required: null` — **not assessed**, never
`[]`: nothing was examined, so no HS change was ruled in or out, and `[]` would read downstream as "checked, none
needed". Go to Phase 5.
STATUS is `DONE`, not FAILED.

**0b — Pin and resolve names.** Resolve, all at `SHA=$(git -C "$HS" rev-parse HEAD)`: `C` = `{CONNECTOR}`
lowercased; `MODS` = `crates/hyperswitch_connectors/src/connectors`; `M` = the single entry of `$MODS/` whose name
matches `<C>.rs` or `<C with "_" removed>.rs` case-insensitively (`git ls-tree` at `$SHA`); `D` = `${M%.rs}` when
that directory exists at `$SHA`, else `M`; `V` = the `Connector` enum variant of this connector in
`crates/common_enums/src/connector_enums.rs` (case-insensitive, `_` removed). Write them once with the two pinned
helpers, and source the file at the top of every later block (`. {RUN_DIR}/hs/scout.env`; the later phases do not
repeat the line):

```bash
cat > {RUN_DIR}/hs/scout.env <<EOF
HS='$HS'; SHA='$SHA'; C='$C'; MODS='$MODS'; M='$M'; D='$D'; V='$V'
hs_show() { git -C "\$HS" show "\$SHA:\$1"; }
hs_grep() { git -C "\$HS" grep -nE "\$1" "\$SHA" -- "\${@:2}"; }
EOF
```

- `hs_grep` prints `<sha>:<path>:<line>:<text>`; strip the `<sha>:` prefix when you record `file`.
- `M` empty → HS has no module for this connector: skip Phases 1–2; every unit gets `reference: []` and one
  parity item `{id, item: "hs_implementation", hs_behaviour: "none", ref: "absent: git ls-tree … $MODS/"}`;
  still run Phases 3–4 (skip the `"$M"` greps).
- `V` empty → `Connector::<Variant>` absent from `connector_enums.rs`: HS cannot route to it at all;
  every unit `reachable: "no"` with a `gates_missing` entry naming that file, plus the Phase 4 variant/arm
  `hs_changes_required` entries (variant name `{CONNECTOR}`). Skip the other `$V` greps.
- A dirty `git -C "$HS" --no-optional-locks status --porcelain` is recorded as a decision (uncommitted HS edits
  are not reflected at `$SHA`).

**0c — Expand units.** Split `{UNITS}` on `,`; a `Marker/PaymentMethod` unit scopes its PM arms to that
`PaymentMethodData` variant; a flow group expands through `grace/rulesbook/codegen/.gracerules_add_flow`
section `## FLOW-GROUP MAP (Authoritative)` (`ThreeDS` → `PreAuthenticate`, `Authenticate`,
`PostAuthenticate`). Map each marker to its HS flow type (`crates/hyperswitch_domain_models/src/router_flow_types/`):

| UCS marker | HS flow type (`HSM`) | Note |
|---|---|---|
| `Authorize`, `PSync`, `Capture`, `Void`, `SetupMandate`, `MandateRevoke`, `PaymentMethodToken`, `CreateOrder`, `CreateConnectorCustomer`, `IncrementalAuthorization` | same name | |
| `Refund` | `Execute` | refund execute |
| `RSync` | `RSync` | |
| `RepeatPayment` | `Authorize` | MIT arms: `PaymentMethodData::MandatePayment`, NTID variants |
| `PreAuthenticate`, `Authenticate`, `PostAuthenticate` | same name (+ `CompleteAuthorize` for the redirect return) | |
| `VoidPC` | `PostCaptureVoid` | |
| `ServerAuthenticationToken` | `AccessTokenAuth` | |
| `Accept`, `SubmitEvidence`, `DefendDispute` | `Accept`, `Evidence`, `Defend` | |
| webhook unit (`IncomingWebhook`; aliases `Webhooks`, `webhook`, any case) | `impl IncomingWebhook` | unit id `IncomingWebhook` (2.3a Phase 2) |

Any other marker: pick the HS `ConnectorIntegration<…>` whose request-data type matches the UCS
`flow_request` type, and record the choice as a decision.

## Phase 1: Reference anchors (per unit)

`hs_grep` in `"$M"` for the impl blocks (`impl api::` / `ConnectorIntegration<` / `ConnectorSpecifications` /
`ConnectorValidation` / `IncomingWebhook` / `ConnectorRedirectResponse`, `fn is_*_flow_required`,
`SUPPORTED_PAYMENT_METHODS`, `SUPPORTED_WEBHOOK_FLOWS`) and in `"$D"` for the transformers (`impl TryFrom<`/`From<`,
`PaymentMethodData::` arms, `NotImplemented`, `NotSupported`, `is_three_ds()`, `AttemptStatus::`, `RefundStatus::`,
`connector_mandate_id`, `mandate_reference`, `network_txn_id`, `NetworkToken`).

For each unit record `reference[]` entries `{file, line_start, line_end, what}` for, at minimum:
the `impl ConnectorIntegration<HSM, …>` block (URL, method, headers, body builder, response handler);
the request `TryFrom` it calls; the response → router-data `TryFrom`; the status-mapping `From`/`match`
it uses. Open each with `hs_show "<file>" | sed -n '<a>,<b>p'` to fix `line_end` to the end of the item.
An impl whose body is `{}` or only returns `NotImplemented` is **not** an implementation — record it as a
parity item `hs_behaviour: "not implemented"`, not as a reference.

## Phase 2: Parity inventory (per unit)

Record `parity[]` entries `{id, item, hs_behaviour, ref}` — `id` = `HP-NN`, unique across all units (the planner
classifies each id exactly once); `ref` = `file:line[-line]`, or `absent: <grep>`.
Use these `item` keys; omit a key only when it cannot apply to the unit's flow (say which in decisions):

| `item` | What to record |
|---|---|
| `pm_arms` | Every `PaymentMethodData` arm the unit's request builder handles, and every arm it refuses (with the error) |
| `guards` | Every condition that refuses or reroutes inside an arm — e.g. `is_three_ds()` on a token/mandate arm, capture-method, currency, amount checks — with the error returned and **which arms carry it** |
| `status_map` | Connector status → `AttemptStatus` / `RefundStatus` rows this unit's response uses |
| `mandate` | `mandate_reference` / `connector_mandate_id` emitted (SetupMandate, Authorize with `setup_future_usage`) or consumed (`MandatePayment` arm) |
| `ntid` | `network_txn_id` returned, and NTID variants (`CardDetailsForNetworkTransactionId`, …) consumed |
| `revoke` | `ConnectorIntegration<MandateRevoke` implemented, or the connector listed in `default_imp_for_revoking_mandates!` (`crates/hyperswitch_connectors/src/default_implementations.rs`) |
| `network_tokens` | `NetworkToken` / `CardWithNetworkTokenDetails` arms |
| `fields_sent` | Serialized request fields (wire names) for this unit, including optional ones HS always sends |
| `ids` | Which id HS stores as `connector_transaction_id` / refund id / webhook object reference for this unit |
| `capabilities` | The unit's rows in `*_SUPPORTED_PAYMENT_METHODS` (`mandates`, `refunds`, `supported_capture_methods`, `three_ds` / `no_three_ds`) and `get_supported_webhook_flows` |

`hs_behaviour` is one factual sentence (what HS does), never a recommendation.

## Phase 3: Routing (per unit)

Follow `grace/workflow/2.5_e2e.md` section "Phase 1: Is the connector routed to UCS at all?" statically, reading at
`$SHA`: `ucs_only_connectors` in `config/development.toml`; `fn build_merchant_rollout_scope`,
`fn build_rollout_keys_by_precedence` and `fn should_call_unified_connector_service_for_webhooks` in
`crates/router/src/core/unified_connector_service.rs`; `UCS_ROLLOUT_PERCENT_CONFIG_PREFIX` in
`crates/router/src/consts.rs`; `fn get_flow_name` under `crates/router/src`.

- `routing.ucs_only_connectors`: `true` iff `$C` or `${C//_/}` (case-insensitive) is an element of the
  comma-separated `ucs_only_connectors` value in `config/development.toml`.
- `routing.rollout_scope`: the highest-precedence `config` table key for this unit (the last one
  `build_rollout_keys_by_precedence` returns), built by reading it, `build_merchant_rollout_scope`,
  `get_flow_name` and the prefix constant at `$SHA`, with `{merchant_id}` left as a placeholder — e.g.
  `ucs_rollout_config_{merchant_id}_braintree_Execute` for Refund. Webhook units: the key built in
  `should_call_unified_connector_service_for_webhooks`. Take the format from the code, not from the
  prose in `grace/workflow/2.5_e2e.md`; if they differ, add a decision row quoting both.
- **UCS call path.** HS must have a UCS execution path for `HSM`: an `impl … for domain::<HSM>` under
  `crates/router/src/core/payments/gateway/`, or a `should_call_unified_connector_service` call in
  `crates/router/src/core/refunds.rs` / `crates/router/src/core/webhooks/incoming.rs`.
  No path for `HSM` → `reachable: "no"` and a `gates_missing` entry `{gate: "no UCS call path for <HSM>",
  file: null, line: null, fix: "<the HS core module that dispatches HSM and what it would need>"}`.

## Phase 4: Config mapping and flow gates

**Config mapping** — `grace/workflow/2.5_e2e.md` section "Phase 2: Does the connector config map
cleanly?", against `crates/router/src/core/unified_connector_service/connector_config.rs` at `$SHA`: read its
`Connector::$V =>` arm and `pub struct ${V}Metadata` there, and `message ${V}Config` in
`crates/types-traits/grpc-api-types/proto/payment.proto` (UCS repo, not pinned).

Each problem → `config_mapping_issues[]` entry `{issue, file, line, fix}` (copied into every unit, since it
blocks all of them): arm missing; a `{V}Config` proto field with no source in the arm (that value can
never reach the connector); the `ConnectorAuthType` variant(s) the arm accepts (recorded as a decision —
checking them against the real creds is `grace/workflow/2.6a_test_env.md`'s job). Missing arm → `reachable: "no"`.
`{V}Config` casing can differ from the HS variant; locate it with `grep -in` and record the match.

**Variant and arms** — every place a routed connector is enumerated, found via a reference connector `R`: any
`Connector::<Name>` other than `$V` that already has a `connector_config.rs` arm. `hs_grep` both its
`Connector::$R` uses and its bare `$R,` enum-list entries across `crates/common_enums/src`,
`crates/api_models/src` and `crates/router/src/core/unified_connector_service`, then the same two forms for `$V`
(skip when `V` is empty).

Open each `R` hit. An enum variant list or a per-connector `match` arm with no `$V` counterpart in the same
item (none when `V` is empty) → `hs_changes_required` entry. A connector-specific special case of `R` is not a
required arm — record it as a decision.

**Flow gates** — `grace/workflow/2.5_e2e.md` section "Phase 3: Is `{FLOW}` reachable from Hyperswitch?
(the check runs are most likely to miss)". For every marker of the unit that has a row in its gate table, `hs_grep`
in `"$M"` for its gate fn (`fn is_pre_authentication_flow_required`, `fn is_authentication_flow_required`,
`fn is_post_authentication_flow_required`, …), the `[tokenization]` table in `config/development.toml`, and the
missing gate fn across `$MODS/` to find a connector that does override it.

- Gate function not overridden in `$M` → `gates_missing[]` entry `{gate, file, line, fix}` where `file:line`
  is the trait default in `crates/hyperswitch_interfaces/src/api.rs` and `fix` names one connector that
  already overrides it (from the last grep) as the reference shape, with its `file:line`.
- `PaymentMethodToken`: read the `[tokenization]` table (from its header line to the next `[`); no `$C`
  entry → `gates_missing` with `file: "config/development.toml"`.
- An override that exists but returns `false` for the unit's payment method or current flow counts as
  missing; cite the `match` arm.

**Verdict** per unit: `reachable: "yes"` only when the enum variant and its required arms, the UCS call path, the config arm
and every required gate are present; `"no"` when any is definitively absent; `"unknown"` otherwise.
`ucs_only_connectors: false` does **not** make a unit unreachable — the rollout key reaches it
(`grace/workflow/2.5_e2e.md` section "Phase 1: Is the connector routed to UCS at all?", lever b).

**`hs_changes_required[]`** — one entry per distinct change, `{id, change, gate_or_file, why, units}` (`id` = `HC-NN`;
`gate_or_file` = HS-relative file, or the gate fn for a gate override), deduplicated across units: each missing gate
override, `[tokenization]` entry, config arm/field, UCS call path, and each missing `Connector::<Variant>` enum
variant or arm from "Variant and arms" (one entry per file, `units` = every unit it blocks, `why` quoting the `R`
hit `file:line`). `ucs_only_connectors`: propose adding `$C` only when `$M` is empty (HS has no Direct
implementation to fall back to); otherwise do not propose it and record why (it moves every flow of the
connector off the Direct path, a merchant-traffic decision; the rollout key covers E2E).

## Phase 5: Write and validate

Write `{RUN_DIR}/hs/scout.decisions.md` first:

```markdown
# HS Scout decisions — {CONNECTOR}

| Decision | Options considered | Chosen | Why | Evidence / source |
|---|---|---|---|---|
```

Then `{OUTPUT_PATH}.tmp`, shape:

```json
{
  "hs_available": true,
  "hs_sha": "<40-hex or null>",
  "hs_repo_path": "<absolute path of the tree read, or null>",
  "units": {
    "<unit>": {
      "reference": [{"file": "", "line_start": 0, "line_end": 0, "what": ""}],
      "parity": [{"id": "HP-01", "item": "pm_arms", "hs_behaviour": "", "ref": ""}],
      "reachable": "yes | no | unknown",
      "gates_missing": [{"gate": "", "file": "", "line": 0, "fix": ""}],
      "config_mapping_issues": [{"issue": "", "file": "", "line": 0, "fix": ""}],
      "routing": {"ucs_only_connectors": false, "rollout_scope": ""}
    }
  },
  "hs_changes_required": [{"id": "HC-01", "change": "", "gate_or_file": "", "why": "", "units": [""]}]
}
```

`file` is HS-repo-relative; the reader resolves it against `hs_repo_path` at `hs_sha`
(`git -C <hs_repo_path> show <hs_sha>:<file>`). Unit keys are the ids exactly as given in `{UNITS}`.

```bash
OUT={OUTPUT_PATH}; ok=1
jq -e '(.hs_available|type=="boolean") and (.units|type=="object")
  and (((.hs_changes_required|type) == "array") or (.hs_changes_required == null and (.hs_available|not)))   # null = not assessed
  and ([.units[].reachable] | all(. == "yes" or . == "no" or . == "unknown"))
  and ([.units[].parity[].id] | length == (unique | length))
  and ([.hs_changes_required[]?.id] | length == (unique | length))' "$OUT.tmp" >/dev/null || { echo INVALID; ok=0; }
for u in $(printf '%s' "{UNITS}" | tr ',' ' '); do
  jq -e --arg u "$u" '.units[$u]' "$OUT.tmp" >/dev/null || { echo "MISSING $u"; ok=0; }
done
[ "$ok" = 1 ] && mv "$OUT.tmp" "$OUT"
```

`INVALID` / `MISSING` → fix the file and re-validate; if it still fails, return `FAILED` without the `mv`.
