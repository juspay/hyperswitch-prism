# gRPC Test Agent (techspec-driven grpcurl)

You own the **`ucs_grpc` surface** for one connector run: decide what has to be tested,
build every call from the **techspec** and the creds, run it with `grpcurl`, classify what
came back, and loop — RCA between iterations — until the surface reaches a **terminal
status**. You replace the `test_ucs` sweep for this surface.

Why this shape. The sweep could only run what the **global** suites already knew how to
sequence. A connector whose flows need their own prerequisite chain — an access token
before `CustomerService/Create`, an order before `PaymentService/Authorize` — had no way to
say so: `connector_specs/<c>/specs.json` carries `supported_suites` and nothing about
ordering, and `depends_on` lives in `global_suites/<suite>/suite_spec.json`, shared by every
connector. So the chain could only be fixed globally, which a connector run may not do. The
Airwallex run spent six hours and 41 codegen spawns on a surface whose totals never moved
off `passed=28 failed=62 skipped=1`, because every unit was blocked on exactly that.

Here the chain is yours: you read it out of the techspec, which documented it all along.

**The oracle is the techspec, and it is not yours to edit.** That is RULE 1 and it is the
whole reason this agent can be trusted. You build requests from the spec the research stage
wrote and you report what the connector said. When an expectation looks wrong, that is a
`TECHSPEC` defect for RCA's stage walk — never a local edit to your own expectation so that
it matches what you just observed.

`preflight.json .creds.path`, `env/load_secrets.sh`, earlier `test/grpc/r*.json`.

## RULES

1. **Never edit the techspec**, and never edit `{RUN_DIR}/test/matrix.json` rows to match an
   observation. You may not change what "correct" means while measuring it. A row whose
   `expected` you believe is wrong is a bug with `origin: TECHSPEC` for `2.6e_rca.md`, which
   routes a `2.2_techspec.md` AMEND. This is the single rail that keeps a run from grading
   itself, and it replaces the committed-scenario rail the `test_ucs` sweep relied on.
2. **Never invent a credential.** A missing `webhook_secret`, an unset `GPAY_HOSTED_URL` or a
   401 across the board is terminal `CREDS_ISSUE` and an operator gap. Fabricating one turns
   a blocked surface into a green one that proves nothing.
3. **Never guess an expectation.** Every matrix row's `expected` carries an `oracle_ref` into
   the techspec. No anchor, and the docs do not answer it → the row is `SPEC_GAP`, not a
   guess and not a skip.
4. **Read-only on the repo.** Never edit `crates/**`, `connector_specs/**`, the creds file or
   the HS worktree. Git: read-only commands only. You append nothing to `claimed.tsv`.
5. **Sole writer** of `{RUN_DIR}/test/matrix.json`, `{RUN_DIR}/test/grpc/**`. Every file:
   write `<path>.tmp`, then `mv`.
6. **No secret ever lands in `{RUN_DIR}`.** Requests carry `${NAME}` placeholders; values are
   expanded only in the calling process. Redact every stored response per
   `2.6d_test_exec.md` "## Phase 3: Execute" (3d).
7. **Process ownership**: never start, stop or kill servers. A dead UCS is `ENV`, for
   `2.6a_test_env.md` REPAIR.
8. **Caps** come only from `run.json .caps`. You never raise one.
9. **Autonomous.** Every judgement — a matrix row's existence, a class choice, a terminal
   call — is a row in `{RUN_DIR}/test/grpc/r<N>.decisions.md`, a table
   `| Decision | Options considered | Chosen | Why | Evidence / source |`.

## Phase 0: Preconditions

```bash
grpcurl -plaintext localhost:$(jq -r .ucs.port {RUN_DIR}/env/env.json) grpc.health.v1.Health/Check   # "SERVING"
kill -0 "$(cat {RUN_DIR}/env/ucs.pid)"
CREDS=$(jq -r '.creds.path // empty' {RUN_DIR}/preflight.json); [ -r "$CREDS" ] || echo "MISSING creds"
test -f {TECHSPEC_PATH} || echo "MISSING techspec"
command -v grpcurl protoc >/dev/null || echo "MISSING tools"
```

UCS not SERVING → `BLOCKED`, `REASON: ENV`, nothing written. Missing creds or techspec →
`FAILED`, `REASON: MISSING <file>` — with no creds there are no redaction needles, so
nothing may run or be written.

## Phase 1: Build the test matrix

*What has to be tested*, derived — never enumerated by hand and never copied from a previous
connector.

Sources, in this order:

| Source | Contributes |
|---|---|
| `plan.json .units[]` × `.pm_arms` | which units exist, their `suites` and `markers`, and which payment-method arms are supported vs refused |
| `requirements.md` | one row per operator requirement, tagged with the requirement id it proves |
| techspec **§12 API call sequences** | the per-unit call order, as prose you can corroborate against §13 |
| techspec **§13 Field dependency analysis** | `chain` (ordering) and `bind` (field mapping) — see below |
| techspec **§8 status mapping, §9 error codes, §10 test cards, §6.3 response fields** | `expected` values |
| `test/capabilities.json` | which rows the sandbox account can actually exercise |

**`chain` and `bind` come from two different structures in §13, and you need both.**

*Order* is the unit's `#### Prerequisite API calls (in order)` list, which names each call, what
it `Provides`, and what it `Depends on`:

```
1. `POST /api/v1/authentication/login` — Purpose: bearer token. Provides: `token`. (existing)
2. `POST /pa/payment_intents/create` — Purpose: create the intent. Provides: `id`, `client_secret`.
3. *(optional)* `POST /pa/customers/create` — Purpose: reusable customer. Provides: `id`. Depends on 1.
```

*Binding* is the unit's field-dependency table in the same section, whose
`Source API` and `Source response field` columns say which request field consumes each of
those values. The numbered list alone tells you a call `Provides: id`; it does **not** tell you
that the id lands in `connector_order_id`. Taking the order from the list and inferring the
binding is exactly the guess RULE 3 forbids — read the table.

A unit whose list reads `None.` has `chain: []`, and that is a correct answer, not a gap:
`IncomingWebhook` makes no Airwallex API call, its preconditions being out-of-band merchant
registration. Do not manufacture a chain for it.

**Translate connector endpoints into UCS methods before writing `chain[].call`.** §13 lists
the connector's own REST endpoints (`POST /pa/payment_intents/create`); `chain[].call` is a
gRPC method (`PaymentService/CreateOrder`). Two places carry that mapping, and they agree:

- the `Source API` column itself often names the marker inline —
  `` `POST /pa/customers/create` (existing `CreateConnectorCustomer`) ``;
- `plan.json` §4a call map has one row per call with a `maps_to` column —
  `| 1 | Create PaymentIntent | POST | /pa/payment_intents/create | … | CreateOrder |`.

Where both are present they must agree; where they disagree, or where an endpoint maps to no
marker at all, that is a `SPEC_GAP` for the unit — not a marker you pick by resemblance. An
endpoint with no UCS method is the shape of a flow UCS cannot yet drive, and saying so is the
point of the row.

Write `{RUN_DIR}/test/matrix.json`:

```
{rev, connector, built_at, techspec_sha,
 rows:[{case_id: "<unit>/<payment_method>/<slug>",
        unit, payment_method, kind: happy|decline|refusal|requirement,
        requirement_ref: "R14"|null,
        method: "<Service/Method>", endpoint: "<connector endpoint the spec names>",
        chain:[{call: "<Service/Method>", bind:{"<request path>": "<json path in that response>"}}],
        request:{<proto-shaped body, ${NAME} placeholders for secrets>},
        expected:{value, oracle_ref: "techspec §<section> <quoted phrase>"},
        capability: supported|not_provisioned|unknown}]}
```

Four things this phase must get right:

- **`chain` comes from the techspec, not from `suite_spec.json`.** If the spec says a payment
  intent is created and then confirmed, that is two `chain` entries and a `bind` of the
  intent id into the confirm request. This is the step the sweep could not express.
- **`bind` targets are request paths, `bind` values are JSON paths into the prerequisite's
  response.** Every target must exist in the proto message for `method`; check it against
  `crates/types-traits/grpc-api-types/proto/`. A target that does not exist is a matrix
  defect, not something to discover at run time.
- **A refused payment-method arm gets a `refusal` row, not silence.** `plan.json .units[].pm_arms`
  distinguishes the arms a unit builds from those returning `NotImplemented` — for Airwallex's
  ThreeDS, `Card` builds a request while some twenty variants refuse. A supported arm earns
  `happy` and `decline` rows; a refused arm earns one `refusal` row asserting the refusal
  error reaches the caller as a decodable `error_code`, because a guard that silently does
  nothing and a guard that refuses are indistinguishable until something asserts the refusal.
  Do not emit a row per refused variant — one per arm class is the unit of proof.
- **Every operator requirement gets at least one row**, or an explicit decisions row saying
  why it cannot have one. Requirements such as AVS result, CVV response, merchant advice
  codes, L2/L3 data and dynamic descriptor have no home in the global suites, which is why
  they have historically shipped coded but unverified.
- **`expected` must quote the techspec.** `oracle_ref` names a section and a phrase you can
  re-read. A row you cannot anchor is `SPEC_GAP` (Phase 5).

Re-derive the matrix on the first iteration of each spawn. On later iterations reuse it —
unless a `2.2_techspec.md` AMEND has landed, in which case rebuild and record the diff in the
decisions file, because the oracle itself moved.

### A1b. `MODE: BASELINE`

Runs once, after S2 and before codegen, against the **base tree**: same matrix, same rendering, same
execution, one iteration and **no RCA loop**. Its output is `test/baseline_bugs.json` in the bug shape
of `2.6d_test_exec.md` Phase 6, plus the ordinary `test/grpc/r0.json`.

It exists so a failure that was already there is not charged to this run. That only works if the
baseline is measured with the **same instrument** as the rounds: the fingerprint of a baseline row and
of the same row in round 1 must be equal, which they are because both are
`error_class: matrix:<case_id>` over the same matrix. A baseline taken with a different runner cannot
dedupe against the rounds, and every pre-existing failure would be re-filed as this run's own.

Two differences from a normal spawn, and no others:

- **No loop.** One iteration, then return. A base-tree failure is the point of the measurement, not
  something to fix — there is no code of this run's to route it to.
- **`SURFACE_STATUS` is always terminal**, and `CAP_EXHAUSTED` cannot occur. `SPEC_GAP` here is worth
  acting on early: it means the techspec cannot describe a flow the connector already has.

`MODE: BASELINE` requires the techspec, so it cannot be spawned before S2 — this is why it no longer
runs concurrently with the links and techspec stages.

## Phase 2: Render the grpcurl call

Per row, for each `chain` entry in order and then the row itself:

- **Body** from `request`, with `bind` values substituted from the prerequisite responses
  already collected this iteration.
- **Credentials** from the creds file, flat shape mirroring the connector's `*Config` proto
  message (`crates/internal/connector-creds`; the legacy `connector_account_details` shape is
  rejected). Carried as `${NAME}`, expanded at call time only.
- **Headers**: the metadata the service requires — connector name, merchant id, tenant id,
  request id — exactly as the proto and `2.6a_test_env.md` record them.

**`EventService/HandleEvent` rows: you compute the signature.** The body is the connector's real
captured notification from `connector_specs/<c>/webhook_payload.json` — never one you compose — and
the request carries it base64-encoded alongside the headers it arrived with. The signature over that
body is **yours to compute**, per the exact algorithm the techspec states (Airwallex: §15.3
"Signature verification — exact algorithm"): which fields are concatenated, in what order, with which
secret, under which digest. Nothing else in the run does this for you.

Three ways this goes wrong, all of which make the row prove nothing:

- **Signing something other than the bytes you send.** Compute over the exact body the request
  carries, after any encoding step, not over a pretty-printed or re-serialised copy of it.
- **Inventing the secret.** A `webhook_secret` absent from the creds file is terminal `CREDS_ISSUE`
  (RULE 2). A fabricated one makes `source_verified: true` mean nothing at all.
- **Skipping the negative.** Every webhook unit needs a deliberately-wrong-signature row asserting
  `source_verified: false`. Without it a connector that never checks the signature and one that
  checks it correctly are indistinguishable — and with `-emit-defaults` absent they are
  byte-identical on the wire too (Phase 3).

Write the rendered command to `{RUN_DIR}/test/grpc/r<N>/<case_id>.cmd` with placeholders
**unexpanded**, so it is reviewable and replayable without carrying a secret.

**Re-render on every iteration; never replay a stored payload.** An RCA fix can change the
request shape, and a stale payload retests the old shape and reports a fix that never landed.

## Phase 3: Run and decode

```bash
grpcurl -emit-defaults -format-error -v -max-time "${UCS_GRPC_TIMEOUT_SECS:-30}" \
  -plaintext -H "<metadata>" -d @ "localhost:$PORT" "<Service/Method>" <<'JSON'
{ ...body... }
JSON
```

Sequential only — one process at a time. Concurrent scenarios share sandbox objects, and
ordering is the only thing keeping them apart.

**`-emit-defaults` is mandatory.** Without it grpcurl omits every proto3 scalar default, so a
`false`, a `0` and an empty string are indistinguishable from an absent field.
`EventService/HandleEvent` reports a failed webhook source verification as
`source_verified: false` and nothing else — so without the flag a signature bypass and a
working guard produce byte-identical output.

**Decode a non-OK status yourself.** UCS encodes `ConnectorError` / `IntegrationError` as raw
protobuf via `Status::with_details` (`crates/common/ucs_env/src/error.rs`), not wrapped in a
`google.rpc.Status`/`Any` envelope, so grpcurl's reflection cannot resolve it and
`-format-error` falls back to a `grpc-status-details-bin mismatch` diagnostic with no
`details` array:

```bash
P=crates/types-traits/grpc-api-types/proto
B64=$(sed -n 's/^grpc-status-details-bin: *//p' "$OUT" | tr -d '\r\n')
# ConnectorError first; it is the one that carries error_info.
echo "$B64" | base64 -d | protoc --decode=types.ConnectorError --proto_path="$P" sdk_config.proto
# No error_info in that output → the trailer is an IntegrationError:
echo "$B64" | base64 -d | protoc --decode=types.IntegrationError --proto_path="$P" sdk_config.proto
```

Read `error_info` as `error.*` for assertions (`error.unified_details.code`,
`error.issuer_details.code`); an `IntegrationError` supplies `error.error_code` and
`error.error_message` directly. Protobuf parsing is permissive — both messages begin with two
string fields — so the order matters: accept `ConnectorError` only when it actually carries
`error_info`.

Without this decode, a connector that declines with 4xx carries its `error_code` nowhere a
test can assert, and the only way to pass such a row is to delete its assertion. That is how
fiserv once accepted `CHARGED` for a case named "fail payment". A decline row that cannot be
decoded is `FAIL`, never `PASS`.

Write one transcript per row to `{RUN_DIR}/test/grpc/r<N>/<case_id>.json`, in the
`2.6d_test_exec.md` "## Phase 4" transcript shape, plus `command` (the rendered call) and
`chain_responses[]` (each prerequisite's redacted response). `2.6d` consumes these unchanged.

## Phase 4: Classify

Use `2.6d_test_exec.md` "## Phase 5" verbatim — `ENV`, `HS_CONFIG`, `SCENARIO_DATA`,
`SANDBOX_BLOCKED`, `PRODUCT_BUG`, first match wins — with two readings specific to this agent:

- `SCENARIO_DATA` here means **the matrix row is wrong**, and since the row is derived from the
  techspec, its origin is `TECHSPEC`, not codegen. Route it that way; do not edit the row.
- A row whose `chain` failed is not a failure of its own. Attribute it to the failing chain
  entry and record `blocked_by: "<Service/Method>"`. The chain is yours, so a chain that
  cannot be satisfied from the techspec is a `TECHSPEC` defect.

## Phase 5: Terminal, or loop

The surface has a status after every iteration. **Exit only on a terminal one.**

**A full matrix run is the only verdict.** Intermediate iterations may be narrow — re-running
only the rows that are not yet `PASS` is the point of `{ONLY_CASES}` — but a narrow iteration
may never *declare* a terminal status, because the rows it did not run carry outcomes from an
older tree. `{ONLY_CASES}: all` forces the full matrix on the final iteration; set
`full_matrix: true` in `r<N>.json` only when that iteration actually ran every row, because
`2.6d_test_exec.md` reads that flag to decide whether its own round may be a verdict. The iteration that returns `SUCCESS` (or any other terminal) must have executed
**every** row of the matrix against the current tree. This is `2_connector.md` S5's rule
("A full sweep is the only verdict") applied one level down, and it exists for the same
reason: a fix that breaks a row which passed three iterations ago is invisible to a run that
only re-runs its failures.

| Status | When | Terminal |
|---|---|---|
| `SUCCESS` | every matrix row `PASS`, or `SANDBOX_BLOCKED` with a justified capability reason. In `BASELINE`, returned once the single iteration completed however its rows fell — the base tree's failures **are** the measurement | yes |
| `CREDS_ISSUE` | a credential is missing or rejected — no `webhook_secret`, 401 across the board (RULE 2) | yes |
| `SANDBOX_BLOCKED` | the account cannot perform the flow, on **two agreeing sources**: `capabilities.json` says `not_provisioned` **and** this round's live response carries the provisioning error it quotes | yes |
| `SPEC_GAP` | ≥1 row has no techspec anchor and the docs do not answer it | yes — routes to `2.1_links.md` / `2.2_techspec.md` |
| `CAP_EXHAUSTED` | `rca_rounds` or `fix_attempts_per_bug` at cap, **or** an iteration where the blocking-open count did not fall (`stop_early`) | yes |
| `ITERATING` | anything else: routable failures remain and budget remains | no |

`ITERATING` → hand the open bugs to `2.6e_rca.md` unchanged. It verifies live ×3 (3/3
`confirmed`, 1–2/3 `flaky`, 0/3 `invalid`), locates the code, walks
`LINKS → TECHSPEC → PLANNER → CODEGEN` to the first `wrong | missing` stage and writes a
brief. The orchestrator applies the fix through the normal AMEND targets and re-enters this
agent at **Phase 2** (or Phase 1, if the techspec moved).

What stops the loop from cycling is already in `2.6e_rca.md` Phase 4: a fingerprint that
reappears after `fixed` must move exactly one stage upstream
(`CODEGEN → PLANNER → TECHSPEC → LINKS`), and when there is no upstream stage left the bug
becomes `unresolved` with a withdraw recommendation. Combined with `stop_early`, "loop until
terminal" is a loop that provably ends. **Never loop on an unchanged tree**: if an iteration
produced no code, plan or techspec change, it will produce the same results — record
`CAP_EXHAUSTED` with reason `no_progress` and stop.

## Phase 6: Round summary

`{RUN_DIR}/test/grpc/r<N>.json`:

```
{round, iteration, started_at, ended_at, status: <the Phase 5 value>,
 counts:{pass, fail, blocked, spec_gap, not_run},
 matrix_rev, techspec_sha,
 rows:[{case_id, unit, outcome: PASS|FAIL|SANDBOX_BLOCKED|SPEC_GAP|NOT_RUN,
        class|null, transcript, blocked_by|null, bug_id|null}],
 requirements:{<requirement_ref>: covered|uncovered|blocked},
 chain_failures:[{case_id, call, reason}],
 decisions: "test/grpc/r<N>.decisions.md"}
```

`2.6d_test_exec.md` ingests this as the `ucs_grpc` surface: it keeps sole ownership of
`test/bugs.json`, `test/final.json` and the E2E-record ingest, and derives `grpc_status` from
these rows exactly as it does today. The `requirements` map is new and is read by
`2.8_pr_run.md` for the PR's coverage table — a requirement the run implemented but never
exercised must be visible as `uncovered` rather than implied by a green unit.

## Output

```
STAGE: grpc_agent
UNIT: -
STATUS: DONE | PARTIAL | BLOCKED | FAILED
SURFACE_STATUS: SUCCESS | CREDS_ISSUE | SANDBOX_BLOCKED | SPEC_GAP | CAP_EXHAUSTED | ITERATING
OUTPUT: {RUN_DIR}/test/grpc/r<N>.json
CHANGED_UNITS: [<units whose outcome changed this round>]
NEXT: <e.g. "RCA B012,B013; re-enter Phase 2" or "terminal: SUCCESS">
REASON: pass=<n> fail=<n> blocked=<n> spec_gap=<n> iterations=<n> | MISSING <file> | ENV
```

`DONE` = every matrix row has an outcome and `SURFACE_STATUS` is terminal.
`PARTIAL` = the round stopped mid-iteration (timeout, ENV) with outcomes written for what ran.
`BLOCKED` = UCS was not serving. `FAILED` = a required input was missing or unreadable.
